This guide walks you through bootstrapping an OP Stack execution client from a pre-synced snapshot: download it, verify the checksum, extract it into your data directory, and start the node from the snapshot's tip instead of replaying the chain from genesis.

For **what** snapshots are available for OP Mainnet and OP Sepolia, see the [Snapshots reference page](/op-mainnet/network-information/snapshots).

## When to use a snapshot

<OpGethEol />

This guide assumes an `op-reth` node.

You don't always need one. With [execution-layer sync](/node-operators/reference/consensus-layer-sync) — `--syncmode=execution-layer` and `--l2.enginekind=reth` on `op-node` — `op-reth` retrieves blocks over the P2P network instead of deriving each one, which makes the initial sync much faster and, on most OP Stack chains, needs no snapshot at all. [Nethermind](https://docs.nethermind.io/get-started/running-node/l2-networks#op-stack) downloads what it needs automatically.

Use a snapshot when:

*   You are running an **archive node**, or otherwise need to trace the entire chain.
*   You simply want to skip the initial sync entirely: a mature chain's data directory can run to terabytes, and even execution-layer sync takes days from scratch. For scale, the current zstd-compressed snapshot downloads are about 1.3 TB (full) and 1.7 TB (archive) for OP Mainnet, and about 265 GB (full) and 262 GB (archive) for OP Sepolia; the extracted data directory is larger.

<Note>
  On **OP Mainnet**, syncing `op-reth` on a fresh data directory is another reason to use a snapshot: it satisfies the [pre-Bedrock state import requirement](/node-operators/op-reth/run/faq/sync-op-mainnet) in one step, even when execution-layer sync is enabled.
</Note>

## Before you begin

*   **Disk space**: you temporarily need room for both the compressed archive and the extracted data directory, so plan for roughly twice the snapshot size during the restore, on fast (NVMe-class) storage.
*   **Tools**: `curl` (or [aria2](https://aria2.github.io/), which can significantly speed up large downloads), `zstd`, and `tar`.
*   **A stopped client**: never extract into a data directory an execution client is actively using.

## Restore the snapshot

<Steps>
  <Step title="Pick a snapshot">
    Pick a recent snapshot matching your network and client from your chain's snapshot provider. For OP Mainnet, OP Sepolia, and the other OP Enterprise Fully Managed networks Optimism publishes snapshots for, select your network and sync type (full or archive, where offered) on [snapshots.optimism.io](https://snapshots.optimism.io/). The site shows each snapshot's `op-reth` version, date, size, and SHA256 checksum. The [Snapshots reference page](/op-mainnet/network-information/snapshots) describes what is available and lists other sources, including third-party providers.

    Prefer a storage v2 snapshot. `op-reth` storage v1 is [deprecated](/notices/op-reth-storage-v1-deprecation), and a data directory restored from a v1 snapshot must be migrated before storage v1 reaches end of support.
  </Step>

  <Step title="Download and verify it">
    Copy the download command (or the snapshot URL) from the snapshot site and run it. On snapshots.optimism.io, it has this form:

    ```bash
    curl -fL -o '<snapshot-file>.tar.zst' '<snapshot-url>'
    ```

    Also download the matching `<snapshot-file>.tar.zst.sha256sum` file (**Download checksum** on snapshots.optimism.io) into the same directory, then verify the archive against it:

    ```bash
    sha256sum -c '<snapshot-file>.tar.zst.sha256sum'          # Linux
    shasum -a 256 -c '<snapshot-file>.tar.zst.sha256sum'      # macOS
    ```

    Don't skip verification — a truncated multi-hundred-gigabyte download is easy to miss and produces a corrupt database.
  </Step>

  <Step title="Stop your node and clear the old datadir">
    If the node has run before and you want to start clean from the snapshot, stop the execution client and remove (or move aside) the contents of its data directory.
  </Step>

  <Step title="Extract into the data directory">
    Inspect the archive layout first, then extract it into your client's data directory:

    ```bash
    zstd -dc '<snapshot-file>.tar.zst' | tar -tf - | head -3

    mkdir -p <datadir>
    zstd -dc '<snapshot-file>.tar.zst' | tar -xvf - -C <datadir> --strip-components=1
    ```

    `--strip-components=1` removes the top-level wrapping directory inside the tarball. If the inspection shows files already at the archive root, omit it. Use the same path your client is configured with (the `--datadir` flag for `op-reth`).
  </Step>

  <Step title="Start the node and confirm it picked up the snapshot">
    Start the execution client pointed at the restored data directory, then confirm the node reports the snapshot's block height — not `0` — as its latest block:

    ```bash
    curl -s -X POST -H "Content-Type: application/json" \
      --data '{"jsonrpc":"2.0","method":"eth_blockNumber","params":[],"id":1}' \
      http://localhost:8545
    ```

    The node then syncs from the snapshot's tip to the current head, which takes minutes to hours depending on the snapshot's age. Once caught up, you can delete the downloaded `.tar.zst` archive to reclaim disk space.
  </Step>
</Steps>
