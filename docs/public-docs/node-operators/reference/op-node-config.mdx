This page provides detailed documentation for all available op-node configuration options, organized by functionality.

The options below match the `op-node v1.18.0` release (binary `v1.18.0-317746fd-2026-05-06T22:11:09Z`). 

Every flag also accepts the equivalent `OP_NODE_*` environment variable shown in each entry's *Environment variable* tab.

<Info>
  **Execution-client default has shifted.** The recommended execution client for new OP Stack deployments is now [op-reth](/node-operators/reference/op-reth-config). When pairing op-node with op-reth, set `--l2.enginekind=reth` (the binary still defaults to `geth` for backward compatibility).
</Info>

## L1 and L2 connection settings

Configure how op-node connects to L1 (Ethereum) and L2 (execution layer) endpoints.

### l1

Address of L1 User JSON-RPC endpoint to use (eth namespace required)

<Tabs>
  <Tab title="Syntax">`--l1=<value>`</Tab>
  <Tab title="Default">`"http://127.0.0.1:8545"`</Tab>
  <Tab title="Environment variable">`$OP_NODE_L1_ETH_RPC`</Tab>
</Tabs>

### l1.beacon

Address of L1 Beacon-node HTTP endpoint to use.

<Tabs>
  <Tab title="Syntax">`--l1.beacon=<value>`</Tab>
  <Tab title="Environment variable">`$OP_NODE_L1_BEACON`</Tab>
</Tabs>

### l1.beacon-header

Optional HTTP header to add to all requests to the L1 Beacon endpoint. Format: 'X-Key: Value'

<Tabs>
  <Tab title="Syntax">`--l1.beacon-header=<value>`</Tab>
  <Tab title="Environment variable">`$OP_NODE_L1_BEACON_HEADER`</Tab>
</Tabs>

### l1.beacon.fetch-all-sidecars

If true, all sidecars are fetched and filtered locally. Workaround for buggy Beacon nodes.

<Tabs>
  <Tab title="Syntax">`--l1.beacon.fetch-all-sidecars`</Tab>
  <Tab title="Default">`false`</Tab>
  <Tab title="Environment variable">`$OP_NODE_L1_BEACON_FETCH_ALL_SIDECARS`</Tab>
</Tabs>

### l1.beacon.ignore

When false, halts op-node startup if the healthcheck to the Beacon-node endpoint fails.

<Tabs>
  <Tab title="Syntax">`--l1.beacon.ignore`</Tab>
  <Tab title="Default">`false`</Tab>
  <Tab title="Environment variable">`$OP_NODE_L1_BEACON_IGNORE`</Tab>
</Tabs>

### l1.beacon.slot-duration-override

Duration in seconds of an L1 slot. When set (non-zero), bypasses the beacon /eth/v1/config/spec fetch and uses this value as SECONDS_PER_SLOT. Useful for devnets where the beacon spec endpoint is unavailable (e.g. anvil).

<Tabs>
  <Tab title="Syntax">`--l1.beacon.slot-duration-override=<value>`</Tab>
  <Tab title="Default">`0`</Tab>
  <Tab title="Environment variable">`$OP_NODE_L1_BEACON_SLOT_DURATION_OVERRIDE`</Tab>
</Tabs>

### l1.cache-size

Cache size for blocks, receipts and transactions. If this flag is set to 0, 3/2 of the sequencing window size is used (usually 2400). The default value of 900 (~3h of L1 blocks) is good for (high-throughput) networks that see frequent safe head increments. On (low-throughput) networks with infrequent safe head increments, it is recommended to set this value to 0, or a value that well covers the typical span between safe head increments. Note that higher values will cause significantly increased memory usage.

<Tabs>
  <Tab title="Syntax">`--l1.cache-size=<value>`</Tab>
  <Tab title="Default">`900`</Tab>
  <Tab title="Environment variable">`$OP_NODE_L1_CACHE_SIZE`</Tab>
</Tabs>

### l1.epoch-poll-interval

Poll interval for retrieving new L1 epoch updates such as safe and finalized block changes. Disabled if 0 or negative.

<Tabs>
  <Tab title="Syntax">`--l1.epoch-poll-interval=<value>`</Tab>
  <Tab title="Default">`6m24s`</Tab>
  <Tab title="Environment variable">`$OP_NODE_L1_EPOCH_POLL_INTERVAL`</Tab>
</Tabs>

### l1.http-poll-interval

Polling interval for latest-block subscription when using an HTTP RPC provider. Ignored for other types of RPC endpoints.

<Tabs>
  <Tab title="Syntax">`--l1.http-poll-interval=<value>`</Tab>
  <Tab title="Default">`12s`</Tab>
  <Tab title="Environment variable">`$OP_NODE_L1_HTTP_POLL_INTERVAL`</Tab>
</Tabs>

### l1.max-concurrency

Maximum number of concurrent RPC requests to make to the L1 RPC provider.

<Tabs>
  <Tab title="Syntax">`--l1.max-concurrency=<value>`</Tab>
  <Tab title="Default">`10`</Tab>
  <Tab title="Environment variable">`$OP_NODE_L1_MAX_CONCURRENCY`</Tab>
</Tabs>

### l1.rpc-max-batch-size

Maximum number of RPC requests to bundle, e.g. during L1 blocks receipt fetching. The L1 RPC rate limit counts this as N items, but allows it to burst at once.

<Tabs>
  <Tab title="Syntax">`--l1.rpc-max-batch-size=<value>`</Tab>
  <Tab title="Default">`20`</Tab>
  <Tab title="Environment variable">`$OP_NODE_L1_RPC_MAX_BATCH_SIZE`</Tab>
</Tabs>

### l1.rpc-rate-limit

Optional self-imposed global rate-limit on L1 RPC requests, specified in requests / second. Disabled if set to 0.

<Tabs>
  <Tab title="Syntax">`--l1.rpc-rate-limit=<value>`</Tab>
  <Tab title="Default">`0`</Tab>
  <Tab title="Environment variable">`$OP_NODE_L1_RPC_RATE_LIMIT`</Tab>
</Tabs>

### l1.rpckind

The kind of RPC provider, used to inform optimal transactions receipts fetching, and thus reduce costs. Valid options: alchemy, quicknode, infura, parity, nethermind, debug_geth, erigon, basic, any, standard

<Tabs>
  <Tab title="Syntax">`--l1.rpckind=<value>`</Tab>
  <Tab title="Default">`standard`</Tab>
  <Tab title="Environment variable">`$OP_NODE_L1_RPC_KIND`</Tab>
</Tabs>

### l1.runtime-config-reload-interval

Poll interval for reloading the runtime config, useful when config events are not being picked up. Disabled if 0 or negative.

<Tabs>
  <Tab title="Syntax">`--l1.runtime-config-reload-interval=<value>`</Tab>
  <Tab title="Default">`10m0s`</Tab>
  <Tab title="Environment variable">`$OP_NODE_L1_RUNTIME_CONFIG_RELOAD_INTERVAL`</Tab>
</Tabs>

### l1.trustrpc

Trust the L1 RPC, sync faster at risk of malicious/buggy RPC providing bad or inconsistent L1 data

<Tabs>
  <Tab title="Syntax">`--l1.trustrpc`</Tab>
  <Tab title="Default">`false`</Tab>
  <Tab title="Environment variable">`$OP_NODE_L1_TRUST_RPC`</Tab>
</Tabs>

### l2

Address of L2 Engine JSON-RPC endpoints to use (engine and eth namespace required)

<Tabs>
  <Tab title="Syntax">`--l2=<value>`</Tab>
  <Tab title="Environment variable">`$OP_NODE_L2_ENGINE_RPC`</Tab>
</Tabs>

### l2.engine-rpc-timeout

L2 engine client rpc timeout

<Tabs>
  <Tab title="Syntax">`--l2.engine-rpc-timeout=<value>`</Tab>
  <Tab title="Default">`10s`</Tab>
  <Tab title="Environment variable">`$OP_NODE_L2_ENGINE_RPC_TIMEOUT`</Tab>
</Tabs>

### l2.enginekind

The kind of engine client, used to control the behavior of op-node in respect to different types of engine clients. Valid options: `geth`, `reth`, `erigon`.

<Tip>
  **Set this to `reth` when pairing with op-reth.** `op-reth` is the recommended execution client for new OP Stack deployments; the binary default of `geth` is kept for backward compatibility. Setting the wrong value can cause op-node to mis-handle engine-API responses (e.g. payload-id formatting, sync hints).
</Tip>

<Tabs>
  <Tab title="Syntax">`--l2.enginekind=<value>`</Tab>
  <Tab title="Default">`geth`</Tab>
  <Tab title="Possible Values">`geth, reth, erigon`</Tab>
  <Tab title="Environment variable">`$OP_NODE_L2_ENGINE_KIND`</Tab>
</Tabs>

### l2.follow.source

Address of L2 CL RPC HTTP endpoint to follow source

<Tabs>
  <Tab title="Syntax">`--l2.follow.source=<value>`</Tab>
  <Tab title="Environment variable">`$OP_NODE_L2_FOLLOW_SOURCE`</Tab>
</Tabs>

### l2.jwt-secret

Path to JWT secret key. Keys are 32 bytes, hex encoded in a file. A new key will be generated if the file is empty.

<Tabs>
  <Tab title="Syntax">`--l2.jwt-secret=<value>`</Tab>
  <Tab title="Environment variable">`$OP_NODE_L2_ENGINE_AUTH`</Tab>
</Tabs>

### rollup.config

Rollup chain parameters

<Tabs>
  <Tab title="Syntax">`--rollup.config=<value>`</Tab>
  <Tab title="Environment variable">`$OP_NODE_ROLLUP_CONFIG`</Tab>
</Tabs>

### rollup.l1-chain-config

Path to .json file with the chain configuration for the L1, either in the direct format or genesis.json format (i.e. embedded under the .config property). Not necessary / will be ignored if using Ethereum mainnet or Sepolia as an L1.

<Tabs>
  <Tab title="Syntax">`--rollup.l1-chain-config=<value>`</Tab>
  <Tab title="Environment variable">`$OP_NODE_ROLLUP_L1_CHAIN_CONFIG`</Tab>
</Tabs>

### syncmode

Blockchain sync mode (options: consensus-layer, execution-layer)

<Tabs>
  <Tab title="Syntax">`--syncmode=<value>`</Tab>
  <Tab title="Default">`consensus-layer`</Tab>
  <Tab title="Environment variable">`$OP_NODE_SYNCMODE`</Tab>
</Tabs>

### syncmode.offset-el-safe

After execution-layer sync completes, set safe and finalized heads to this duration behind the synced tip (converted to L2 blocks via rollup block time using ceiling division). Default 0 (safe/finalized stay at the tip). Set to e.g. 168h to force derivation of the most recent 7 days of blocks before they are considered safe.

<Tabs>
  <Tab title="Syntax">`--syncmode.offset-el-safe=<value>`</Tab>
  <Tab title="Default">`0s`</Tab>
  <Tab title="Environment variable">`$OP_NODE_SYNCMODE_OFFSET_EL_SAFE`</Tab>
</Tabs>

### syncmode.req-resp

Toggles the consensus-layer Req/Res P2P sync client.

<Warning>
  **Deprecated.** Default `false` in v1.18.0. The Req/Res CL P2P sync **client** is being removed in favor of execution-layer syncing; only enable temporarily for backward compatibility. The Req/Res **server** path (controlled by `--p2p.sync.req-resp`) remains for now to support older peers but is also planned for removal. See [Deprecation of Req/Res CL P2P sync](/notices/req-resp-cl-sync-deprecation).
</Warning>

<Tabs>
  <Tab title="Syntax">`--syncmode.req-resp`</Tab>
  <Tab title="Default">`false`</Tab>
  <Tab title="Environment variable">`$OP_NODE_SYNCMODE_REQ_RESP`</Tab>
</Tabs>

## Node log levels

Node log levels determine the verbosity of log messages, allowing operators to filter messages based on importance and detail. The log levels for the op-node are:

- **Silent (0)** — No log messages are displayed.
- **Error (1)** — Only error messages are displayed.
- **Warn (2)** — Error messages and warnings.
- **Info (3)** — Default level: errors, warnings, and normal activity logs.
- **Debug (4)** — Info-level plus additional debugging information.
- **Detail (5)** — Most verbose, including low-level system operations.

To set the log level use the `--log.level` flag:

```sh
op-node --log.level=debug
```
