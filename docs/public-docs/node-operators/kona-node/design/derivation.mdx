The derivation system in kona-node is responsible for transforming L1 data into L2 payload attributes that can be executed to produce the canonical L2 blocks. This document covers how the [`kona-derive`][kd] crate is integrated and used within the kona-node architecture.

## Overview

The derivation subsystem in kona-node decides the engine's safe head. Its actors live in `kona_node_actors::derivation`: `derivation::untrusted` runs the trait-abstracted [`kona-derive`][kd] pipeline to derive L2 payload attributes from L1 data, and `derivation::trusted` follows the heads an external derivation delegate reports. The engine drives whichever one the node runs.

### Key Components

- **Untrusted derivation actor**: Runs the derivation pipeline, built with `derivation::untrusted::Builder` and driven through `derivation::untrusted::Handle`
- **Trusted derivation actor**: Follows a derivation delegate, built with `derivation::trusted::Builder` and read through `derivation::trusted::Handle`
- **OnlinePipeline**: A concrete implementation of the derivation pipeline using online providers
- **Signal System**: Handles pipeline resets, hardfork activations, and error conditions

## Architecture

### The Engine Drives Derivation

The engine drives derivation, and derivation never asks anything of the engine. Once the execution layer has synced, the engine resets derivation and repeatedly asks the `engine::Safety` trait's `next` for what to make safe next on top of its safe head:

- `Derived::Attributes`: payload attributes derived from L1 that no unsafe block matches, which the engine builds into the next safe block, as described in [the engine's operations](/node-operators/kona-node/design/engine#driving-safety-and-finality). If the execution layer rejected the block, a deposits-only block replaces it, and the engine calls `flush` so derivation drops the rest of its channel.
- `Derived::Safe`: a block the execution layer has, and the L1 block it was derived from, which the engine makes safe as it is.

After each of its resets, whatever caused it, the engine calls `reset` with its new safe head. It also gives the `engine::Finality` trait each safe head whose source it knows, and finalizes the blocks finality decides. The node's `Safety` and `Finality` adapters, in the service's `adapters` module, put the actors behind the traits: the untrusted handle implements `Safety`, the finality actor's handle implements `Finality`, and the trusted handle implements `Finality` and, through the adapter, which needs no resets or flushes from it, `Safety`.

### Untrusted Derivation

`derivation::untrusted::Builder::new` creates the actor's request queue and published values before any dependencies exist. `Builder::build` takes the derivation pipeline, the L1 actor's handle, and the L2 execution layer, and returns the actor's lifetime future. The actor compares each set of attributes it derives with the unsafe chain: it reads the execution layer's block at their height through the read-only `derivation::untrusted::L2` trait, and checks it against them. A block that matches is what to make safe next, with the L1 block the attributes were derived from; otherwise, or if the block cannot be read, the attributes are, for the engine to build. Only the engine uses the Engine API. The handle drives the actor:

- `derive(safe_head)` publishes the engine's safe head and waits for what the actor derives on top of it. That stays published until a newer safe head replaces it, so cancelling the wait loses nothing.
- `reset(safe)` restarts derivation from the safe head. The actor discards the attributes it derived before, and its pipeline resets onto the safe head before it derives again. The reply comes once the actor has taken the reset; the pipeline resets in the actor's own time, so the engine never waits on L1 for it.
- `flush` flushes the channel of the last block derived.
- `current_l1` returns the pipeline's origin, the L1 block derivation has read up to, which may not be fully derived yet. Observing a newer L1 head does not advance it until derivation reaches it, and resets can move it backwards. It is the default block until derivation starts.

The actor follows L1 through the `derivation::L1` trait, which the L1 actor's handle implements.

### Trusted Derivation

`derivation::trusted::Builder::build` takes the derivation delegate and an L1 provider. The actor polls the delegate every four seconds, checks the L1 blocks its sync status reports against the canonical chain, and publishes the delegate's safe and finalized heads only once they pass. The delegate reports no source for its safe head, so the L1 block it has derived up to stands in for it: that block is at or after the source. The handle's `next_safe` returns the delegate's latest safe head once it differs from the one it last returned, or from the engine's, such as after an engine reset; its `Finality::next` returns the delegate's finalized head once it differs from the one it last returned. Each clone remembers what it returned, so the engine reads safe and finalized heads through separate clones. Its `current_l1` returns the delegate's current L1 block.

The actors coordinate with several other node components:
- **Engine Actor**: Drives derivation and finality, makes safe and final what they decide, resets itself, and publishes its state
- **L1 Actor**: Holds the canonical L1 chain, which both the pipeline and derivation read

### Pipeline Construction

The derivation pipeline is constructed by the `RollupNode` service when it wires up the derivation actor. The node builds caching L1/L2 providers and then creates an `OnlinePipeline`, which traverses L1 by asking its chain provider for the block after its origin:

```rust
OnlinePipeline::new_polled(
    self.chain.rollup_config.clone(),
    self.chain.l1_config.clone(),
    OnlineBlobProvider::init(self.clients.l1_beacon.clone()).await,
    l1_derivation_provider,
    l2_derivation_provider,
    Some(self.chain.dependency_set.clone()),
)
```

### Provider Configuration

The node uses caching providers to optimize performance:

- **L1ChainProvider**: Provides L1 blockchain data. It reads the canonical block at each height from the L1 actor, so the pipeline follows the same chain as every other actor, and reads block contents by hash through an `AlloyChainProvider` with a configurable cache size
- **AlloyL2ChainProvider**: Provides L2 blockchain data and system configuration
- **OnlineBlobProvider**: Retrieves blob data from the beacon chain for post-4844 transactions

The cache size is set to 1024 entries by default:

```rust
const DERIVATION_PROVIDER_CACHE_SIZE: usize = 1024;
```

## Pipeline Operation

### Main Processing Loop

The untrusted actor derives nothing until the engine first resets it. It then repeatedly selects, in this order of priority:

1. **Requests**: A reset discards the attributes derived before it, and makes the pipeline reset onto the reset's safe head before it derives again; it interrupts derivation in progress. A flush signals the pipeline to flush its channel.
2. **A new safe head**: Once the attributes on the safe head are published, the safe head the engine gives next becomes the one derivation derives on.
3. **Derivation**: Otherwise, it resets the pipeline if a reset asked for it, then steps the pipeline on the safe head until it produces attributes, and publishes them. A pipeline reset that fails, other than critically, is retried after an interval until it succeeds; a pipeline that cannot reset onto the safe head, such as one whose L1 origin an L1 reorg replaced, retries too, since the engine resets for such a reorg. When a step fails temporarily and L1 has no block after the pipeline's origin, it waits for L1 to extend the origin and steps again; if L1 reorgs out the origin instead, the pipeline resets onto the safe head. If L1 already has a block after the origin, something else failed, and it steps again after an interval. When the pipeline asks for a reset, it resets onto the safe head. A critical failure stops the actor

A reset interrupts a pipeline step in progress. The pipeline reset that follows rebuilds every stage from the safe head's L1 origin, so the interrupted step leaves nothing behind. Nothing else interrupts a step: the engine flushes and gives the next safe head only after adopting the published attributes. A block L1 adds while deriving is found once the pipeline next fails to advance, so it resumes derivation.

When L1 reorgs out blocks the engine's heads rest on, the engine finds it while checking L1 and resets, which resets derivation. A reorg that leaves the engine's heads alone only resets the pipeline.

### Finality

The finality actor in `kona_node_actors::finality`, not derivation, decides which derived blocks to finalize. The engine drives it through its handle, which implements `engine::Finality`: the handle's `next` gives the actor the engine's safe head with the L1 block it was derived from, and waits for a block to finalize other than the one it last returned. The engine gives it a safe head only once it knows its source, so not between a reset and the next block it makes safe. The actor records the highest safe head derived from each L1 block, follows the L1 actor's finalized block, and decides the highest recorded safe head whose source that block covers. The engine's safe head only moves forward except when it resets, so a safe head at or below one recorded follows a reset, which an L1 reorg may have caused: the actor forgets the safe heads from its height up. Those below are its ancestors, older than any reorg the reset walked back from. Safe heads given faster than the actor reads them coalesce, so it may miss some; it then finalizes the highest one it saw. The engine finalizes a decided block only if it is past its finalized head and not past its safe head. Trusted derivation runs no finality actor: its handle reports the delegate's finalized heads.

### Stepping Logic

The core derivation logic is implemented in the untrusted actor's `Deriver::step()`, which owns the pipeline, the safe head it derives on, and the L1 chain it waits on:

```rust
async fn step(&mut self) -> Result<Stepped, ActorError>
```

This method continuously steps the pipeline until payload attributes are produced or the pipeline needs a reset, waiting after each temporary failure until stepping again may succeed:

1. **Step the pipeline** with the safe head the engine last gave, or reset onto
2. **Handle step results**:
   - `PreparedAttributes`: Attributes are ready to be consumed
   - `AdvancedOrigin`: Pipeline advanced to next L1 block
   - `OriginAdvanceErr`/`StepFailed`: Handle various error conditions
3. **Return attributes** when available

### Error Handling

The untrusted derivation actor handles three categories of pipeline errors:

#### Temporary Errors
- `PipelineError::NotEnoughData`: Continue stepping, more data may become available
- Any other temporary error: If L1 has no block after the pipeline's origin, the pipeline has derived from all of L1: wait until L1 has a canonical child of the origin, or reset the pipeline onto the safe head if L1 reorged out the origin, incrementing the `L1_REORG_COUNT` metric. Otherwise step again after an interval

#### Reset Errors  
- `ResetError::HoloceneActivation`: Send an `ActivationSignal` to the pipeline and keep stepping
- Any other reset error, including `ResetError::ReorgDetected`: Reset the pipeline onto the safe head. `ReorgDetected` additionally increments the `L1_REORG_COUNT` metric.

#### Critical Errors
- Unrecoverable errors that terminate the derivation process
- Increment metrics counter and propagate error up

### Signal Handling

The pipeline supports several signal types for coordination:

- **ResetSignal**: Resets pipeline state with new L1 origin and system config
- **ActivationSignal**: Handles hardfork activations (e.g., Holocene)
- **FlushChannel**: Invalidates current channel data for deposit-only blocks

Derivation sends these signals to its own pipeline, in response to the engine's resets and flushes, and to the pipeline's own errors.

## Configuration

### Rollup Configuration

The derivation pipeline requires a [`RollupConfig`][rc] that defines:
- Chain parameters (chain ID, block time, etc.)
- Hardfork activation heights
- System configuration addresses
- Batch and channel parameters

### Runtime Configuration

Runtime configuration includes:
- Provider cache sizes
- Polling intervals for L1 data
- Metrics collection settings

## Integration Patterns

### With Engine Actor

The engine asks derivation what to make safe next on top of its safe head, through the `engine::Safety` trait:

```rust
let derived = safety.next(state.safe_head()).await?;
```

The engine builds the attributes the untrusted actor derives into its next safe block, or makes safe the unsafe block that matched them, and asks again on top of the new safe head. It makes the safe heads the trusted actor reports safe as they are.

### With the L1 Actor

The L1 actor holds the canonical L1 chain from the latest finalized block to the head, and its handle answers questions about it. The pipeline's `L1ChainProvider` asks the handle for the canonical block at each height, and finds no block after the actor's head, which fails the step temporarily. Derivation then asks the handle for the canonical child of the pipeline's origin, which waits until L1 has one, or reports that L1 reorged out the origin. `L1ChainProvider` does not report a missing block as `PipelineError::Eof`, which a pipeline reset takes for success: a reset onto an origin after the actor's head fails temporarily and is retried. Blocks before the finalized block cannot reorg, so the handle reads them from L1, and a pipeline far behind the head reads L1 the same way. The finality actor asks the handle for each new finalized block.

### With RPC Layer

The rollup RPC reads `current_l1` for `optimism_syncStatus` through the `kona_rpc::Derivation` trait, which the node's `Safety` adapter implements for both actors.

## Metrics and Observability

The untrusted derivation actor exposes several metrics for monitoring:

- `DERIVATION_L1_ORIGIN`: Current L1 origin block number
- `DERIVATION_CRITICAL_ERROR`: Count of critical derivation errors  
- `L1_REORG_COUNT`: Count of detected L1 reorganizations

These metrics help operators monitor the health and progress of the derivation process.
