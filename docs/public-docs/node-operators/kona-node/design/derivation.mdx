The derivation system in kona-node is responsible for transforming L1 data into L2 payload attributes that can be executed to produce the canonical L2 blocks. This document covers how the [`kona-derive`][kd] crate is integrated and used within the kona-node architecture.

## Overview

The derivation subsystem in kona-node is built around the derivation actor in `kona_node_actors::derivation`, which manages the derivation pipeline lifecycle and coordinates with other node components. The actor uses the trait-abstracted [`kona-derive`][kd] pipeline to continuously process L1 data and produce L2 payload attributes.

### Key Components

- **Derivation actor**: The main actor responsible for running the derivation pipeline, built with `derivation::Builder` and reached through `derivation::Handle`
- **OnlinePipeline**: A concrete implementation of the derivation pipeline using online providers
- **Signal System**: Handles pipeline resets, hardfork activations, and error conditions

## Architecture

### Builder, Handle, and Actor

`derivation::Builder::new` creates the actor's `DerivationStatus` publisher before any dependencies exist, so the node can hand the status to the RPC layer before building either actor. The builder then builds one of two actors, each returning its lifetime future:

- `Builder::build` takes the engine, the derivation pipeline, and the L1 head receiver, and derives payload attributes from L1.
- `Builder::build_delegated` takes the engine, the derivation delegate, and an L1 provider, and follows the delegate's safe head instead. It also starts by resetting the engine once the execution layer is synced.

Derivation drives the engine; the engine only replies to requests and publishes its state and resets. Derivation starts by asking the engine to reset once the execution layer is synced, retrying while the engine reports it is still syncing. It then consolidates each set of derived attributes and waits for the reply, which carries the engine state and whether to flush the channel of a block the engine replaced. The engine publishes each reset, whichever actor asked for it, before replying to the request that caused it; derivation resets its pipeline onto the safe head of every reset it sees, including one that left the safe head where it was. Derivation reaches the engine only through the `derivation::Engine` trait, whose `next_reset` waits for the engine's next reset. `Handle::status` subscribes to the published `DerivationStatus`. L1 head updates arrive directly through a watch receiver.

The actor publishes `DerivationStatus` through a watch channel after pipeline steps and signals. Its `current_l1` is the pipeline's current origin, so observing a newer L1 head does not advance this field until derivation processes it. Resets can move the published origin backwards. In delegated mode, the actor publishes the delegate's current L1 block only after validating the reported L1 information against the canonical chain.

The actor coordinates with several other node components:
- **Engine Actor**: Consolidates payload attributes and replies with the outcome, resets on request, and publishes its state
- **L1 Actors**: Publish head block observations through a watch channel

### Pipeline Construction

The derivation pipeline is constructed by the `RollupNode` service when it wires up the derivation actor. The node builds caching L1/L2 providers and then creates an `OnlinePipeline`, which traverses L1 by polling its chain provider for the next block:

```rust
OnlinePipeline::new_polled(
    self.config.clone(),
    self.l1_config.chain_config.clone(),
    OnlineBlobProvider::init(self.l1_config.beacon_client.clone()).await,
    l1_derivation_provider,
    l2_derivation_provider,
    self.dependency_set.clone(),
)
```

### Provider Configuration

The node uses caching providers to optimize performance:

- **AlloyChainProvider**: Provides L1 blockchain data with configurable cache size
- **AlloyL2ChainProvider**: Provides L2 blockchain data and system configuration
- **OnlineBlobProvider**: Retrieves blob data from the beacon chain for post-4844 transactions

The cache size is set to 1024 entries by default:

```rust
const DERIVATION_PROVIDER_CACHE_SIZE: usize = 1024;
```

## Pipeline Operation

### Main Processing Loop

The derivation actor resets the engine, then repeatedly selects, in this order of priority:

1. **Engine reset**: When the engine resets, by any actor's request, derivation resets the pipeline onto the engine's safe head. A pipeline reset that fails temporarily is retried, onto the safe head of the latest engine reset, until it succeeds. A pipeline that cannot reset onto the safe head, such as one whose ancestors an L1 reorg replaced, asks the engine to reset. A critical failure stops the actor
2. **Derivation**: Otherwise, it steps the pipeline on the safe head until it produces attributes, and consolidates the engine's safe head with them. When the pipeline runs out of data, it waits for an L1 head update and steps again. When the pipeline asks for a reset, derivation asks the engine to reset, and the engine's reset then resets the pipeline

An engine reset interrupts a pipeline step in progress. The pipeline reset that follows rebuilds every stage from the safe head's L1 origin, so the interrupted step leaves nothing behind. Nothing else interrupts a step. An L1 head update that arrives while deriving is read once the pipeline runs out of data, so it resumes derivation.

### Finality

The finality actor in `kona_node_actors::finality`, not derivation, finalizes derived blocks. It follows the engine's published state, which records the L1 block each safe head was derived from, and the finalized L1 block receiver. When an L1 block finalizes, it asks the engine to finalize the highest safe head it recorded whose source that L1 block covers. The published state coalesces, so the actor may miss some safe heads; it then finalizes the highest one it saw, and catches up when the next L1 block finalizes. Each reset the engine publishes drops the safe heads recorded before it, whose sources an L1 reorg may have replaced. Delegated derivation runs no finality actor: it finalizes the delegate's finalized blocks itself.

### Stepping Logic

The core derivation logic is implemented in `Deriver::next()`, which owns the pipeline, the safe head it derives on, and the L1 head receiver:

```rust
async fn next(&mut self) -> Result<Derived, ActorError>
```

This method continuously steps the pipeline until payload attributes are produced or the pipeline needs a reset, waiting for the next L1 head whenever the pipeline runs out of data:

1. **Step the pipeline** with the engine's safe head from the latest consolidation or reset
2. **Handle step results**:
   - `PreparedAttributes`: Attributes are ready to be consumed
   - `AdvancedOrigin`: Pipeline advanced to next L1 block
   - `OriginAdvanceErr`/`StepFailed`: Handle various error conditions
3. **Return attributes** when available

### Error Handling

The derivation actor handles three categories of pipeline errors:

#### Temporary Errors
- `PipelineError::NotEnoughData`: Continue stepping, more data may become available
- `PipelineError::Eof`: Stop deriving until more L1 data arrives

#### Reset Errors  
- `ResetError::HoloceneActivation`: Send an `ActivationSignal` to the pipeline and keep stepping
- Any other reset error, including `ResetError::ReorgDetected`: Ask the engine to reset; the engine's published reset then resets the pipeline. `ReorgDetected` additionally increments the `L1_REORG_COUNT` metric.

#### Critical Errors
- Unrecoverable errors that terminate the derivation process
- Increment metrics counter and propagate error up

### Signal Handling

The pipeline supports several signal types for coordination:

- **ResetSignal**: Resets pipeline state with new L1 origin and system config
- **ActivationSignal**: Handles hardfork activations (e.g., Holocene)
- **FlushChannel**: Invalidates current channel data for deposit-only blocks

Derivation sends these signals to its own pipeline, in response to the engine's replies and published resets.

## Configuration

### Rollup Configuration

The derivation pipeline requires a [`RollupConfig`][rc] that defines:
- Chain parameters (chain ID, block time, etc.)
- Hardfork activation heights
- System configuration addresses
- Batch and channel parameters

### Runtime Configuration

Runtime configuration includes:
- Provider cache sizes
- Polling intervals for L1 data
- Metrics collection settings

## Integration Patterns

### With Engine Actor

The derivation actor produces `OpAttributesWithParent` and consolidates the engine's safe head with them through the `derivation::Engine` interface:

```rust
let Consolidation { state, flush } = self.engine.consolidate(attributes).await?;
```

The engine actor executes these attributes, updates the L2 safe head, and replies with its state, which lets derivation derive the next attributes, or reset if the engine reset. When derivation is delegated, the delegated derivation actor sends the delegate's safe head with `follow_safe_head` instead.

### With the L1 Actors

The derivation actor subscribes directly to the head L1 block receiver published by the L1 polling actors. Head changes indicate when new L1 data is available for processing. The receiver retains the latest observation while derivation is busy, including reorgs. Initial snapshots do not trigger processing. The finality actor subscribes to the finalized L1 block receiver the same way.

### With RPC Layer

The RPC layer can query derivation status and potentially trigger pipeline operations through the standard node RPC interface.

## Metrics and Observability

The derivation actor exposes several metrics for monitoring:

- `DERIVATION_L1_ORIGIN`: Current L1 origin block number
- `DERIVATION_CRITICAL_ERROR`: Count of critical derivation errors  
- `L1_REORG_COUNT`: Count of detected L1 reorganizations

These metrics help operators monitor the health and progress of the derivation process.
