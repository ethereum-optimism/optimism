The `kona-engine` crate provides a modular execution engine implementation for the OP Stack rollup node. It serves as the bridge between the rollup protocol and the execution layer (EL), managing Engine API interactions through operations performed one at a time.

## Architecture Overview

The execution engine is built around several key components:

- **Engine Operations**: Engine API operations performed one at a time against the engine state
- **Error Severities**: Each operation's errors say how the caller should recover
- **Engine Client**: HTTP client for communicating with the execution layer
- **Actor Integration**: Service layer integration through the engine actor

## Error Severity

### EngineTaskError

The `EngineTaskError` trait provides sophisticated error handling with severity levels:

```rust
pub trait EngineTaskError {
    fn severity(&self) -> EngineTaskErrorSeverity;
}

pub enum EngineTaskErrorSeverity {
    Temporary,  // Retry the task
    Critical,   // Propagate to engine actor
    Reset,      // Request derivation reset
    Flush,      // Request derivation flush
}
```

This allows operations to signal different recovery strategies based on the error type.

## Operations

The `Engine` performs one operation at a time, giving it exclusive access to the `EngineState`, and publishes the state after every operation, whether or not it succeeds. A failed operation returns its error, and the caller decides whether to retry it; the engine actor retries temporary errors as described under [Communication Channels](#communication-channels). Operations run in the order the caller performs them; there is no priority ordering. They use the concrete `EngineClient`, whose Alloy providers share their RPC connections. Tests supply mock transports to the same client.

Each operation updates the execution layer's forkchoice state with `engine_forkchoiceUpdated` as part of its work, and tracks whether the execution layer has finished syncing.

- **`insert_unsafe`** inserts an unsafe payload, received from gossip or the admin API, with `engine_newPayload`, then makes it the unsafe head. A payload the execution layer reports as `INVALID` or `ACCEPTED` is dropped.
- **`build`** starts building a block from payload attributes in sequencer mode, and returns the payload ID. Its failures are returned to the caller instead of being retried by the engine; the sequencer retries a failed build on its next block-time tick.
- **`seal`** retrieves a started block with the version-specific `engine_getPayload` call, inserts it, and makes it the unsafe head. It fails if the unsafe head moved since the build started.
- **`consolidate`** advances the safe chain through derivation. If the unsafe block at that height matches the derived attributes, it becomes safe; otherwise the engine builds and seals the attributes, reorging the unsafe chain. With derivation delegated, the engine follows the delegated safe block instead.
- **`finalize`** finalizes an L2 block identified by number or hash.
- **`reset`** finds a plausible sync starting point and reorgs the execution layer to it.

After Holocene, a sealed payload that the execution layer does not accept as valid is replaced by a deposits-only block built from the same attributes, unless the attributes were already deposits-only, and the error asks the caller to flush derivation.

## Engine State Management

The `EngineState` tracks the current state of the execution engine:

```rust
pub struct EngineState {
    /// The sync state of the engine.
    pub sync_state: EngineSyncState,
    /// Whether or not the EL has finished syncing.
    pub el_sync_finished: bool,
    /// Tracks when the rollup node changes the forkchoice to restore a
    /// previously known unsafe chain (e.g. an unsafe reorg caused by an
    /// invalid span batch).
    pub need_fcu_call_backup_unsafe_reorg: bool,
}
```

The unsafe, safe, and finalized heads live in the nested `EngineSyncState`. State updates are communicated through watch channels, enabling reactive programming patterns across the system.

## Integration with kona-node

The `kona-node` service layer integrates the engine through the engine actor in `kona_node_actors::engine`.

### Builder, Handle, and Actor

`engine::Builder::new` creates the actor's bounded request queue and engine state publisher before any dependencies exist, so the node can give `engine::Handle` clones to derivation, the network, the sequencer, and the admin RPC before building the actor. `Builder::build` takes the Engine API client, rollup configuration, derivation client, and imported block sink, and returns the actor's lifetime future. The node supervisor spawns that future; dropping it stops the actor.

### Communication Channels

The engine actor receives all state-mutating input through its handle: payload attributes from derivation, unsafe blocks from gossip and the admin API, reset requests, finalization requests, and block building requests (sequencer mode only). Reset, build, and seal requests wait for the actor's reply; the others return once the request is queued. The actor executes one request at a time, in the order requests arrive, with one handler per request. Builds and seals reply to their caller, which decides whether to retry them. For the other operations, the actor retries a temporary failure in place with backoff, starting at 100 ms and doubling up to 5 s, while later requests wait in the handle's bounded queue. An operation still failing after 60 seconds is abandoned and the engine is reset, so derivation restarts from the execution layer's heads; a reset is retried until it succeeds. A flush completes its operation, because the deposits-only replacement block has already been imported. `Handle::state` subscribes to the engine state the actor publishes after each operation. The node service adapts the handle to the narrow engine-client traits that derivation, the network, and the sequencer depend on. The `RollupRpc` module serves read-only RPC requests directly. It shares the engine's connection through a cloned `EngineClient`, constrained by the `OutputProvider` trait to query only `output_at_block`, and reads engine state through that subscription.

### Rollup RPC Reads

`RollupRpc` clones the rollup configuration for `optimism_rollupConfig`, combines published engine, L1 block, and derivation snapshots for `optimism_syncStatus`, and calls `OutputProvider::output_at_block` with its rollup configuration for `optimism_outputAtBlock`. The L1 polling actors publish observed head, safe, and finalized blocks through separate watch channels; derivation publishes its current L1 origin. Sync-status reads do not queue actor requests or make L1 RPC calls. The legacy `current_l1_finalized` field uses the finalized L1 receiver's block. Any Alloy `Provider<Optimism>`, including `EngineClient`, implements the output trait without dynamic dispatch or boxed futures. The RPC module computes the output using the configured genesis and fork rules. These reads run in jsonrpsee request handlers, so a slow output-root query does not block other state reads.

## Usage Patterns

### Basic Engine Setup

```rust
// Create the concrete engine client through `EngineClientBuilder`.
let client = EngineClientBuilder {
    l2: l2_engine_url,
    l2_jwt: jwt_secret,
    l1_rpc: l1_rpc_url,
    cfg: rollup_config,
}
.build();

// Initialize engine state
let state = EngineState::default();
let (state_sender, state_receiver) = watch::channel(state);

// Create the engine, which publishes its state to `state_receiver`.
let mut engine = Engine::new(
    Arc::new(client),
    rollup_config.clone(),
    block_sink,
    state,
    state_sender,
);
```

### Performing Operations

`Engine` has one method per operation: `insert_unsafe`, `build`, `seal`, `consolidate`, `finalize`, and `reset`. Each returns its own error type, whose severity tells the caller how to recover.

```rust
match engine.consolidate(input).await {
    Ok(()) => info!("Consolidated"),
    Err(e) => match e.severity() {
        EngineTaskErrorSeverity::Temporary => {
            // Retry after a delay
        },
        EngineTaskErrorSeverity::Reset => {
            // Reset the engine and derivation
        },
        EngineTaskErrorSeverity::Flush => {
            // Flush derivation; the operation is complete
        },
        EngineTaskErrorSeverity::Critical => {
            // Stop
        },
    }
}
```

## Error Handling and Recovery

The engine provides robust error handling through:

### Severity-Based Recovery

- **Temporary errors**: Retried by the engine actor
- **Critical errors**: Propagated to the actor
- **Reset errors**: Trigger derivation pipeline reset
- **Flush errors**: Trigger derivation pipeline flush

A verdict from the execution layer is not a temporary error, because retrying returns the same verdict. An unsafe payload that `engine_newPayload` reports as `INVALID` or `ACCEPTED` is dropped. A forkchoice update reported as `INVALID` or `ACCEPTED` is a reset error: the engine actor resets the engine for the operations it retries itself, while `build` and `seal` return the error to their caller.

### State Consistency

Operations run atomically on the `EngineState`, ensuring consistency even during error conditions.

## Version Support

The engine automatically selects appropriate Engine API versions based on hardfork activation:

- **Pre-Ecotone (Bedrock, Canyon, Delta)**: Uses `engine_newPayloadV2` and `engine_getPayloadV2`
- **Post-Ecotone**: Uses `engine_newPayloadV3` and `engine_getPayloadV3`
- **Post-Isthmus**: Uses `engine_newPayloadV4` and `engine_getPayloadV4`
- **Post-Karst (Osaka)**: Uses `engine_getPayloadV5` (`engine_newPayload` and `engine_forkchoiceUpdated` stay at their V4/V3 versions)

## Metrics and Observability

The engine always includes metrics instrumentation for:

- Task execution success and failure counts
- Error rates by task type
- Engine state transitions
- API call latencies

## Extensibility

Each operation's error type implements `EngineTaskError`, so callers can decide how to recover from any operation's failure by its severity. Tests run the operations against mock RPC transports through the same `EngineClient`.
