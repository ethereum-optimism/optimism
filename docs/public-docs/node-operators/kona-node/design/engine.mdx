The engine actor in `kona-node-service` owns execution mutations and resets. The
`kona-engine` crate supplies the Engine API client, state, ordinary execution operations,
and canonical reset traversal. The independent `kona-node` binary connects to an external
execution client such as op-reth through the Engine API.

## Execution ownership

Producers use a concrete `EngineHandle`. Its messages and reply channels stay private to
the service. Sequencing starts a build, retrieves its payload, then canonicalizes it.
Derivation submits attributes and waits for the actual accepted result. Gossip uses
bounded best-effort admission; reliable payload admission waits for capacity.

The owner serializes mutations and publishes one atomic `EngineState` snapshot before
acknowledging an attempt. The snapshot includes unsafe, local-safe, safe and finalized
heads, the pending-safe parent of an incomplete span, a reset epoch, and the current phase: initializing, syncing, resetting or ready.
The historical `el_sync_finished` flag records that a valid Engine API response has been
seen; it does not by itself mean that a reset has finished.

A reset increments the epoch even when it returns the same heads. Work prepared against
an old epoch or parent is rejected before it can change execution. Opaque build tokens
carry that context through retrieval and canonicalization.

## Scheduling and recovery

Acknowledged commands use a bounded mailbox. Unsafe payloads have a separate bounded
FIFO and one retained active attempt. Reset control has its own bounded lane, so an
unsafe backlog cannot prevent reset admission. Commands and eligible unsafe attempts
alternate, and commands continue during unsafe retry backoff.

The actor completes an in-flight Engine API call before processing reset control. It
reconciles uncertain forkchoice responses through reset before the next mutation. A
failed idempotent `newPayload` call can instead retry the same payload. Temporary reset
dependencies retain the reset and its bounded waiters; an invariant failure stops the node.

## Derivation outcomes

Consolidation reports `Applied`, `Replaced` or `Dropped`. Before Holocene, an incomplete
span advances only pending-safe; a rejected later element rewinds it to completed safe.
Finalization never consumes a pending prefix. Holocene selection uses the L1
inclusion source's timestamp. A rejected pre-Holocene batch is dropped; a rejected
Holocene batch is replaced once with deposits only. A successful replacement advances the
actual safe state and instructs derivation to flush its channel before continuing. A
rejected deposits-only block is fatal. `ACCEPTED` and `SYNCING` are temporary responses
for derived imports and do not trigger replacement.

Finalization carries a recorded L2 hash and, for local derivation, its L1 inclusion source.
The owner checks the epoch, applied safe bound, canonical L2 hash and canonical L1 source
before moving finalized forkchoice. Trusted delegation uses an explicit delegated mode.

## Queries and observability

The read-only `EngineRpcActor` shares the accepted state and pending-work watches with the
owner. It serves configuration, status, output and subscription queries through the
existing RPC interface. Pending work includes accepted mailbox entries and active attempts,
including while an execution RPC is stalled.

Existing engine operation metrics retain their wire names and labels. Block-label gauges
reflect published accepted state, including partial changes made before a later error.
Engine API versions follow the configured rollup hardfork schedule.
