The engine actor in `kona_node_actors::engine` is the OP Stack rollup node's execution engine. It serves as the bridge between the rollup protocol and the execution layer (EL), managing Engine API interactions through operations performed one at a time. It talks to the execution layer through the Engine API client in the `kona-sources` crate, which selects each method's version.

## Architecture Overview

The execution engine is built around several key components:

- **Engine Operations**: Engine API operations the engine actor performs one at a time against the engine state
- **Error Severities**: Each operation's errors say how to recover
- **Engine API Client**: `EngineApi`, the HTTP client for the execution layer's Engine API, from `kona-sources`
- **Actor Integration**: Service layer integration through the engine actor's handle

## Error Severity

### EngineTaskError

The `EngineTaskError` trait provides sophisticated error handling with severity levels:

```rust
pub trait EngineTaskError {
    fn severity(&self) -> EngineTaskErrorSeverity;
}

pub enum EngineTaskErrorSeverity {
    Temporary,  // Retry the task
    Critical,   // Propagate to engine actor
    Reset,      // Reset the engine
    Flush,      // Replace the block with a deposits-only block
}
```

This allows operations to signal different recovery strategies based on the error type. The trait and the error types live in `kona_node_actors::engine`.

## Operations

The engine actor performs one operation at a time, giving it exclusive access to the `EngineState`, and publishes the state after every request, whether or not it succeeds. It also publishes before replying to a seal, consolidation, or reset, so the caller reads the new heads. The engine never sends another actor anything on its own: it only replies to requests and publishes its state and resets. A request whose operation is retried publishes after its last attempt, not between attempts. Builds and seals return their failures to the caller, which decides whether to retry them; the actor retries the other operations' temporary errors as described under [Communication Channels](#communication-channels). Operations run in the order their requests arrive; there is no priority ordering among requests. They use the concrete `EngineApi`, which talks only to the Engine API; a reset, and following L1, also ask the L1 actor's handle whether L1 blocks are canonical. Tests supply a mock transport to the same client, and a test L1 chain to the handle.

Each operation updates the execution layer's forkchoice state with `engine_forkchoiceUpdated` as part of its work, and tracks whether the execution layer has finished syncing.

- **`insert_unsafe_block`** inserts an unsafe payload, received from gossip or the admin API, with `engine_newPayload`, then makes it the unsafe head. A payload the execution layer reports as `INVALID` or `ACCEPTED` is dropped.
- **`start_build`** starts building a block from payload attributes for the sequencer, and returns the payload ID. Its failures are returned to the caller instead of being retried by the actor; the sequencer retries a failed build on its next block-time tick.
- **`seal`** retrieves a started block with the version-specific `engine_getPayload` call, inserts it, and makes it the unsafe head. It fails if the unsafe head moved since the build started.
- **`consolidate`** advances the safe chain with attributes derived from L1. If the unsafe block at that height matches the derived attributes, it becomes safe; otherwise the actor builds and seals the attributes, reorging the unsafe chain. Attributes that do not extend the safe head are skipped.
- **`follow_safe_head`** follows a safe head supplied by the derivation delegate when derivation is delegated. If the unsafe block at that height matches it, that block becomes safe; otherwise it becomes the unsafe and safe head.
- **`finalize`** finalizes an L2 block identified by number or hash. A request for a block above the safe head, which a reset can leave behind, is dropped.
- **`reset`** finds a plausible sync starting point: it walks the unsafe head back until its L1 origin is the canonical L1 block at that height, or is after the L1 actor's head, where it may yet be. An origin L1 reorged out does not count, though L1 may still serve it by hash. The reset reorgs the execution layer to it, publishes the reset, and replies with the engine state.

The engine resets itself once the execution layer has synced, and derivation starts from that first reset. Until then, it asks the execution layer every second whether it synced, by sending the current forkchoice again, and takes an answer of VALID to mean it has; a forkchoice the execution layer rejects counts too, because the reset replaces it. Before the engine has sent any forkchoice, there is none to send again, and it waits: a reset never points a syncing execution layer back at its own stale heads. Gossip, or the sequencer's first block, sends the first forkchoice.

After Holocene, a sealed payload that the execution layer does not accept as valid is replaced by a deposits-only block built from the same attributes, unless the attributes were already deposits-only, and the consolidation's reply tells derivation to flush its channel.

### Following L1

From its first reset, the engine follows L1 reorgs itself. It checks the L1 blocks its heads rest on against the L1 head: the unsafe head's L1 origin, and the L1 block the safe head was derived from, or the safe head's L1 origin where that is unknown. It checks them whenever the L1 actor's head changes, and at once whenever its heads come to rest on other L1 blocks, such as a safe head derived from data read before an L1 reorg. If L1 has another block at the height of either, the engine resets. An L1 origin after the L1 head cannot be checked yet, and a later L1 head checks it; a block before the finalized L1 block cannot reorg any more, and is not checked again. Before its first reset, the engine's heads are the execution layer's own, unchecked, and the first reset checks them against L1. The engine checks L1 before further requests; a request that arrives while a check waits on L1 runs first, and the check is done again after it.

## Engine State Management

The `EngineState` in `kona_node_actors::engine` tracks the engine's view of the L2 chain:

```rust
pub struct EngineState {
    unsafe_head: L2BlockInfo,
    local_safe_head: L2BlockInfo,
    safe_head: L2BlockInfo,
    finalized_head: L2BlockInfo,
    safe_head_source: Option<BlockInfo>,
}
```

The heads are read through accessors such as `EngineState::safe_head`, and change only through `EngineState::apply_update`, which also records each head's block number in the `kona_node_block_labels` gauge. `EngineState::safe_head_source` is the L1 block the safe head was derived from, which a consolidation records and the finality actor reads; it is forgotten when the safe head changes otherwise, and on a reset. The engine actor publishes the state through a watch channel, which `Handle::state` subscribes to. It also publishes the state after each reset through a second watch channel, after publishing the state itself and before replying to the request that caused the reset, so a reader that sees the reset finds no older state left to read; `Handle::resets` subscribes to the resets from then on.

## Integration with kona-node

The `kona-node` service layer integrates the engine through the engine actor in `kona_node_actors::engine`.

### Builder, Handle, and Actor

`engine::Builder::new` creates the actor's bounded request queue and engine state publisher before any dependencies exist, so the node can give `engine::Handle` clones to derivation, the network, the sequencer, and the admin RPC before building the actor. It takes the state the engine starts from: the execution layer's latest, safe and finalized blocks, which `engine::execution_layer_state` reads when the node starts. Handles read those heads from the start, so the node never reports empty heads, until the engine's first reset checks them against L1 and replaces them. The engine sends no forkchoice for them: until it sends one, it takes the execution layer to be syncing, and it resets itself once the execution layer has synced. `Builder::build` takes the Engine API client, rollup configuration, and imported block sink, and returns the actor's lifetime future. The node supervisor spawns that future; dropping it stops the actor.

### Communication Channels

The engine actor receives all state-mutating input through its handle: payload attributes from derivation, unsafe blocks from gossip and the admin API, reset requests, finalization requests, and block building requests (from the sequencer only). Reset, consolidation, build, and seal requests wait for the actor's reply; the others return once the request is queued. A consolidation replies with the resulting engine state, and whether a deposits-only block replaced the derived one, so derivation must flush its channel. Attributes whose parent is not the safe head were derived before a reset; the engine skips them and replies with its state. The actor executes one request at a time, in the order requests arrive, with one handler per request. Builds and seals reply to their caller, which decides whether to retry them. For the other operations, the actor retries a temporary failure in place with backoff, starting at 100 ms and doubling up to 5 s, while later requests wait for room in the handle's queue, which holds one request; the network drops the unsafe blocks it receives over gossip while the queue is full. An operation still failing after 60 seconds is abandoned and the engine is reset; a reset is retried until it succeeds. Derivation and finality follow the published resets, which include a reset that leaves the safe head where it was. A flush completes its operation, because the deposits-only replacement block has already been imported. `Handle::state` subscribes to the engine state the actor publishes after each request. The node service adapts the handle to the narrow engine-client traits that derivation, finality, the network, and the sequencer depend on. The `RollupRpc` module serves read-only RPC requests directly. It reads L2 through the node's L2 provider, constrained by the `OutputProvider` trait to query only `output_at_block`, and reads engine state through that subscription.

### Rollup RPC Reads

`RollupRpc` clones the rollup configuration for `optimism_rollupConfig`, combines published engine, L1 block, and derivation snapshots for `optimism_syncStatus`, and calls `OutputProvider::output_at_block` with its rollup configuration for `optimism_outputAtBlock`. The L1 actor's handle reports the head, safe, and finalized L1 blocks from one view of L1; derivation publishes its current L1 origin. Sync-status reads do not queue actor requests or make L1 RPC calls. The legacy `current_l1_finalized` field uses the finalized L1 block. Any Alloy `Provider<Optimism>` implements the output trait without dynamic dispatch or boxed futures. The RPC module computes the output using the configured genesis and fork rules. These reads run in jsonrpsee request handlers, so a slow output-root query does not block other state reads.

## Usage Patterns

### Basic Engine Setup

```rust
// Create the Engine API client from an authenticated Engine API provider.
let client =
    EngineApi::new(kona_sources::l2_provider(l2_engine_url, jwt_secret), rollup_config.clone());

// Start from the execution layer's heads, then create the request queue and state publisher,
// and hand out handles.
let state = engine::execution_layer_state(&rollup_config, &client).await?;
let builder = engine::Builder::new(state);
let handle = builder.handle();

// Supply the dependencies and spawn the actor's lifetime future. The engine asks the L1 actor,
// through `l1`, whether L1 blocks are canonical, to find a plausible sync starting point on a
// reset and to follow L1 reorgs.
let actor = builder.build(Arc::new(client), l1, rollup_config, block_sink);
tokio::spawn(actor);
```

### Performing Operations

`engine::Handle` has one method per operation: `insert_unsafe_block`, `start_build`, `seal`, `consolidate`, `follow_safe_head`, `finalize`, and `reset`. Builds, seals, consolidations, and resets reply with the operation's result; the sequencer classifies a failed build by its error.

```rust
let payload_id = handle.start_build(attributes.clone()).await?;
let payload = handle.seal(payload_id, attributes).await?;
```

## Error Handling and Recovery

The engine provides robust error handling through:

### Severity-Based Recovery

- **Temporary errors**: Retried by the engine actor
- **Critical errors**: Stop the engine actor
- **Reset errors**: Reset the engine, which derivation and finality follow through the published resets
- **Flush errors**: Replace the rejected block with a deposits-only block, and tell derivation to flush its channel

A verdict from the execution layer is not a temporary error, because retrying returns the same verdict. An unsafe payload that `engine_newPayload` reports as `INVALID` or `ACCEPTED` is dropped. A forkchoice update reported as `INVALID` or `ACCEPTED` is a reset error: the engine actor resets the engine for the operations it retries itself, while builds and seals return the error to their caller.

### State Consistency

Operations run atomically on the `EngineState`, ensuring consistency even during error conditions.

## Version Support

The engine automatically selects appropriate Engine API versions based on hardfork activation:

- **Pre-Ecotone (Bedrock, Canyon, Delta)**: Uses `engine_newPayloadV2` and `engine_getPayloadV2`
- **Post-Ecotone**: Uses `engine_newPayloadV3` and `engine_getPayloadV3`
- **Post-Isthmus**: Uses `engine_newPayloadV4` and `engine_getPayloadV4`
- **Post-Karst (Osaka)**: Uses `engine_getPayloadV5` (`engine_newPayload` and `engine_forkchoiceUpdated` stay at their V4/V3 versions)

## Metrics and Observability

The engine always includes metrics instrumentation for:

- Task execution success and failure counts
- Error rates by task type
- Engine state transitions
- API call latencies

## Extensibility

Each operation's error type implements `EngineTaskError`, whose severity decides how the engine actor recovers from the operation's failure. Tests run the operations against mock RPC transports through the same `EngineApi`.
