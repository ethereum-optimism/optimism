<Note>

</Note>

### Chain ID Support

The `--l2-chain-id` flag supports flexible chain identification using the `alloy_chains` crate:

**Numeric Chain IDs:**
```bash
kona-node --l2-chain-id 10 node [args...]      # Optimism mainnet
kona-node --l2-chain-id 8453 node [args...]    # Base mainnet
kona-node --l2-chain-id 1 node [args...]       # Ethereum mainnet
```

**String Chain Names:**
```bash
kona-node --l2-chain-id optimism node [args...]
kona-node --l2-chain-id base node [args...]
kona-node --l2-chain-id mainnet node [args...]
```

**Short Flag and Environment Variable:**
```bash
kona-node -c optimism node [args...]
export KONA_NODE_L2_CHAIN_ID=optimism && kona-node node [args...]
```

Supported chain names include all those recognized by `alloy_chains` (e.g., `optimism`, `base`, `mainnet`). Unknown numeric chain IDs are accepted for custom networks.

### Static peers

`--p2p.static-peers` lists peers that the node connects to directly and keeps connected, whatever discovery finds. Use it to make sure that a node, such as a sequencer, stays connected to the nodes it trusts.

<Warning>

Static peers don't turn discovery off. On a chain in the superchain registry, discovery starts from the chain's built-in bootnodes, even with no `--p2p.bootnodes`, and the node dials the peers saved in its bootstore. So the node still finds other nodes and connects to them, and they can find it. To connect only to static peers, also set `--p2p.no-discovery`, see [running without discovery](#running-without-discovery).

</Warning>

Each entry is a TCP multiaddr that ends in the peer's ID:

```bash
kona-node node --p2p.static-peers /dns4/node-1.example.com/tcp/9222/p2p/16Uiu2HAm...,/dns4/node-2.example.com/tcp/9222/p2p/16Uiu2HAk...
```

- Prefer `/dns4/...` addresses to `/ip4/...` ones. The name is resolved on every dial, so the list keeps working when a peer's IP changes.
- Repeat the flag, or give it a comma-separated list, as the environment variable needs. Spaces around entries are ignored, and an empty environment variable means no static peers.
- The node doesn't start if an address isn't TCP or doesn't end in `/p2p/<peer id>`.
- Several addresses with the same peer ID make one peer, dialed at whichever address connects first.
- The node ignores entries with its own peer ID, so every node in a group can use the same list.

A peer ID is derived from the node's P2P private key. Give every static peer a fixed key with `--p2p.priv.path` or `--p2p.priv.raw`; without one, a node generates a new key, and so a new peer ID, each time it starts. To find a running node's address, call [`opp2p_self`](/node-operators/kona-node/rpc/p2p#opp2p_self): `addresses` lists its listen addresses with `/p2p/<peer id>` at the end. Replace the IP with the name or address other nodes reach it at. The node also logs its peer ID when it starts listening. To get the peer ID of a key file without running the node, use `op-node p2p priv2id < key.txt`, which works for kona keys too.

The node treats its static peers as follows:

- It dials them at startup, and once a minute dials those that aren't connected. A static peer that disconnects is dialed again about a second later.
- Static peers are exempt from the redial limit (`--p2p.redial`), are never banned for a low score, and stay protected after `opp2p_unprotectPeer`.
- A static peer blocked with `opp2p_blockPeer`, or at a blocked address or subnet, isn't dialed until it's unblocked.
- The node never passes its static peers on through discovery, so other nodes can't find a static peer through it. A static peer can still be found if it runs discovery itself.

<Info>

op-node calls this flag `--p2p.static`, which kona-node accepts too. The environment variable is `KONA_NODE_P2P_STATIC_PEERS`, not `KONA_NODE_P2P_STATIC`.

</Info>

### Running without discovery

<Unreleased component="kona-node" />

With `--p2p.no-discovery`, the node doesn't run Discv5:

- It binds no UDP port, so `--p2p.listen.udp` may be in use by another process, and publishes no ENR.
- It ignores `--p2p.bootnodes`, the chain's built-in bootnodes and the bootstore.
- It connects only to its [static peers](#static-peers), to peers that dial it, and to peers added with [`opp2p_connectPeer`](/node-operators/kona-node/rpc/p2p#opp2p_connectpeer). Other nodes can't find it, so only the nodes given its address dial it.

It still exchanges blocks over gossip with the peers it's connected to. A node can relay blocks between peers that aren't connected to each other, such as the hub of a group whose members list only the hub as a static peer.

The P2P RPC methods still answer. As op-node's do when discovery is off, [`opp2p_self`](/node-operators/kona-node/rpc/p2p#opp2p_self) returns no ENR, [`opp2p_peerStats`](/node-operators/kona-node/rpc/p2p#opp2p_peerstats) returns a `table` of `0`, and [`opp2p_discoveryTable`](/node-operators/kona-node/rpc/p2p#opp2p_discoverytable) returns the error `discovery disabled`. [`opp2p_peerCount`](/node-operators/kona-node/rpc/p2p#opp2p_peercount), which op-node doesn't have, returns `null` for `connectedDiscovery`, and [`opp2p_peers`](/node-operators/kona-node/rpc/p2p#opp2p_peers) returns no ENR and a `chainID` of `0` for each peer. op-conductor's health check reads `connected` from `opp2p_peerStats`, which counts static peers.

With discovery on, the node stops if discovery fails to start or stops later, even if it has static peers.

The node finds its peers as follows:

| Discovery | Bootnodes | Static peers | Behavior |
|-----------|-----------|--------------|----------|
| On | None, chain in the registry | Any | Connects to the peers it finds from the chain's built-in bootnodes, to the peers saved in its bootstore, and to its static peers. |
| On | None, chain not in the registry | Any | Connects to the peers saved in its bootstore, if any, and to its static peers. Otherwise it finds nobody until other nodes bootstrap from it, as the first bootnode of a new network does. |
| On | Set | Any | Connects to the peers it finds from the bootnodes given and the built-in ones, to the peers saved in its bootstore, and to its static peers. |
| Off | Ignored | Set | Connects only to its static peers and the peers that dial it. A static peer that's down is dialed again once a minute, so a node can start before its peers. |
| Off | Ignored | None | Connects only to peers that dial it, or that are added with `opp2p_connectPeer`, as the hub of a group does. |

With discovery off, the node logs a warning at startup if no static peers are set, and if bootnodes are set, since it ignores them.

## RPC Trust Flags

The `--l1-trust-rpc` and `--l2-trust-rpc` flags control whether Kona verifies the block hashes of RPC responses. For guidance on when to disable trust and worked examples for trusted, untrusted, and mixed provider setups, see [configure RPC trust](/node-operators/kona-node/run/rpc-trust).

## Default Behavior

Unless overridden by the flags above, a `kona-node node` run has the following defaults:

- The P2P stack is spun up. The libp2p swarm listens on TCP `9222`
  to receive block gossip. The `discv5` discovery service runs on
  UDP port `9223`. Peer scoring is enabled.
- An RPC server is exposed at `0.0.0.0:9545`. Websocket connections
  are disabled by default.
- Prometheus metrics are disabled. Enable them with the
  `--metrics.enabled` flag; metrics are then served on `0.0.0.0:9090`,
  configurable via the `--metrics.port` and `--metrics.addr` flags.

## Rollup Configuration Loading

If a file path to a rollup config is _not_ specified via the
`--l2-config-file` cli flag, the Rollup Config will be loaded
via the [superchain registry][scr].

A custom rollup config can either be specified through the
`--l2-config-file` flag, or specific values may be overridden
using a set of override flags provided by the `kona-node`.

Override flags (for example `--canyon-override`) can be viewed
in the help menu by running `kona-node node --help`. The only
overrides currently supported are hardfork timestamps in seconds.

[scr]: https://github.com/ethereum-optimism/superchain-registry/tree/main
