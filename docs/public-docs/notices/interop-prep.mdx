[OP Stack interop](/op-stack/interop) is targeted to activate on **OP Sepolia** (chain ID `11155420`) and **Unichain Sepolia** (chain ID `1301`) on **December 10, 2026**, and on **OP Mainnet** (chain ID `10`) and **Unichain** (chain ID `130`) on **January 11, 2027**, pending governance approval.
Each pair forms a two-chain interop dependency set; run this checklist on testnet before mainnet.
Interop ships in the [Lagoon hardfork](/op-stack/protocol/hardforks/lagoon), which also carries post-execution transactions and [sequencer-defined metering](/op-stack/features/sdm).
Node operators on either chain must change their topology before the activation timestamp: each operator runs one or more [op-supernode](/op-stack/interop/supernode) instances that derive both chains and validate the cross-chain messages between them, and the rest of the fleet runs as [Light CLs](/notices/specialized-node-topology), consensus-layer clients that follow the supernode instead of deriving from L1 themselves.

<Warning>
  **A node that has not been migrated to the [supernode-plus-Light-CL topology](/notices/specialized-node-topology) by the activation timestamp cannot verify cross-chain dependencies.**
  Every op-node in the fleet must run with `--l2.follow.source` (env: `OP_NODE_L2_FOLLOW_SOURCE`) pointed at an op-supernode that derives both chains.
  Without that wiring (flag unset, or pointed at a non-supernode source), the op-node's safe head advances past the activation block without cross-chain validation, so the node cannot serve as a verifier or RPC source for the interop chain.
  The [Specialized op-node topology notice](/notices/specialized-node-topology) describes the pattern in detail.
  Start with that notice if your fleet hasn't moved off the homogeneous topology yet.
</Warning>

<Info>
  The activation timestamps are targeted for **December 10, 2026** on **OP Sepolia** and **Unichain Sepolia** and **January 11, 2027** on **OP Mainnet** and **Unichain**; the exact timestamps are not yet set.
  They will be published in the [superchain-registry](https://github.com/ethereum-optimism/superchain-registry), and this page will be updated once they are pinned.
  The mainnet activation is subject to governance approval.
</Info>

## What's changing

At the activation timestamp, OP Sepolia and Unichain Sepolia form a two-chain dependency set on testnet, and OP Mainnet and Unichain do the same on mainnet.
Every block on either chain can contain executing messages that reference initiating messages on the other; a block is only [safe](/op-stack/interop/explainer#block-safety-levels) once every initiating message it depends on has itself reached the same safety level.
The work of tracking both chains and proving those dependencies moves to a new component, [op-supernode](/op-stack/interop/supernode), that runs every chain in the dependency set together as virtual nodes inside one process.
The rest of the operator's fleet stops deriving locally and follows the supernode's safe view through op-node's [Light CL mode](/notices/specialized-node-topology).

For how cross-chain messages and block safety work under interop, see the [interop explainer](/op-stack/interop/explainer).

## Who this affects

This notice applies to anyone running OP Sepolia or Unichain Sepolia nodes after the testnet activation, and to anyone running OP Mainnet or Unichain nodes after the mainnet activation timestamp.

Every op-node in the fleet, whether a replica, an RPC node, or any other op-node deployment, must run as a Light CL pointed at an op-supernode that derives both chains.
Each operator stands up at least one op-supernode for the dependency set and reconfigures every op-node in their fleet to follow it.

<Warning>
  **If you run only one of the two chains today, you now run both.**
  The supernode needs an execution client for every chain in the dependency set, even if you serve RPC for only one of them.
  For example, an operator that serves only OP Mainnet RPC also runs a Unichain op-reth behind its supernode.
  Plan that second execution client, and its sync time, into the migration.
</Warning>

This rollout is scoped to OP Mainnet and Unichain, with OP Sepolia and Unichain Sepolia as the testnet pair.
Other OP Stack chains activate the same Lagoon hardfork on their own schedule, set in their chain config in the superchain-registry, and still need the Lagoon-aware releases by their own timestamp.
A chain with no dependencies gets a dependency set containing only itself, so there is nothing to cross-validate and those operators can keep running plain op-node.
Other OP Stack chains move to the supernode topology only when they join an interop set.

### What the topology does not allow

*   **Skipping the other chain's execution client.** Each supernode drives one execution client per chain in the dependency set. The one for the chain you don't serve can stay private: it doesn't need to serve RPC to anyone.
*   **Following a supernode you don't operate or trust.** Optimism does not operate a public follow-source endpoint. A Light CL trusts its source for its `safe` and `finalized` view and does not re-derive L2 blocks (see [how a light node trusts its source](/notices/specialized-node-topology#what-this-means)), so point `--l2.follow.source` only at supernodes you operate or explicitly trust.
*   **Backing a chain with a remote or read-only RPC.** The supernode drives each execution client over the authenticated engine API (`--authrpc.*` and a JWT secret), the same way op-node does. An `eth_*` RPC endpoint from a provider cannot stand in for it.
*   **Leaving an op-node on the old topology.** An op-node without `--l2.follow.source` keeps running after activation, but it promotes blocks to safe without checking their cross-chain messages, so its `safe` and `finalized` labels can't be trusted.

## When the safe head lags on one chain

The supernode verifies one L2 timestamp at a time, and moves on only once **every** chain in the dependency set has a local-safe block at that timestamp.
The safe and finalized heads of OP Mainnet and Unichain therefore advance together: if the safe head lags on either chain, it lags on both, including for blocks with no cross-chain messages.
New blocks are not affected: both chains keep producing and gossiping blocks as usual.

Two different things can make one chain's safe head lag:

*   **The chain's safe head lags for everyone.** For example, its batcher stops posting to L1, so no node can derive new safe blocks for it. Every operator sees the lag.
*   **Your supernode's safe head lags for that chain.** For example, the execution client behind your supernode for that chain is down, still syncing, or out of disk. Only your fleet sees the lag, so the execution client for each chain in the dependency set is on the critical path for the chain you serve.

While the safe head is lagging:

*   The unsafe head of both chains keeps advancing over P2P, so `latest` keeps moving.
*   `safe` and `finalized` stop advancing on both chains. Anything that reads those block tags, such as an exchange crediting deposits at `finalized`, waits.
*   No action is needed to recover: once the lagging chain catches up, the supernode verifies the backlog and both safe heads move forward again.

Monitor the per-chain safe head on your supernodes (the `op_node_supernode_refs_number{layer="l2",type="l2_safe"}` gauge, labelled by `virtual_node_chain_id`), and alert when either chain's safe head stops moving, so you can tell a local execution-client problem apart from a lag every operator sees.

## Choose a topology

Pick the smallest topology that meets your availability needs.
All three are valid; they differ in how many processes you run and what fails when one of them goes down.

| Topology | What you run | Use it when |
| -------- | ------------ | ----------- |
| **Minimal** | One op-supernode, plus one op-reth per chain. No separate op-node. Serve `eth_*` RPC from the op-reth of the chain you serve, and op-node RPC methods from the supernode's `/<chainID>` path. | You run a single node, or you're evaluating the setup. The supernode is a single point of failure. |
| **Fleet** | The minimal setup, plus Light CL op-nodes that follow the supernode. Each Light CL drives its own op-reth. | You serve RPC from several nodes and want to add or remove them without touching derivation. The supernode is still a single point of failure for `safe` and `finalized`. |
| **High availability** | At least three supernodes, each with its own op-reth per chain, behind a [consensus-aware `proxyd`](/chain-operators/tools/proxyd#consensus-layer-routing-for-follow-sources) for each chain you serve, with Light CLs following the proxyd. | Production. Recommended before mainnet activation. |

For example, an operator that serves OP Mainnet RPC from two nodes today and doesn't run Unichain would run:

*   **Minimal:** one supernode, one OP Mainnet op-reth, and one Unichain op-reth: three processes, but only one OP Mainnet RPC backend.
*   **Fleet:** the minimal setup, plus two Light CLs, each with its own OP Mainnet op-reth: seven processes.
*   **High availability:** three supernodes with two op-reth each, one proxyd for OP Mainnet (Unichain has no Light CLs, so it needs none), plus two Light CLs, each with its own op-reth: 14 processes.

The [specialized op-node topology notice](/notices/specialized-node-topology#why-this-matters) explains why separating the derivation tier from the RPC tier pays off as a fleet grows.

## Required components

Update or install the following components before the activation timestamp.
The versions below are the current minimums for standing up the topology; the activation releases, which carry the Lagoon timestamps, will be pinned in this notice once they are cut.
Expect two upgrades: migrate the topology on these versions now, then move every component to its activation release once it is pinned here, before your network's activation timestamp.
A binary that does not carry the timestamp diverges from the chain at activation and must be resynced; see [Network upgrades](/op-stack/protocol/network-upgrades#activations).

| Component        | Version | Role |
| ---------------- | ------- | ---- |
| `op-supernode`   | [`v1.0.6`](https://github.com/ethereum-optimism/optimism/releases/tag/op-supernode%2Fv1.0.6) or later | Runs OP Mainnet and Unichain (or OP Sepolia and Unichain Sepolia) as virtual nodes inside one binary and verifies cross-chain messages. Required component. See the [supernode explainer](/op-stack/interop/supernode) and [configuration guide](/node-operators/guides/configuration/supernode). |
| `op-node`        | [`v1.19.11`](https://github.com/ethereum-optimism/optimism/releases/tag/op-node%2Fv1.19.11) or later | Runs as a [Light CL](/notices/specialized-node-topology) on every node in the fleet; safe and finalized views are inherited from the supernode. |
| `op-reth`        | [`v2.6.1`](https://github.com/ethereum-optimism/optimism/releases/tag/op-reth%2Fv2.6.1) or later | Required execution client. Run one per chain in the dependency set — an execution client cannot back two chains (op-node rejects a mismatched chain ID at startup), so a host serving both chains runs at least two execution-client processes. |

The Lagoon activation timestamp and the dependency set are read from the superchain-registry bundle embedded in each release.
With `--network` on op-node and `--vn.<chainID>.network` on op-supernode no extra flag is needed, which is also why the activation releases matter: a binary built before the registry update does not know the timestamp.
The dependency set is looked up by chain ID, so it also applies when you pass a custom rollup config; a custom rollup config must set `lagoon_time` itself.
To override the registry's dependency set, pass `--interop.dependency-set` to op-node or `--dependency-set` to op-supernode.

## Action checklist

The migration has four phases.
Complete each one on OP Sepolia and Unichain Sepolia first, then repeat it on mainnet before the mainnet activation timestamp.
Start the execution clients first, then the supernode — the supernode drives the execution clients (ELs) through their sync, because an EL has no way to know what chain head to target on its own.
Light CLs come last, since they follow the supernode.
Full per-flag reference for the supernode is in the [op-supernode configuration reference](/node-operators/reference/op-supernode-config); this notice walks through both setups.

The command examples in the steps are minimum viable configurations; they cover the flags required for the interop topology and nothing else.
Layer your usual production flags (monitoring, logging, P2P tuning, RPC modules, resource limits) on top as your environment requires.

<Info>
  Each command block has a **Sepolia** tab and a **Mainnet** tab; pick the one for the network you are preparing.
  Sepolia commands use Sepolia L1 and beacon endpoints; mainnet commands use Ethereum mainnet endpoints.
  op-node and op-reth spell the same network differently; use each value exactly as shown.
</Info>

<Steps>
  <Step title="Stand up execution clients for both chains">
  Run at least one op-reth process per chain in the pair: OP Sepolia and Unichain Sepolia on testnet, OP Mainnet and Unichain on mainnet.
  Execution clients are not shared across chains.
  For each chain, plan one EL per consensus client connecting to it — one per supernode virtual node, plus one per Light CL in your fleet.
  Each execution client needs its own JWT secret file (a single file shared across both ELs is fine; see the note at the end of this step) and its own engine-API listen address.
  ELs can start unsynced; they wait until the supernode connects before they know what chain head to sync to.
  The supernode then drives each EL through its initial sync via the engine API, and tolerates the common case where one chain's EL is already synced and the other isn't.
  Configure each EL's history retention so the supernode can backfill initiating-message logs after restarts or downtime; the [EL retention recommendation](/node-operators/guides/configuration/supernode#configure-el-retention-for-supernode-backfill) in the supernode guide covers the retention window, the relevant op-reth pruning flags, and what changes if you also serve historical queries, withdrawal proofs, or run op-challenger.
  Bootstrapping a chain you haven't run before is the longest step: a mature chain's data directory runs to hundreds of gigabytes, and syncing from scratch takes days.

## Verify your setup before activation

Run these checks against your topology before the activation timestamp.
None of them require interop to be active on either chain; they exercise the supernode-plus-Light-CL plumbing on its own so the activation block does not surface configuration errors for the first time.

### Confirm the supernode is hosting both chains

Watch the supernode's logs using whatever you already use (`docker logs -f op-supernode`, `journalctl -fu op-supernode`, `kubectl logs -f op-supernode`, etc.).
Each chain container tags its log lines with its `chain_id`, so a healthy supernode produces interleaved derivation lines for both chains.
The most common line during catch-up is `"Advancing bq origin"` (the batch-queue is walking forward through L1):

<CodeGroup>
```text Sepolia
t=2026-11-20T12:00:00+0000 lvl=info msg="Advancing bq origin" chain_id=11155420 vn_id=7754 origin=0x...:12500000 originBehind=false
t=2026-11-20T12:00:00+0000 lvl=info msg="Advancing bq origin" chain_id=1301     vn_id=d5ca origin=0x...:12500000 originBehind=false
```

```text Mainnet
t=2026-12-01T12:00:00+0000 lvl=info msg="Advancing bq origin" chain_id=10  vn_id=7754 origin=0x...:26800000 originBehind=false
t=2026-12-01T12:00:00+0000 lvl=info msg="Advancing bq origin" chain_id=130 vn_id=d5ca origin=0x...:26800000 originBehind=false
```
</CodeGroup>

Both chain IDs of your pair (`11155420` and `1301` on testnet, `10` and `130` on mainnet) should appear regularly.
Block numbers in the sample lines are illustrative.
If you only see one chain, the other's container failed to start or its execution client is unreachable — error-level lines tagged with the missing chain explain why.
Once the supernode catches up and starts promoting heads, you will also see `msg="Sync progress"` lines with `l2_safe`, `l2_unsafe`, and `l2_finalized` fields tagged with the same `chain_id`.

If you have Prometheus scraping the supernode, the gauge `op_node_supernode_refs_number{layer="l2",type="l2_safe"}` carries the per-chain safe head on the `virtual_node_chain_id` label — a single Grafana panel makes the per-chain progression continuously visible.

### Confirm a Light CL is following the supernode

Watch a Light CL's logs the same way and look for `"Follow Source: Process external refs"` and `"Follow Upstream"` lines.
A working Light CL produces these continuously while it polls the supernode's `optimism_syncStatus`:

<CodeGroup>
```text Sepolia
t=2026-11-20T12:00:00+0000 lvl=info msg="Safety levels" unsafe=enabled safe=http://op-supernode:8545/11155420
t=2026-11-20T12:00:00+0000 lvl=info msg="Follow Upstream" eSafe=0x...:40000000 eLocalSafe=0x...:40000000 eFinalized=0x...:39999900 eCurrentL1=0x...:12500200
t=2026-11-20T12:00:00+0000 lvl=info msg="Follow Source: Process external refs" externalSafe=0x...:40000000 externalLocalSafe=0x...:40000000 externalFinalized=0x...:39999900
```

```text Mainnet
t=2026-12-01T12:00:00+0000 lvl=info msg="Safety levels" unsafe=enabled safe=http://op-supernode:8545/10
t=2026-12-01T12:00:00+0000 lvl=info msg="Follow Upstream" eSafe=0x...:145000000 eLocalSafe=0x...:145000000 eFinalized=0x...:144999900 eCurrentL1=0x...:26800200
t=2026-12-01T12:00:00+0000 lvl=info msg="Follow Source: Process external refs" externalSafe=0x...:145000000 externalLocalSafe=0x...:145000000 externalFinalized=0x...:144999900
```
</CodeGroup>

The first `"Safety levels"` line is the smoke test: if `safe=` shows your supernode URL and per-chain prefix, the wiring is right; the block numbers are illustrative.
Once the supernode is past initial sync and starts promoting safe heads, `eSafe` and `externalSafe` carry climbing block numbers.
If the Light CL never advances past genesis (`eSafe=...:0`) for many minutes, `--l2.follow.source` is pointed at the wrong URL or namespace — recheck the per-chain prefix (`/11155420` for OP Sepolia, `/1301` for Unichain Sepolia; `/10` and `/130` on mainnet).

If you scrape Prometheus, the equivalent gauge on a Light CL is `op_node_default_refs_number{layer="l2",type="l2_safe"}` — one Grafana panel per Light CL plus one panel per supernode chain, side by side, makes any divergence obvious.

## Troubleshooting

* **Safe head advances but RPC consumers report invalid blocks.** The op-node isn't following an op-supernode (`--l2.follow.source` is unset, or it points at a non-supernode source), so safe-head promotion skips cross-chain validation. Point `--l2.follow.source` at a supernode that derives both chains.
* **Blobs missing for L1 blocks older than ~18 days.** The primary beacon node has pruned them. Configure `--l1.beacon-fallbacks` against a non-pruning beacon or an archiver service. See the [blob archiver guide](/node-operators/guides/management/blobs#configuring-a-blob-archiver) for options.
* **Light CL safe head lags the supernode by more than a few blocks.** Check the network path between Light CL and supernode (or supernode `proxyd`). The Light CL polls `optimism_syncStatus` over RPC; a high-latency or rate-limited path here directly delays safe-head propagation.
* **Safe and finalized stop advancing on both chains while unsafe keeps moving.** One chain in the dependency set is behind. Check the supernode's per-chain safe head to see which one, then check that chain's execution client. See [When the safe head lags on one chain](#when-the-safe-head-lags-on-one-chain).

## FAQ

### I only serve OP Mainnet RPC. Do I need to run Unichain?

Yes, you need a Unichain execution client behind your supernode, but you don't need to serve Unichain RPC from it. See [What the topology does not allow](#what-the-topology-does-not-allow).

### Can I follow a supernode operated by Optimism or another provider?

Only one you operate or explicitly trust. Optimism does not operate a public follow-source endpoint, and a Light CL trusts its follow source for its `safe` and `finalized` view.

### Can the supernode use a remote or read-only RPC for the other chain?

No. The supernode drives each chain's execution client over the authenticated engine API, so it needs an execution client it controls.

### How much history does the other chain's execution client need?

At least 7 days of block and receipt history; no archive. See [Configure EL retention for supernode backfill](/node-operators/guides/configuration/supernode#configure-el-retention-for-supernode-backfill) for what changes if you serve historical queries or withdrawal proofs.

### Do I still need op-node?

No. The [minimal topology](#choose-a-topology) is a supernode and one op-reth per chain, with no separate op-node. Add Light CL op-nodes when you want to scale RPC serving independently of derivation.

### Do I need historical proofs?

Only if you serve `eth_getProof` for L2-to-L1 withdrawal proving or run op-challenger. If you use your nodes for RPC calls such as fetching blocks and broadcasting transactions, you don't.

### If OP Mainnet stops syncing, does Unichain's safe head lag too?

Yes. Unichain keeps producing blocks and its unsafe head keeps advancing, but its `safe` and `finalized` heads lag until OP Mainnet catches up, and the same holds the other way around. See [When the safe head lags on one chain](#when-the-safe-head-lags-on-one-chain).

### What happens to an op-node I don't migrate?

It keeps running, but it promotes blocks to safe without checking their cross-chain messages, so it can't serve as a verifier or a trustworthy RPC source after activation.
