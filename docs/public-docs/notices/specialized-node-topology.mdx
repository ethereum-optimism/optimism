In a **specialized topology**, a small number of nodes derive the [safe chain](/op-stack/reference/glossary#safe-l2-block) from L1, and every other `op-node` in the fleet runs as a [Light CL](/op-stack/reference/glossary#light-cl), also called a light node.
A Light CL is started with `--l2.follow.source` pointed at a derivation source.
It stops deriving from L1 itself, adopts the source's safe and finalized heads, and keeps advancing the [unsafe chain](/op-stack/reference/glossary#unsafe-l2-block) over P2P gossip as before.

<Warning>
  **Required for upcoming interop activation.** This topology is required for node operators on **OP Mainnet** and **Unichain** once interop activates on those chains. See the [Prepare for interop on OP Mainnet and Unichain](/notices/interop-prep) notice page for the dates and action checklist.
</Warning>

## What this means

*   **Source nodes** derive the full chain from L1. For chains in an interop dependency set, the source is an [`op-supernode`](/op-stack/interop/supernode), which derives every chain in the set together and verifies cross-chain messages. For every other chain, the source is a regular `op-node`.
*   **Light CLs** are `op-node` instances started with `--l2.follow.source=<source-rpc-endpoint>`. They poll the source's `optimism_syncStatus` and adopt its safe and finalized heads instead of deriving them.
*   **Only the derivation role changes.** Light CLs still serve RPC, participate in gossip, and drive their execution client. If the source becomes unreachable, a Light CL keeps advancing its unsafe head over P2P; its safe and finalized heads hold until the source is back. Under interop, the safe heads of every chain in a dependency set advance together; see [When the safe head lags on one chain](/notices/interop-prep#when-the-safe-head-lags-on-one-chain).
*   **A Light CL trusts its source.** It checks that the source's safe, local-safe (derived from L1 but not yet cross-chain verified), and finalized heads are consistent and that their L1 origins are on its own L1 chain, but it does not re-derive L2 blocks, and it reorgs onto the source's chain if they diverge. Point `--l2.follow.source` only at a source you operate or explicitly trust. Optimism does not operate a public follow-source endpoint.
*   `op-node` is not being deprecated, and the homogeneous topology is not being removed for chains outside an interop dependency set.

## How to migrate

### OP Mainnet and Unichain: required

Interop puts OP Mainnet and Unichain, and OP Sepolia and Unichain Sepolia, into two-chain dependency sets, so a plain `op-node` can no longer act as a derivation source for any of them.
An `op-node` left without `--l2.follow.source` keeps running, but after activation it promotes blocks to safe without cross-chain validation, so its safe and finalized labels cannot be trusted.
Before the activation timestamp on each network:

*   Run at least one `op-supernode` that derives both chains in the pair, with its own `op-reth` per chain. An execution client cannot back two chains or two consensus clients, so an operator that serves only OP Mainnet still runs a Unichain `op-reth` behind the supernode, in addition to the `op-reth` behind each Light CL.
*   Point every `op-node` you keep at the supernode's per-chain endpoint: `--l2.follow.source=http://<supernode-host>:<rpc-port>/<chainID>`, using `/10` and `/130` on mainnet or `/11155420` and `/1301` on Sepolia.
*   Migrate the Sepolia pair first; it activates earlier and is the rehearsal for mainnet.

The smallest valid setup is one `op-supernode` plus one `op-reth` per chain, with no `op-node` at all; see [Choose a topology](/notices/interop-prep#choose-a-topology) for the minimal, fleet, and high-availability options and the [FAQ](/notices/interop-prep#faq) for the questions operators ask most.

Minimum component versions are in [Required components](/notices/interop-prep#required-components); commands and verification steps are in the [action checklist](/notices/interop-prep#action-checklist).

### Other OP Stack chains: recommended

On chains outside an interop dependency set, the specialized topology is a recommended operational upgrade, not a requirement.
Existing homogeneous fleets keep working, and you can migrate one Light CL at a time.

1.  Designate one or more `op-node` instances as the **source tier**, running full L1 derivation. Size it with redundancy for failover.
2.  Start the remaining `op-node` instances (v1.16.3 or later) as Light CLs with `--l2.follow.source=<source-op-node-rpc>` (env: `OP_NODE_L2_FOLLOW_SOURCE`). `--l1` and `--l1.beacon` are still required; op-node rejects the configuration without them. Keep the network path to the source reliable and low-latency; `--l2.follow.source.rpc-timeout` (default `10s`) bounds each call.
3.  Verify each Light CL before shifting production traffic. At startup it logs `msg="Safety levels" unsafe=enabled safe=<your-source-url>`; once running, `msg="Follow Upstream"` lines report the safe and finalized heads it adopted from the source.
4.  Treat the source tier's health as a dependency of the Light CL tier in dashboards and alerting.

### Chain operators

Everything above applies to chain operators.
A sequencer `op-node` can also run with `--l2.follow.source`, which removes the derivation workload from the block-producing node.

### Highly available topology with consensus-aware proxyd

For production deployments, put the source tier behind a [consensus-aware `proxyd`](/chain-operators/tools/proxyd#consensus-layer-routing-for-follow-sources) and expose Light CLs through a separate RPC-serving tier:

<img src="/public/img/notices/light-node-topology.png" alt="Specialized op-node topology: three source op-nodes with EL (Reth) feed a consensus-aware proxyd via CL API, which fans out to two light op-nodes via --l2.follow.source" width="600" />

*   **Source tier**: a small, redundant set of `op-supernode` instances for interop chains, or `op-node` instances for other chains, behind a `proxyd` configured with `routing_strategy = "consensus_aware_consensus_layer"`. The proxy presents them as one endpoint and hides individual failures or reorgs from downstream consumers.
*   **Light CL tier**: a horizontally scalable pool of `op-node` instances with `--l2.follow.source` pointed at the source-tier `proxyd`.
*   **Edge tier**: an API gateway or user-facing `proxyd` that handles external RPC traffic, rate limiting, and routing.

For interop chains, the [supernode configuration guide](/node-operators/guides/configuration/supernode#run-an-ha-pool-of-supernodes-behind-a-consensus-aware-proxyd) covers pool size and failure behavior.

## Why this matters

*   **Less L1 load.** Only source nodes issue L1 RPC calls for derivation, which cuts L1 API load and provider cost for operators running many nodes.
*   **Independent scaling.** Add or remove Light CLs to match read traffic without changing L1 load, and size the source tier for derivation and redundancy.
*   **Cheaper upgrades.** Interop moves derivation into `op-supernode` for chains in a dependency set, and later protocol changes may raise derivation requirements on other chains. A small source tier means fewer nodes to upgrade each time.
