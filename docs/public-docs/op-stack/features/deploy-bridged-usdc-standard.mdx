This guide walks chain operators through deploying the [Bridged USDC Standard for the OP Stack](/op-stack/features/bridged-usdc-standard) on their chain using the reference implementation in the [defi-wonderland/opUSDC](https://github.com/defi-wonderland/opUSDC) repository.

For background on what the Bridged USDC Standard is and why you would deploy it, read the [Bridged USDC Standard explainer](/op-stack/features/bridged-usdc-standard) first.

## How the deployment works

The reference implementation deploys everything from a single L1 transaction:

1.  You call the `L1OpUSDCFactory` contract on L1 (Ethereum or Sepolia).
2.  The factory deploys and configures the `L1OpUSDCBridgeAdapter`, which locks USDC on L1 and relays bridge messages.
3.  The factory sends a deployment message through your chain's `L1CrossDomainMessenger`. When that message is relayed on L2, it deploys the L2 USDC proxy and the `L2OpUSDCBridgeAdapter`, which mints and burns bridged USDC on your chain.

Because the L2 contracts are deployed via a cross-domain message, you don't need to submit any L2 transactions yourself — but the bridged USDC implementation contract must already exist on your L2 before you start.

## Before you begin

You need:

*   [Foundry](https://github.com/foundry-rs/foundry#installation) and [Node.js with Yarn](https://yarnpkg.com/) installed.
*   The **bridged USDC implementation contract deployed on your L2 ahead of time**. The factory wires the L2 proxy to this implementation, so its address is a required input.
*   The address of your chain's **L1 `CrossDomainMessenger`**. For chains deployed with [OP Deployer](/chain-operators/tools/op-deployer/overview), you can read it from your deployment's state output.
*   An L1 account funded with enough ETH to submit the factory transaction, and its private key available for signing.
*   An L1 RPC endpoint for the network you are deploying on (Ethereum Mainnet or Sepolia).

<Warning>
  The deploy script contains placeholder values and a sanity check that reverts if you don't review and update them. Read through the script before broadcasting anything to Mainnet.
</Warning>

## Deploy the contracts

<Steps>
  <Step title="Clone the repository and install dependencies">
    ```bash
    git clone https://github.com/defi-wonderland/opUSDC.git
    cd opUSDC
    yarn install
    ```
  </Step>

  <Step title="Configure your environment">
    Create a `.env` file in the repository root and set the deployment variables:

    ```text
    L1_FACTORY=<L1OpUSDCFactory address for your L1 network>
    BRIDGED_USDC_IMPLEMENTATION=<your pre-deployed L2 USDC implementation address>
    L1_MESSENGER=<your chain's L1 CrossDomainMessenger address>
    CHAIN_NAME=<your chain's name>
    PRIVATE_KEY=<key that signs the L1 deployment transaction>
    ETHEREUM_RPC=<L1 RPC endpoint>
    ```

    The canonical `L1OpUSDCFactory` addresses for Ethereum Mainnet and Sepolia are listed in the [opUSDC README](https://github.com/defi-wonderland/opUSDC#readme).
  </Step>

  <Step title="Review the deploy script">
    Open `script/mainnet/Deploy.s.sol` and review the values it will use — in particular the token name (by default `Bridged USDC (<your chain name>)`) and the USDC initialization transactions. The script's sanity check reverts if the default placeholder values are left unchanged for a production deployment.
  </Step>

  <Step title="Build and simulate">
    Compile the contracts and run the deployment as a simulation first (no transactions are broadcast):

    ```bash
    yarn build
    yarn script:deploy
    ```

    Check the simulation output: it precalculates the L1 and L2 contract addresses, so you can record where the adapters and the L2 USDC proxy will land.
  </Step>

  <Step title="Broadcast the deployment">
    When the simulation looks correct, run the deployment for real:

    ```bash
    yarn script:deploy:broadcast
    ```

    This submits the factory transaction on L1. The L2 side deploys automatically when the cross-domain message is relayed on your chain — this happens within a few minutes on a healthy chain.
  </Step>

  <Step title="Verify the deployment">
    Confirm on an explorer that the `L1OpUSDCBridgeAdapter` exists on L1 and that the L2 USDC proxy and `L2OpUSDCBridgeAdapter` exist on your L2 at the precalculated addresses. If you verify contract source on an explorer, note the repository's guidance: the contracts target the `paris` EVM version, and `L1OpUSDCFactory` verification needs the `CrossChainDeployments` library address supplied in the verification settings.
  </Step>
</Steps>

## Upgrading to native USDC later

The point of the standard is that Circle can upgrade your bridged USDC to native USDC in place, preserving supply, holders, and integrations. The migration is **irreversible**, permanently disables the bridge adapters for new messages, and requires coordination with Circle, who provide the role-transfer and burn addresses used by the process. When you reach that stage, follow the migration flow documented in the [opUSDC repository](https://github.com/defi-wonderland/opUSDC) together with Circle.
