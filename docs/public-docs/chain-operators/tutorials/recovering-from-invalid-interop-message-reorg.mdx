# Recovering From an Invalid Interop Message Reorg

<Warning>Interop is still in development. This is a manual, safety-over-liveness recovery. The interop failsafe — not the stall — is what makes the network safe: while it is engaged, no interop transactions are admitted, so no new invalid executing message can be included and no further interop reorg can be triggered. **Engaging the failsafe is always the correct first step.** When you cannot confidently identify the canonical head, the target node, or the failure mode, halt with the failsafe engaged and get more engineering eyes on it — do not force recovery alone.</Warning>

When an OP Stack interop network includes an **invalid executing message**, cross-chain validation rejects it and the message — together with every block built on it — is reorged out. The invalid block is replaced with a deposit-only block at the same height, and the execution layer rewinds from the tip back to the last common ancestor. This rewind can be deep; recovery is complete when heads reconverge on the canonical chain, not at any fixed depth. Never accepting an invalid message is the correct behavior, so the protocol deliberately stops rather than serve invalid state.

The cost of that safety is that several components do not recover from the resulting deep reorg on their own and need manual operator intervention: the `op-interop-filter` failsafe stays engaged, `op-conductor` can deadlock on a stale unsafe head, a follow-mode sequencer can stay stuck on the wrong chain, and `op-reth`'s interop transaction pool can stay evicted after the failsafe clears. This runbook walks a chain operator or on-call engineer through detecting the stall, recovering each affected component, and restoring normal interop operation.

The recovery follows a single outer loop, the **failsafe-first spine**: keep interop admission blocked while you repair the wedged components, and only re-enable interop once every affected network is canonical and finalizing. The sections below are steps inside that loop.

The failsafe is the thing that makes the network safe, and it is what you engage first. A network that has truly stalled — producing no blocks at all — is incidentally safe because nothing is being admitted, but you should not rely on the stall: the guarantee comes from the failsafe blocking interop-transaction admission, which prevents any new invalid executing message from landing and any further interop reorg from being triggered. Not every failure mode stalls. Some leave the sequencer producing blocks on an **orphaned chain** — the network is live but building on a fork the rest of the dependency set has reorged away. In that case the failsafe is what keeps it safe, so engage the failsafe regardless of whether the sequencer is stalled or still producing.

This runbook targets `op-reth`-based interop deployments. It assumes the validating topology is `op-supernode` driving `op-node`, with `op-interop-filter` enforcing executing-message validity at sequencer ingress.

## Before You Begin

You should be comfortable operating `op-node`, `op-reth`, `op-conductor`, `op-interop-filter`, and the batcher and proposer for the affected network, and reaching each over RPC or `kubectl`. Recovery touches consensus-layer-aware state across multiple components, so confirm your access and inputs before you start.

### Required Tooling

Match the tool versions pinned in `mise.toml` in the optimism monorepo on the branch you deploy; that file is the source of truth and tracks each release. Older `cast` in particular may not parse the RPC syntax used throughout this runbook.

| Tool | Version |
| --- | --- |
| `foundry` (`cast`) | see `mise.toml` |
| `curl` | any |
| `jq` | see `mise.toml` |
| `kubectl` | matches your cluster |

The `op-interop-filter` admin RPC is JWT-authenticated; `cast` mints the token for you from the secret file (see **Authenticate to Admin Endpoints**), so no separate JWT helper is needed.

### Confirm Access

Confirm you can reach all of the following **before** an incident escalates:

* The JWT secret and a reachable admin port for **every** `op-interop-filter` instance in the deployment.
* `op-conductor` RPC and `op-node` admin RPC for each sequencer, reachable **directly** — by port-forward or node address, **not** through `proxyd`. During an incident `proxyd` ingress may be returning errors or restarting, and routing your control plane through it can sever your own access mid-recovery.
* The upstream `op-supernode` RPC for the network. This is the source of truth for the canonical head.
* `kubectl` or equivalent exec access to restart `op-reth`, `op-rbuilder`, and `op-node`, and to pause, inspect, and restart the batcher, proposer, and `proxyd`.

### Authenticate to Admin Endpoints

Some admin endpoints in this runbook are JWT-authenticated — the `op-interop-filter` admin port most prominently, but the same pattern applies to any JWT-protected OP Stack RPC. Each protected service has its own 32-byte hex secret in a file passed to that service (for the filter, the `--admin.jwt-secret` path); use the right file for each service rather than assuming one shared secret.

`cast rpc` mints the token for you. Point `--jwt-secret` at that secret file and `cast` signs a fresh HS256 JWT — with the required `iat` (issued-at) claim, valid for the server's 60-second window — on every call:

```bash
cast rpc <method> [params...] --jwt-secret <PATH_TO_JWT_SECRET> -r http://<HOST>:<ADMIN_PORT>
```

No manual token minting is needed. If a call ever fails with an authentication error, just re-run it — `cast` signs a new token each time, so a stale-token failure cannot persist. Throughout this runbook `<PATH_TO_JWT_SECRET>` is the filter's `--admin.jwt-secret` file.

### Enumerate the Interop Dependency Set

List every network in this interop set. A reorg on one network can cascade a reorg onto a dependent network, so more than one may end up reorged and stalled, and you engage the failsafe across all of them up front.

For each network, have a per-network status check ready so you can tell which networks actually reorged and need recovery:

* The network's `op-interop-filter` failsafe state (and the reason it tripped).
* The sequencer's heads, from its own `op-node`:

```bash
cast rpc --rpc-url http://<SEQ_NODE_RPC> optimism_syncStatus \
  | jq '{unsafe: .unsafe_l2, cross_unsafe: .cross_unsafe_l2, local_safe: .local_safe_l2, safe: .safe_l2, finalized: .finalized_l2}'
```

* The **canonical** heads for that chain, from the upstream `op-supernode` — this is the source of truth you compare every node against:

```bash
cast rpc --rpc-url http://<SUPERNODE_RPC> supernode_syncStatus \
  | jq '.chains["<CHAIN_ID>"] | {unsafe: .unsafe_l2, cross_unsafe: .cross_unsafe_l2, local_safe: .local_safe_l2, safe: .safe_l2, finalized: .finalized_l2}'
```

A network has reorged and needs recovery when a node's `unsafe_l2` (or `local_safe_l2`) hash diverges from the supernode's canonical hash at the same height, or when its heads have stopped advancing. Post-interop, `safe_l2` is the **cross-safe** head — already cross-validated — so it is the most trustworthy field to compare.

### Gather the Required Inputs

Collect these for the network you are recovering:

* The filter **index-to-URL** map (HA deployments only). When `op-reth` is configured with multiple `op-interop-filter` endpoints, it labels per-endpoint metrics and logs by configuration index (`endpoint="0"`, `"1"`, and so on) rather than URL, because the URLs can carry basic-auth credentials. Keep a mapping from index to physical filter host so you know which filter each metric and command refers to. A single-filter deployment can skip this.
* The set of sequencer and `op-conductor` nodes for the network.
* The upstream `op-supernode` RPC (the canonical-head source of truth).
* How to reach the batcher, proposer, and `proxyd` to pause, inspect, and restart them.
* Whether the `proxyd` sequencer-ingress backend group uses `routing_strategy = "consensus_aware"`. This determines whether the `proxyd` recovery section applies — confirm it now, because it is hard to determine mid-incident.

### Know When to Stop

A stalled-but-safe network is an acceptable holding state. There is no automatic recovery deadline. Before you take any risky step, know who or what you turn to for additional engineering judgment — your team's on-call or a co-responder. This runbook does not assume a formal escalation tier; "escalate" here means pause and bring in more eyes, not hand off to a separate group.

## Recovery Principles

These principles apply to **every** recovery section below. They are the spine that keeps the per-component steps from becoming a footgun. Read them before you start, and apply them at every mutating step.

* **Failsafe first.** The global order is fixed: (1) engage or keep the failsafe engaged so no interop transaction is admitted while the chain is repaired, (2) recover the wedged components until heads reconverge across every affected network, and (3) clear the failsafe **last** and restart `op-reth`. Every per-component section is a step inside this loop.
* **Confirm the target before every mutating command.** Interop spans multiple networks, and there are multiple filters, sequencers, conductors, and `op-reth` nodes. Before any write, confirm and echo back which chain ID (`eth_chainId` or `optimism_syncStatus`), which node, which filter index, and which conductor you are about to act on.
* **One observed confirmation per hazardous step.** Every hazardous step ends with a check you must observe before continuing. Never chain two mutations without confirming the first took effect, and do not proceed when a check does not return what is expected.
* **Issue recovery RPCs directly to the node, never through `proxyd`.** Every `admin_*`, `conductor_*`, and `optimism_*` recovery call targets the node directly. `proxyd` ingress can be unavailable or restarting during the incident.
* **Capture the incident baseline first.** Record the **reorg height** (the last common ancestor or replacement height) and the pre-action head numbers and hashes per affected node. The restore gate and the destructive-step rollbacks are evaluated against this baseline; without it you cannot tell when recovery is complete.
* **The supernode is the source of truth for the correct head.** Derive the canonical post-reorg head from the upstream `op-supernode` and confirm hashes against it. Never hand-enter a head. `admin_postUnsafePayload` performs **no** canonicity check — it validates only the envelope's own block hash — so posting a wrong head and starting on it re-forks the chain.
* **Destructive steps are flagged and gated.** Execution-layer rewinds, raft re-bootstrap (clearing `--raft.storage.dir` then setting `OP_CONDUCTOR_RAFT_BOOTSTRAP=true`), and filter wipe-and-restart each discard data irreversibly. Each carries a warning stating exactly what is lost, requires you to capture the pre-action state first, and marks an explicit point of no return.
* **Steps that are not validated are labeled.** Some procedures here have not yet been exercised against a real wedged chain. Those steps are labeled so you do not treat unverified prose as battle-tested during a live incident.

### On Stopping Safely

This is a safety-over-liveness system: a stalled network with the failsafe engaged is safe. Stopping is always a valid choice.

* **Do not start under uncertainty.** If you cannot confidently identify the canonical head, the target node, or the failure mode, halt and leave the failsafe engaged. The network stays safe, just stalled. Get more eyes on it before taking a risky step rather than forcing recovery alone.
* **If a step makes things worse, roll back.** Each hazardous section names how to return to the known-safe baseline — failsafe engaged, every sequencer stopped — and stop there. Returning to the safe baseline and pausing is always preferable to improvising mid-incident.

## Symptoms and Alerting

Alerting should detect this situation, not only guide recovery once you are already looking. The signals below are both what you observe during triage and the basis for alert definitions; tune thresholds and panels with your observability owner.

* **Interop failsafe engaged.** The `op-reth` aggregate gauge `optimism_transaction_pool.interop.failsafe_enabled == 1` sustained beyond a few minutes, or any filter's `admin_getFailsafeEnabled == true`. This is the first thing to check.
* **Sequencer unsafe-head lag.** `optimism_syncStatus.unsafe_l2` time falling behind wallclock or not advancing, and `op-conductor` logging `unsafe head is falling behind the unsafe interval`.
* **Sequencer on an orphaned chain.** The sequencer's `unsafe_l2` is still advancing — so head-lag and stall alerts stay quiet — but its hash diverges from the upstream `op-supernode`'s canonical chain at the same height. A still-producing sequencer is not safe while it builds on an orphaned fork; engage the failsafe.
* **Conductor cluster wedged.** `conductor_sequencerHealthy == false` across the cluster, no node reporting `conductor_leader == true`, and a high leadership-transfer rate.
* **Follower diverged or stalled.** A follow-mode node's head lagging or disagreeing with the upstream `op-supernode`, a rising `follow_source_requests_total{result="error_*"}` rate, or repeated `Follow Upstream:` warnings (notably `L1 origin of external local safe head mismatch`).
* **Filter quorum rejecting.** Rising `optimism_transaction_pool.interop.filter_decisions{result="rejected_*"}` counts on `op-reth`.

Look first at the failsafe state and its **reason**, `optimism_syncStatus` per network, and conductor health. Those three route the rest of triage.

## Triage

Work this decision tree top to bottom. It is explicit about ordering: the failsafe-first spine wraps the whole tree, and sequencer recovery comes before `proxyd` recovery and before the restore gate.

1. **Confirm, contain, and record the baseline.** Confirm the reorg or invalid message from the filter failsafe state, its **reason label**, and the supernode and sync status. **Record the reorg height** (the last common ancestor or replacement height) — the restore gate compares against it. If it is not obvious from the failsafe logs, determine it by walking back from the diverged head, comparing block hashes against a node already on the supernode-canonical chain until they agree (the walk-back command is in **Recover a Stuck or Stalled Follow-Mode Sequencer**, Rung 3). Ensure the failsafe is **engaged** (it usually auto-trips on the reorg; if not, engage it) before anything else.
   * *Non-reorg branch:* if the failsafe is on but the reason is **not** `reorg` or `cross_validation` — that is, `conflict`, `data_corruption`, or `invalid_log` — this is not an invalid-message reorg. Route to the filter non-reorg remedy (wipe-and-restart, see **Inspect and Control the Interop Filter Failsafe**) and stop. The rest of this runbook does not apply.
   * *Failsafe-off-but-wedged branch:* if symptoms of trouble are present but the failsafe is off — for example it was cleared too early, or auto-recovery cleared an `ErrorReorg` while the chain stayed wedged — **re-engage the failsafe network-wide** and continue. The symptoms are not only a stall: head lag, conductor churn, or a stuck follower, **but also a sequencer that is still producing blocks on an orphaned chain** (a fork the rest of the dependency set reorged away). A live-but-orphaned sequencer is not safe until the failsafe is engaged, so engage it here regardless of whether blocks are still being produced.
2. **Engage the failsafe network-wide, then work one network at a time.** This runbook is written from the perspective of a single network whose sequencers got stuck during the reorg. Enable the failsafe across the whole dependency set up front, because a reorg on one network can cascade onto a dependent one. Then recover this one network with the sections below. If a second network in the set also reorged and stalled, **repeat the whole runbook for that network**. There is no cross-network ordering beyond keeping the failsafe engaged everywhere until each affected network is individually recovered and canonical. See **Scope: One Network at a Time**.
3. **Coordinate the batcher and proposer** for the network under repair — pause the batcher before any head surgery. See **Coordinate the Batcher and Proposer**.
4. **Recover the wedged sequencer first.** The sequencer and execution-layer heads must stop regressing before `proxyd` or the restore gate can succeed.
   * Is the sequencer conductor-managed and wedged? Go to **Recover a Conductor-Managed Sequencer**.
   * Is a follow-mode or light-mode sequencer stuck on the wrong chain or stalled? Go to **Recover a Stuck or Stalled Follow-Mode Sequencer**.
   * *Combined case:* if the wedged sequencer is **both** conductor-managed and a stalled follower, **re-anchor the follower's head first** (follow-mode section), then run the conductor recovery — otherwise `admin_startSequencer` rejects the pinned stale head.
5. **Recover the flashblocks builder stack**, if the network runs flashblocks (`rollup-boost` and `op-rbuilder`). Confirm `rollup-boost` fell back to its standard `op-reth` execution client, and check whether the builder is silently dropping interop transactions. The network's safety does not depend on the builder. See **Recover the Flashblocks Builder Stack**.
6. **Recover `proxyd`**, now that heads are stable. If ingress is still failing for all clients (`ErrNoBackends`), or the ingress group is `consensus_aware` and showing banned backends, go to **Recover proxyd**. Do this **after** the sequencer is recovered — restarting `proxyd` while heads still regress just re-bans backends within about a second. If interop transactions fail but the filter is healthy and the group is **not** `consensus_aware`, that is the `op-reth` interop pool eviction; restart `op-reth` (handled in **Clear the Network-Wide Failsafe and Re-Enable Interop**), not a `proxyd` problem.
7. **Restore this network.** Once this network's heads are canonical, the batcher and proposer are resumed, and a healthy batch has been posted to L1 and processed, go to **Restore This Network** — the failsafe stays engaged there. The failsafe is cleared only in the single terminal section **Clear the Network-Wide Failsafe and Re-Enable Interop**, run once **every** affected network has reached this point.

At any branch where you are uncertain, stop. Leave the failsafe engaged — the network is safe, just stalled — and get more eyes on it before forcing a risky step. See [On Stopping Safely](#on-stopping-safely).

## Inspect and Control the Interop Filter Failsafe

`op-interop-filter` validates interop executing messages at sequencer ingress and answers `interop_checkAccessList`. Its **failsafe** is the master switch for interop admission: while engaged, the filter rejects every interop access-list check with JSON-RPC error code `-320602`, so no executing-message transaction is admitted. Non-interop transactions are unaffected. The failsafe is the first lever in the failsafe-first spine — engage it before any recovery, and clear it only at the very end.

The failsafe turns on in two ways:

* **Automatically.** Any chain reorg the filter ingests trips it (reason `reorg`), as do `conflict`, `data_corruption`, `invalid_log`, and a cross-validation failure (reason `cross_validation`). During an invalid-message reorg it has almost certainly already tripped before you look.
* **Manually.** You set it with `admin_setFailsafeEnabled` (reason `manual`).

The filter exposes two RPC servers:

* **Public RPC** (default port `8545`, no auth): `interop_checkAccessList` and the read-only `admin_getFailsafeEnabled`. This is the port `op-reth` and `proxyd` poll.
* **Admin RPC** (default port `8546`, JWT-authenticated): the write toggle `admin_setFailsafeEnabled`, plus `admin_getFailsafeEnabled`. It is enabled only when `admin.rpc.addr` is configured; the JWT secret is the path given by `--admin.jwt-secret`.

### Query the Failsafe State

Read the boolean from the public port, with no auth:

```bash
cast rpc --rpc-url http://<FILTER_HOST>:8545 admin_getFailsafeEnabled
# Expect: false  (validating normally)  |  true  (failsafe engaged, rejecting all interop txs)
```

The boolean does not tell you **why** the failsafe tripped. Read the reason from the filter's metrics or logs:

* Metric: the filter's `failsafe_reason_active` gauge (exported as `op_interop_filter_<process>_failsafe_reason_active`, where `<process>` defaults to `default`), labeled `reason="manual"`, `"reorg"`, `"conflict"`, `"data_corruption"`, `"invalid_log"`, or `"cross_validation"`, with value `1` for each currently active reason. More than one reason can be active at once.
* Log: while the failsafe is engaged the filter re-logs the active reason at `WARN` on a heartbeat (`--failsafe-log-interval`, default `1m`).

The reason routes triage. `reorg` or `cross_validation` is the invalid-message-reorg path this runbook covers. `conflict`, `data_corruption`, or `invalid_log` is a different failure with a different remedy — see [Non-Reorg Failsafe Trips](#non-reorg-failsafe-trips).

### Engage the Failsafe

If the failsafe has not already auto-tripped — or the sequencer is still producing blocks on an orphaned fork — engage it on the JWT admin port:

```bash
cast rpc admin_setFailsafeEnabled true --jwt-secret <PATH_TO_JWT_SECRET> -r http://<FILTER_HOST>:8546
```

Confirm it took effect from the public port:

```bash
cast rpc --rpc-url http://<FILTER_HOST>:8545 admin_getFailsafeEnabled
# Expect: true
```

`--jwt-secret` points at the filter's `--admin.jwt-secret` file (see [Authenticate to Admin Endpoints](#authenticate-to-admin-endpoints)). Engaging the failsafe is always safe — it only blocks interop admission — so when in doubt, engage it first.

Clearing the failsafe is the **last** step of recovery, owned by the terminal **Clear the Network-Wide Failsafe and Re-Enable Interop** section, because clearing it also requires restarting `op-reth` to undo a transaction-pool eviction. Do not clear it mid-recovery.

### Verify the Filter Is Validating

To confirm the filter process itself is healthy and answering — independent of failsafe state — call `interop_checkAccessList` with an empty access list on the public port:

```bash
cast rpc --rpc-url http://<FILTER_HOST>:8545 interop_checkAccessList '[]' '"unsafe"' '{}'
# Expect: null  (healthy and not in failsafe)
# Expect: an error with code -320602  (failsafe engaged)
```

<Note>The exact encoding of the `minSafety` and executing-descriptor arguments is version-specific; pin it against your deployment during validation. An empty inbox-entries list is enough to tell a healthy filter (`null`) from one in failsafe (`-320602`).</Note>

<Note>The filter's `/healthz` probe reports process liveness only — it is **not** failsafe-aware. Never infer failsafe state from `/healthz`.</Note>

Under `proxyd`'s default `agreement` interop-validation strategy, a `-320602` failsafe rejection is recognized by its error **code** and returned to the caller as a genuine rejection — the filter is healthy, just rejecting, so it is **not** counted as a backend-health failure. (Only the alternative `health-aware-load-balancing` strategy treats an HTTP 5xx — which includes the failsafe's `503` — as a transient unhealthy signal and re-probes the backend after about 10 seconds, `load_balancing_unhealthiness_timeout`; do not mistake that re-probe window for a stuck filter.)

### HA Setups With Multiple Interop Filters

When `op-reth` is configured with multiple filters (`--rollup.interop-http` repeated, with `--rollup.interop-min-responses` as the quorum threshold), `op-reth` aggregates across them and the failsafe behaves as **any-trips-all** and **clear-requires-unanimity-and-reachability**.

* **Engage (any-trips-all).** The moment **any** filter reports failsafe — on a transaction check, or on `op-reth`'s roughly 1-second background poll, which short-circuits on the first `true` — `op-reth` halts all interop admission. A failsafe on one filter cannot be outvoted by healthy ones. So to stop admission across the set, engaging the failsafe on **any one** filter is enough.
* **Disengage (clear-requires-unanimity-and-reachability).** `op-reth` clears its gate only when **every** filter replies `false`. If any filter is silent or unreachable, the gate stays closed — a silent filter might be the one in failsafe. So clearing requires setting `admin_setFailsafeEnabled false` on **every** filter instance, then confirming each is reachable and returns `false`. Loop over all filter hosts; do not stop after the first.

Read the aggregate state:

* There is no single aggregate RPC. Per-filter truth is each instance's own `admin_getFailsafeEnabled`.
* `op-reth`'s OR-aggregate view is the gauge `optimism_transaction_pool.interop.failsafe_enabled` (`1` or `0`); it reads `0` only when the gate is truly clear across every filter.
* Per-endpoint metrics live under `optimism_transaction_pool.interop.endpoint`, labeled `endpoint="<index>"` by **configuration index, not URL** (URLs can carry basic-auth credentials). The per-endpoint verdict counter is `endpoint.verdicts`, labeled `verdict="valid"`, `"invalid"`, or `"unavailable"`; there is also a per-endpoint `endpoint.up` gauge and an `endpoint.query_latency`. Use the index-to-URL map from [Before You Begin](#before-you-begin) to know which filter each label refers to.

Degraded quorum can block admission even with the failsafe off:

* Watch the `op-reth` counter `optimism_transaction_pool.interop.filter_decisions`, labeled `result="rejected_disagreement"` (filters returned mixed verdicts) and `result="rejected_no_quorum"` (too few definitive verdicts — fail-closed), plus the rate-limited "interop failing closed" log. These clear automatically once enough filters return definitive, agreeing verdicts.
* Under the `--rollup.interop-min-responses` default (unanimity, fail-closed), a single unreachable or out-of-sync filter blocks all interop admission. A majority quorum (`N/2 + 1`) tolerates one degraded filter while still only admitting on unanimous agreement among responders.

<Note>The any-trips-all aggregation described here is `op-reth`'s. `proxyd` has its own, independent interop-filter validation path that is also fail-closed and failsafe-aware — it rejects on a `-320602` failsafe verdict from any filter and applies its own quorum across the filter endpoints — described in **Recover proxyd**. That path is separate from this `op-reth` gate, and `proxyd`'s consensus poller (block-tag routing) is **not** failsafe-aware. Recover each independently.</Note>

<Note>Toggling one filter while `op-reth`'s roughly 1-second poll is mid-flight can briefly flap the gate. A filter you restart to clear errors reads as `unavailable` and holds the gate closed for the whole set until it finishes resyncing. Sequence filter restarts expecting the set to stay closed until the last one is back.</Note>

### Non-Reorg Failsafe Trips

If the failsafe reason is `conflict`, `data_corruption`, or `invalid_log` rather than `reorg` or `cross_validation`, this is **not** an invalid-message reorg and the rest of this runbook does not apply.

`admin_rewind` is not implemented — it returns an error directing you to wipe and restart — and the filter's automatic recovery clears only a `reorg` error. So the remedy for these reasons is to **wipe the filter's data directory and restart it**, letting it re-ingest from its sources.

<Warning>Wiping the filter's data directory discards its ingested state and is irreversible; the filter rebuilds by re-ingesting from its configured sources on restart. Confirm you have targeted the correct filter instance before deleting anything. In an HA set, wipe and restart one filter at a time — a restarting filter reads as `unavailable` and holds the gate closed for the whole set until it resyncs.</Warning>

The filter also has an opt-in `--reorg-recovery-enabled` flag (default off). When enabled, a background loop rewinds each errored chain's local state to its finalized point and clears **only** the `reorg` error, so a pure-reorg failsafe trip can self-clear without operator action. Manual failsafe and non-reorg errors are never auto-cleared.

## Scope: One Network at a Time

This runbook is written from the perspective of a **single network** whose sequencers got stuck during the reorg — the network where the invalid executing message landed. It does not prescribe a cross-network ordering algorithm.

Enable the failsafe **network-wide** across the whole interop dependency set up front, before recovering anything. A reorg on one network can cascade onto a dependent network, so more than one may end up reorged and stalled. Keeping the failsafe engaged everywhere blocks interop admission across the set while any single network is still being repaired.

Resuming this network's batcher and sequencer is safe even while a neighbor is still stalled. The failsafe gates only interop **executing-message admission** — it has no effect on block production, batching, or derivation (it is not referenced anywhere in `op-batcher` or `op-proposer`). So this network can produce blocks, batch to L1, and advance its safe and finalized heads while a neighbor is down, and it still cannot emit a cross-network executing message, because admission stays blocked network-wide. Resuming one network does not re-open cross-network interop.

There is no cross-network coordination beyond that:

* Recover this one network with the sections below.
* If a second network in the dependency set also reorged and stalled, **repeat the whole runbook for that network**.
* Completion is per-network canonicity — validate by canonicity, never by a reorg-depth bound. Interop reorgs can be deep.
* The network-wide failsafe stays engaged until **every** affected network has individually recovered and is canonical. It is cleared only once, in the terminal **Clear the Network-Wide Failsafe and Re-Enable Interop** section.

## Coordinate the Batcher and Proposer

Before any head surgery on the wedged sequencer, settle the two services that read from it and write to L1. Both run independently of the failsafe, so neither stops on its own when interop admission is blocked.

Both services expose their `admin_*` controls on a plain-HTTP admin RPC — **no JWT** — that is enabled only when the service runs with `--rpc.enable-admin` (or `OP_BATCHER_RPC_ENABLE_ADMIN=true` / `OP_PROPOSER_RPC_ENABLE_ADMIN=true`). The commands below target that admin RPC directly, not `proxyd`.

### Pause the Batcher Before Head Surgery

The batcher loads **unsafe** blocks from the sequencer and submits them to L1. It has safe-chain reorg detection and rebuilds its channel state from the recovered chain on resume (`clearState`), but it has two windows where it can write bad data to L1:

* Between the reorg and the manual head set, it can submit data for blocks that have just been reorged out.
* After a force-set head, it can submit data that conflicts with the recovered chain.

So pause the batcher **before** the head surgery in **Recover a Conductor-Managed Sequencer** (or the follow-mode recovery). Pause it:

```bash
cast rpc --rpc-url http://<BATCHER_ADMIN_RPC> admin_stopBatcher
# Expect: null  (now stopped)  |  error "batcher is not running"  (it was already stopped)
```

The error doubles as a state check: `admin_stopBatcher` reports `batcher is not running` if it was already stopped, and `admin_startBatcher` reports `batcher is already running` if it was already running. There is no separate read-only state RPC.

Resume the batcher **only after** the unsafe head has converged on the supernode-confirmed canonical head. Confirm convergence first, then resume:

```bash
# 1. Sequencer head vs supernode canonical head — hashes must match at the same height:
cast rpc --rpc-url http://<SEQ_NODE_RPC> optimism_syncStatus | jq '.unsafe_l2'
cast rpc --rpc-url http://<SUPERNODE_RPC> supernode_syncStatus | jq '.chains["<CHAIN_ID>"].unsafe_l2'

# 2. Once they agree, resume:
cast rpc --rpc-url http://<BATCHER_ADMIN_RPC> admin_startBatcher
# Expect: null  (now running)
```

After resuming, confirm the batcher is tracking the recovered chain rather than a stale channel: the sequencer's `safe_l2` should advance on the recovered hash within a few L1 blocks, and the batcher logs `building L2 block` / `publishing` lines for blocks at or above the recovered head.

**Re-pause guard.** If, after resuming the batcher, the unsafe head changes again — a re-reorg, or a cascade from another network — **immediately re-pause the batcher** (`admin_stopBatcher`) and return to the safe baseline before bad data is batched. The healthy-batch check in **Restore This Network** guards against this by comparing the batched `safe_l2` **hash** against the supernode-canonical hash, not merely the block number: a wrong-fork batch can advance the number too.

### The Proposer Needs No Action

The proposer requires no intervention, because it proposes only **validated** state. It proposes from `FinalizedL2`, or from `SafeL2` when `AllowNonFinalized` is set, and never reads the unsafe head.

Post-interop, `SafeL2` is the **cross-safe** head: a block becomes cross-safe only after the supernode's cross-L2 validation passes, so an invalid executing message is rejected at the local-safe-to-cross-safe boundary and never reaches the proposer's input. (`SafeL2` reorgs only on an L1 reorg — a different scenario than the invalid-message reorg this runbook covers.) The proposer therefore cannot propose across an invalid-message reorg discontinuity, with or without `AllowNonFinalized`. It simply stalls while cross-safe is held back during the wedge, and resumes on its own once cross-safe and finalized advance past the reorg. Confirm it resumes at the restore gate; no detection or remediation step is needed.

If you prefer to pause it anyway as a precaution during head surgery, `admin_stopProposer` and `admin_startProposer` on its admin RPC do so — it is not required:

```bash
cast rpc --rpc-url http://<PROPOSER_ADMIN_RPC> admin_stopProposer
cast rpc --rpc-url http://<PROPOSER_ADMIN_RPC> admin_startProposer
```

## How the Corrected Head Propagates

Recovery depends on two distinct P2P facts, and conflating them causes mistakes.

* `admin_postUnsafePayload` feeds a payload **only** into the receiving node's local derivation pipeline and engine — it does **not** re-gossip that payload to peers. It is the same ingress path a node uses for a payload received over P2P, and the same path `op-conductor` uses to hand a node a payload during failover.
* What actually propagates the corrected chain to verifiers and replicas is the chosen node **resuming sequencing** (Step 5): the blocks it seals are gossiped over P2P to the rest of the network. The sequencer producing canonical blocks — not the post call — is what pulls healthy downstream nodes onto the corrected chain.

Two consequences for recovery:

* **Before** you resume sequencing, confirm the **supernode** is on the canonical chain. If you start the chosen node on a non-canonical head, it gossips a fork that is itself about to be replaced.
* **After** the chosen node is sequencing, verify the corrected head reached downstream replicas, and re-anchor by hand any node still pinned on the pre-reorg branch — an `admin_postUnsafePayload` to the sequencer will not pull them over on its own.

## Recover a Conductor-Managed Sequencer

When the sequencer is `op-conductor`-managed and the cluster has wedged — no healthy leader, heads frozen — you manually resume sequencing on one chosen node. This is the most hazardous procedure in this runbook: while the conductor's leadership guard is overridden, nothing but your own discipline prevents two active sequencers forking the unsafe chain. Work the steps in order and do not skip a confirmation.

All commands target the conductor RPC and the `op-node` admin RPC **directly** (not through `proxyd`). The `op-node` admin calls require the node started with `--rpc.enable-admin`. Throughout, keep the interop failsafe **engaged** — none of these steps clear it.

Confirm your target before any mutation. Echo the chain ID and the node you are about to act on:

```bash
cast rpc --rpc-url http://<NODE_RPC> eth_chainId
# Expect: the hex chain ID of the network you intend to recover — re-check if it is any other chain
```

### Recognize the Deadlock

The cluster is wedged when leadership has collapsed and the unsafe head has stopped advancing. Confirm all three:

```bash
# No node thinks it is leader (run against every conductor — expect true on none):
cast rpc --rpc-url http://<CONDUCTOR_RPC> conductor_leader
# Expect: false on every conductor (a wedged cluster has no leader)

# The cluster reports itself unhealthy:
cast rpc --rpc-url http://<CONDUCTOR_RPC> conductor_sequencerHealthy
# Expect: false

# The unsafe head is frozen — read twice, a few seconds apart:
cast rpc --rpc-url http://<SEQ_NODE_RPC> optimism_syncStatus | jq '.unsafe_l2.number'
# Expect: the same number both times (a healthy chain advances)
```

Corroborating log signatures: `op-conductor` logging `unsafe head is falling behind the unsafe interval` and a high leadership-transfer rate; no node logging that it has become leader.

<Warning>This procedure overrides the conductor leadership guard. `conductor_overrideLeader` is only a flag — it provides **no** mutual exclusion between sequencers. The only thing preventing a split-brain forked chain is Step 2 having stopped sequencing on every other node. Complete and verify Step 2 before any override.</Warning>

### Step 1: Pause Every Conductor

Pause the conductor on **every** node in the cluster so none tries to start or stop a sequencer underneath you. Loop over every conductor RPC:

```bash
cast rpc --rpc-url http://<CONDUCTOR_RPC> conductor_pause
# Expect: null

cast rpc --rpc-url http://<CONDUCTOR_RPC> conductor_paused
# Expect: true
```

Confirm `conductor_paused` returns `true` on each before continuing.

### Step 2: Stop Sequencing on Every Node and Verify

This is a standalone, fully-completed gate. Stop sequencing on **every** node, then positively confirm each is inactive — do not merely issue the stop. On each node:

```bash
cast rpc --rpc-url http://<NODE_RPC> admin_stopSequencer
# Expect: a block hash (the last block it sequenced) — record it

cast rpc --rpc-url http://<NODE_RPC> admin_sequencerActive
# Expect: false
```

<Warning>A single node left sequencing here becomes a second active sequencer the moment you override leadership in Step 3, forking the unsafe chain. Confirm `admin_sequencerActive == false` on **every** enumerated node before proceeding. If any node does not return `false`, stop and resolve it first.</Warning>

### Step 3: Override Leadership on Exactly One Node

Choose one node to resume sequencing. Override leadership on **only** that node's conductor:

```bash
cast rpc --rpc-url http://<CHOSEN_CONDUCTOR_RPC> conductor_overrideLeader true
# Expect: null

cast rpc --rpc-url http://<CHOSEN_CONDUCTOR_RPC> conductor_leaderOverridden
# Expect: true
```

If no conductor is functioning at all, override on the `op-node` instead (this call takes no argument and forces the node into non-HA mode):

```bash
cast rpc --rpc-url http://<CHOSEN_NODE_RPC> admin_overrideLeader
# Expect: null
```

Confirm no **other** node is overridden — `conductor_leaderOverridden` must be `false` everywhere except the one you chose.

### Step 4: Confirm the Chosen Node Is on the Canonical Head

The chosen node must already be on the supernode-canonical head before you start sequencing — `admin_startSequencer` only starts at the node's current head, and `admin_postUnsafePayload` performs **no** canonicity check, so a wrong head here re-forks the chain. Compare hashes:

```bash
# Canonical head (source of truth):
cast rpc --rpc-url http://<SUPERNODE_RPC> supernode_syncStatus | jq '.chains["<CHAIN_ID>"].unsafe_l2'

# Chosen node's head:
cast rpc --rpc-url http://<CHOSEN_NODE_RPC> optimism_syncStatus | jq '.unsafe_l2'
# Expect: identical hash and number to the supernode's
```

If the chosen node is behind or on a different hash, do **not** force a head onto it. Canonical unsafe blocks propagate over P2P from whatever node is producing them, so a healthy node converges on its own — wait and re-check. If it will not converge, the node itself is stuck: re-anchor it with **Recover a Stuck or Stalled Follow-Mode Sequencer** first, then return here.

<Note>`admin_postUnsafePayload` exists to feed a payload directly, but it takes a full execution-payload envelope and is normally used only programmatically by `op-conductor` during failover. Hand-posting is not a routine recovery lever — prefer P2P convergence or the follow-mode re-anchor above. If you must use it, source the envelope from a node already on the canonical head and confirm the hash against the supernode first.</Note>

### Step 5: Start Sequencing on the Chosen Node

Start the chosen node at its **current** unsafe head — `admin_startSequencer` validates that the hash you pass equals the node's latest head:

```bash
HEAD=$(cast rpc --rpc-url http://<CHOSEN_NODE_RPC> optimism_syncStatus | jq -r '.unsafe_l2.hash')

cast rpc --rpc-url http://<CHOSEN_NODE_RPC> admin_startSequencer "$HEAD"
# Expect: null
# Expect on mismatch: error "block hash does not match" — the head moved; re-read $HEAD and retry

cast rpc --rpc-url http://<CHOSEN_NODE_RPC> admin_sequencerActive
# Expect: true

# Confirm the head is advancing — read twice, a few seconds apart:
cast rpc --rpc-url http://<CHOSEN_NODE_RPC> optimism_syncStatus | jq '.unsafe_l2.number'
# Expect: an increasing number
```

### Step 6: Re-Bootstrap Raft and Resume the Cluster

With one node sequencing, rebuild the raft cluster around it.

<Warning>`OP_CONDUCTOR_RAFT_BOOTSTRAP=true` only takes effect on **empty** raft storage. If the node still has raft state, the conductor logs `Raft cluster already exists, skipping bootstrap` and keeps the old membership — the flag alone does **not** rebuild the cluster. To genuinely re-bootstrap a fresh single-node cluster you must **delete the chosen node's `--raft.storage.dir` contents while its conductor is stopped**, which **discards the existing raft cluster state irreversibly**. This is the point of no return for the old cluster membership. Confirm you are bootstrapping from the node that is actively and correctly sequencing, and set `OP_CONDUCTOR_RAFT_BOOTSTRAP=false` again before the next redeploy so it does not attempt to bootstrap on a normal restart.</Warning>

Stop the chosen node's conductor, wipe its raft storage (the irreversible step above), then restart it with `OP_CONDUCTOR_RAFT_BOOTSTRAP=true` and `OP_CONDUCTOR_PAUSED=true`. After it bootstraps, resume it and re-add the other nodes as voters. The voter `id` and `addr` are each server's raft ID and consensus address; the `version` is the current cluster version from `conductor_clusterMembership`:

```bash
# 1. Stop the chosen node's conductor so nothing holds the raft store open (deployment-specific:
#    scale the workload down, or stop the conductor container if it is a sidecar):
kubectl -n <NAMESPACE> scale deploy/<CONDUCTOR> --replicas=0
kubectl -n <NAMESPACE> rollout status deploy/<CONDUCTOR>   # confirm it is fully stopped

# 2. With the conductor stopped, clear its raft storage (the irreversible step above) on the node's
#    storage volume — via a maintenance pod or direct volume access. --raft.storage.dir /
#    OP_CONDUCTOR_RAFT_STORAGE_DIR points at the path:
rm -rf <RAFT_STORAGE_DIR>/*

# 3. Set bootstrap + paused and bring the conductor back (set these via your deployment's env config;
#    kubectl set env shown for illustration):
kubectl -n <NAMESPACE> set env deploy/<CONDUCTOR> OP_CONDUCTOR_RAFT_BOOTSTRAP=true OP_CONDUCTOR_PAUSED=true
kubectl -n <NAMESPACE> scale deploy/<CONDUCTOR> --replicas=1
kubectl -n <NAMESPACE> rollout status deploy/<CONDUCTOR>

# 4. On the freshly bootstrapped leader, read the current membership and version:
cast rpc --rpc-url http://<LEADER_CONDUCTOR_RPC> conductor_clusterMembership | jq
# Expect: {"servers":[{"id":...,"addr":...,"suffrage":...}],"version":<N>}

# 5. Re-add each other node as a voter (version = the N above):
cast rpc --rpc-url http://<LEADER_CONDUCTOR_RPC> conductor_addServerAsVoter "<server-id>" "<consensus-addr>" <version>
# Expect: null

# 6. Resume the conductor on each node once it is a member again:
cast rpc --rpc-url http://<CONDUCTOR_RPC> conductor_resume
# Expect: null

# 7. Clear the bootstrap flag in the deployment config so a later redeploy does not re-bootstrap.
#    Updating it via kubectl set env rolls the pod now, which is safe — bootstrap is a no-op on the
#    existing raft state at this point. (You already resumed via conductor_resume above; setting
#    PAUSED=false just aligns the stored config with that runtime state.)
kubectl -n <NAMESPACE> set env deploy/<CONDUCTOR> OP_CONDUCTOR_RAFT_BOOTSTRAP=false OP_CONDUCTOR_PAUSED=false
```

### Exit Gate

Do not leave this section until the deadlock is positively gone:

```bash
# Every expected voter is present:
cast rpc --rpc-url http://<LEADER_CONDUCTOR_RPC> conductor_clusterMembership | jq '.servers'
# Expect: all nodes in the cluster, with the expected suffrage

# Exactly one leader (run against every conductor):
cast rpc --rpc-url http://<CONDUCTOR_RPC> conductor_leader
# Expect: true on exactly one node, false on all others

# Healthy cluster-wide:
cast rpc --rpc-url http://<CONDUCTOR_RPC> conductor_sequencerHealthy
# Expect: true on every node

# Head advancing:
cast rpc --rpc-url http://<SEQ_NODE_RPC> optimism_syncStatus | jq '.unsafe_l2.number'
# Expect: an increasing number across reads
```

The interop failsafe stays engaged — clearing it is the terminal **Clear the Network-Wide Failsafe and Re-Enable Interop** step, not part of this section.

### If a Step Makes Things Worse

If churn continues, two nodes appear active, or the head forks again, return to the known-safe baseline rather than improvising: re-engage the failsafe if it was somehow cleared, `admin_stopSequencer` on every node and confirm `admin_sequencerActive == false` on each, leave the conductors paused, and escalate. A stopped, failsafe-engaged cluster is safe; a half-recovered one with an ambiguous leader is not.

## Recover a Stuck or Stalled Follow-Mode Sequencer

A follow-mode (light-mode) sequencer runs `op-node` with `--l2.follow.source` pointed at an upstream consensus-layer RPC — the network's `op-supernode` or its `op-node` — and tracks that upstream's heads instead of deriving independently. After an interop reorg, a follower can be left on a branch the upstream reorged away, or stalled and not advancing. This section detects which of those happened and walks a least-to-most-invasive remedy ladder.

Keep the interop failsafe **engaged** throughout. Confirm the chain and node first:

```bash
cast rpc --rpc-url http://<FOLLOWER_NODE_RPC> eth_chainId
# Expect: the hex chain ID of the network you intend to recover
```

The light-sequencer invalid-message-replacement path is **op-reth-only**; the EL-specific steps below assume an `op-reth` execution client.

### Recognize the Two Failure States

Distinguish the two states — they need different remedies:

* **Stuck on the wrong chain.** The follower's head is at (or near) the upstream's height but on a **different hash** — a branch the upstream reorged away.
* **Stalled / not producing.** The follower's head **number is flat** while the upstream's advances.

Compare the follower against the upstream canonical head:

```bash
# Follower's heads:
cast rpc --rpc-url http://<FOLLOWER_NODE_RPC> optimism_syncStatus | jq '{unsafe: .unsafe_l2, local_safe: .local_safe_l2, safe: .safe_l2}'

# Upstream canonical heads for this chain (source of truth):
cast rpc --rpc-url http://<SUPERNODE_RPC> supernode_syncStatus | jq '.chains["<CHAIN_ID>"] | {unsafe: .unsafe_l2, local_safe: .local_safe_l2, safe: .safe_l2}'
```

Read it as: same `unsafe_l2.number` but different `unsafe_l2.hash` means **wrong chain**; a follower `unsafe_l2.number` that does not change across reads while the upstream's climbs means **stalled**.

The follower's follow loop also exposes its own signal. The metric labels the wrong-chain case distinctly:

```bash
curl -s http://<FOLLOWER_METRICS_HOST>:7300/metrics | grep follow_source_requests_total
# Expect: rising result="error_l1_mismatch"  (follower's L1 origin disagrees with the upstream — wrong chain)
#         rising result="error_fetch_status"  (follower cannot reach the upstream)
```

Corroborating `op-node` logs (the loop logs under the `Follow Upstream` prefix): an `Follow Upstream: Invalid external local safe: L1 origin of external local safe head mismatch` warning is the wrong-chain signature; a periodic `Follow Upstream` info line with `eSafe`/`eLocalSafe`/`eFinalized` that never moves the follower's own head is the stalled signature.

### Remedy Ladder

Work these rungs in order. Stop as soon as the follower converges (see the convergence check at the end); only escalate to the next rung if the current one does not un-stick it.

**Rung 1: Confirm the upstream canonical head and target.** Use the two `syncStatus` commands above. Fix in your mind the canonical `unsafe_l2` hash you expect the follower to reach, and the chain ID and node you are acting on.

**Rung 2: Restart `op-node`.** A follow-mode sequencer forces an initial engine reset on startup and re-runs head discovery, which is the primary un-stick for both states:

```bash
kubectl -n <NAMESPACE> rollout restart deploy/<FOLLOWER_OP_NODE>
kubectl -n <NAMESPACE> rollout status deploy/<FOLLOWER_OP_NODE>

# Then watch the follower move toward the upstream:
cast rpc --rpc-url http://<FOLLOWER_NODE_RPC> optimism_syncStatus | jq '.unsafe_l2'
# Expect: hash/number converging on the upstream canonical head
```

**Rung 3: Rewind the execution layer offline, then restart `op-node`.** If the follower is still on the wrong chain after a restart, its `op-reth` holds reorged-away blocks that must be removed. `op-reth` has **no online rewind** — the node must be stopped, because the unwind opens the database exclusively.

<Warning>An execution-layer unwind permanently discards every block above the target; it is not reversible without a resync. Record the current head height and the target ancestor first, and confirm `op-reth` is fully stopped before unwinding. This is a point of no return for the discarded blocks.</Warning>

The target is the **last common ancestor** — the reorg height you recorded during triage. To confirm it, walk back from the follower's head comparing block hashes against a known-canonical execution client (the recovered sequencer's `op-reth`) until they agree:

```bash
cast block <HEIGHT> --rpc-url http://<FOLLOWER_EL_RPC> --json | jq -r '.hash'
cast block <HEIGHT> --rpc-url http://<CANONICAL_EL_RPC> --json | jq -r '.hash'
# The highest <HEIGHT> where these hashes match is the last common ancestor.
```

Then unwind and restart:

```bash
# 1. Record the current head for your incident log:
cast rpc --rpc-url http://<FOLLOWER_EL_RPC> eth_blockNumber

# 2. Stop op-reth (the unwind needs exclusive DB access):
kubectl -n <NAMESPACE> scale deploy/<FOLLOWER_OP_RETH> --replicas=0

# 3. Unwind to the last common ancestor (removes every block above it):
op-reth stage unwind to-block <LAST_COMMON_ANCESTOR> --chain <CHAIN> --datadir <DATADIR>

# 4. Bring op-reth back, confirm the new tip, then restart op-node:
kubectl -n <NAMESPACE> scale deploy/<FOLLOWER_OP_RETH> --replicas=1
cast rpc --rpc-url http://<FOLLOWER_EL_RPC> eth_blockNumber
# Expect: at or just below the last common ancestor
kubectl -n <NAMESPACE> rollout restart deploy/<FOLLOWER_OP_NODE>
```

<Note>The offline EL-rewind rung has not been exercised against a real wedged follower; treat it as not validated and double-check the resulting tip before restarting `op-node`.</Note>

**Convergence and escalation.** The follower has converged when its `unsafe_l2.hash` matches the upstream's at the same height **and** its head number resumes advancing within a few block times:

```bash
cast rpc --rpc-url http://<FOLLOWER_NODE_RPC> optimism_syncStatus | jq '.unsafe_l2'
cast rpc --rpc-url http://<SUPERNODE_RPC> supernode_syncStatus | jq '.chains["<CHAIN_ID>"].unsafe_l2'
# Expect: identical hash and number, and the follower's number climbing on re-reads
```

If both a restart and an EL rewind fail to converge the follower, this is the end of the documented remedy. Halt, leave the failsafe engaged, and escalate — do not keep improvising.

### Conductor-Operated Followers

<Tabs>
  <Tab title="Standalone follower">
    A follower that is not conductor-managed is always active; apply the remedy ladder above directly. No leadership coordination is involved.
  </Tab>
  <Tab title="Conductor-operated">
    If the stuck follower is also part of a conductor cluster, re-anchor its head **first** with the remedy ladder above, then run **Recover a Conductor-Managed Sequencer**. Overriding leadership does not fix a pinned or wrong head — `admin_startSequencer` validates the head hash and rejects a stale one, so the head must be correct before the conductor recovery's start step can succeed.
  </Tab>
</Tabs>

## Recover the Flashblocks Builder Stack

This section applies **only** to chains running flashblocks. The builder is a **secondary path**: `op-node` talks to `rollup-boost`, which sits in front of two execution clients — a standard non-builder `op-reth` (the fallback) and `op-rbuilder` (the builder) — and `rollup-boost` automatically falls back to the standard `op-reth` when the builder is unhealthy. `op-conductor` also health-checks `rollup-boost` and fails leadership over. So a builder problem **degrades flashblocks; it does not halt the chain**, and there is no bespoke reorg state in the builder that can wedge — in-flight flashblocks are cancelled and rebuilt on the new head, and `op-reth`'s flashblocks cache reconciles reorgs on its own. Recovery is therefore "confirm the fallback happened, restart if unhealthy", plus two interop-specific wrinkles.

<Note>`rollup-boost` and `op-rbuilder` have **no** interop failsafe of their own — there is no `admin_setFailsafeEnabled` to call on them. The failsafe lives on `op-interop-filter` (see **Inspect and Control the Interop Filter Failsafe**) and the shared `op-reth` transaction-pool gate. Keep that failsafe engaged through this section.</Note>

Confirm your target first: the chain, and which `rollup-boost` / `op-rbuilder` instances you are acting on (an HA setup has one builder per sequencer).

### Confirm the Chain Is Safe Without the Builder

The chain's safety does not depend on the builder. Confirm the sequencer is still producing on its fallback execution client and that conductor leadership sits on a healthy node:

```bash
# The sequencer's unsafe head keeps advancing even with the builder down — read twice:
cast rpc --rpc-url http://<SEQ_NODE_RPC> optimism_syncStatus | jq '.unsafe_l2.number'
# Expect: an increasing number (rollup-boost is serving blocks from the fallback op-reth)

# Leadership is on a healthy node:
cast rpc --rpc-url http://<CONDUCTOR_RPC> conductor_sequencerHealthy
# Expect: true
```

If in doubt, the safe action is to run on the fallback `op-reth` and leave the builder out — do not fight the builder mid-incident.

### Wrinkle 1: The Shared Interop Pool Stuck State Affects the Builder Too

`op-rbuilder` runs `op-reth`'s **shared** interop transaction pool, so the same post-failsafe pool issue that affects `op-reth` affects the builder: after the filter's failsafe clears, the builder can keep **silently excluding interop (executing-message) transactions** from the blocks it produces.

Detect it: interop transactions are accepted by RPC but never land in builder-produced blocks, and the shared-pool eviction counter `removed_tx_interop` (metrics scope `transaction_pool`, exported `transaction_pool_removed_tx_interop`) climbed while the failsafe was engaged:

```bash
curl -s http://<BUILDER_METRICS_HOST>:<METRICS_PORT>/metrics | grep -E 'removed_tx_interop|interop.*failsafe_enabled'
# Expect: removed_tx_interop incremented during the incident; failsafe_enabled back to 0 after clearing
```

Recovery is the same fallback restart as for `op-reth` (see **Clear the Network-Wide Failsafe and Re-Enable Interop**): **restart the `op-rbuilder` pod**.

```bash
kubectl -n <NAMESPACE> rollout restart deploy/<OP_RBUILDER>
kubectl -n <NAMESPACE> rollout status deploy/<OP_RBUILDER>
```

<Warning>Restarting `op-rbuilder` on the **active conductor leader** can trigger a leadership transfer. The conductor health-checks `rollup-boost`; a builder-down window that exceeds its partial-health tolerance returns `ErrRollupBoostPartiallyHealthy` (builder down, fallback execution client up), which makes the leader stop sequencing and transfer leadership rather than wait. Restart builders on **non-leaders first**; for the leader, either pause its conductor or expect and confirm a clean transfer. Afterward, confirm a single stable leader and an active sequencer.</Warning>

```bash
# After a builder restart, confirm leadership is settled (exactly one leader, head advancing):
cast rpc --rpc-url http://<CONDUCTOR_RPC> conductor_leader        # Expect: true on exactly one node
cast rpc --rpc-url http://<SEQ_NODE_RPC> admin_sequencerActive    # Expect: true on the leader
```

### Wrinkle 2: Set a Conservative Interop Safety Level During Recovery

While the network is unstable, consider building only on **finalized** initiating messages so the builder's blocks are less likely to be reorged out by asynchronous interop validation. The builder's `--rollup.interop-safety-level` defaults to `cross-unsafe`; set it to `finalized` (this is an `op-reth` rollup argument that `op-rbuilder` shares) and restart the builder:

```bash
# Set --rollup.interop-safety-level=finalized on the op-rbuilder deployment, then restart it.
kubectl -n <NAMESPACE> rollout restart deploy/<OP_RBUILDER>
```

<Note>This is a **temporary recovery setting**. Leaving `--rollup.interop-safety-level=finalized` on after the incident is a silent flashblocks latency and inclusion regression. Add reverting it to `cross-unsafe` (and restarting the builder) to your incident close-out checklist.</Note>

### No Manual Flush Is Needed

You do **not** need to clear in-flight flashblocks or any pending builder state. The builder cancels in-flight flashblocks and rebuilds on the new head automatically, and `op-reth`'s flashblocks cache reconciles the reorg on its own. If the builder stack is misbehaving and recovery is uncertain, leave it down, run on the fallback `op-reth`, and escalate.

## Recover proxyd

`proxyd` is the ingress proxy in front of the network's RPC backends. Recover it **after** the sequencer and execution-layer heads have stabilized (the recovery sections above) — restarting its consensus poller while heads are still regressing just re-bans every backend within about a second. There is no urgency to touch `proxyd` mid-surgery: it fronts **new** transactions, which the interop failsafe is blocking anyway, and every recovery command in this runbook goes **directly** to the nodes, never through `proxyd`, so a `proxyd` problem cannot sever your control path.

Two independent subsystems can each look like a `proxyd` failure. Triage them separately — only one is actually a `proxyd` problem.

### The Interop Filter Validation Path Is Self-Healing

If executing-message transactions are rejected at ingress, that is `proxyd`'s interop-filter validation path doing its job, not a `proxyd` fault:

```bash
curl -s http://<PROXYD_METRICS_HOST>:<METRICS_PORT>/metrics | grep -E 'proxyd_rpc_interop_validations_total|proxyd_rpc_interop_filter_checks_total'
# Expect: rpc_interop_validations_total{result="failsafe"} climbing while the filter failsafe is engaged
```

`proxyd` logs `interop access list validation failed` for each rejected transaction. This points at `op-interop-filter` (see **Inspect and Control the Interop Filter Failsafe**), not `proxyd` — restarting `proxyd` does not help. This path self-heals once the filter is healthy and its failsafe is cleared (under the `health-aware-load-balancing` strategy a filter backend returning 5xx is also re-probed after about ten seconds).

### Consensus-Aware Routing Can Stall During a Deep Reorg

This applies **only** if the ingress backend group uses `routing_strategy = "consensus_aware"` (older deployments express the same thing as the now-deprecated `consensus_aware = true`). If the group is `fallback` or `multicall`, `proxyd` runs no consensus poller, a reorg has no special effect on it, and it is stateless — restart only if it is independently unhealthy. Confirm the strategy in the backend group's config before proceeding.

**Why it stalls.** A deep reorg rewinds the `safe` and `finalized` heads backwards. With the default `safe_block_drift_threshold` and `finalized_block_drift_threshold` of `0`, any backwards movement bans the backend for `consensus_ban_period` (default five minutes). If every backend is banned, the consensus group empties and `proxyd` returns `ErrNoBackends` to **all** clients — not just interop traffic — until the bans expire.

**Detect:**

```bash
curl -s http://<PROXYD_METRICS_HOST>:<METRICS_PORT>/metrics | grep -E 'proxyd_group_consensus_count|proxyd_consensus_backend_banned|proxyd_backend_unexpected_block_tags'
# Expect during the stall: group_consensus_count = 0, consensus_backend_banned = 1, backend_unexpected_block_tags rising
```

Corroborating logs: `backend banned - unexpected block tags` and `consensus broken`; clients receiving `ErrNoBackends`.

**Recover — only after heads are stable.** The bans are time-bounded and self-heal in about five minutes once the heads stop regressing. There is **no operator-facing unban endpoint**, so the only two levers are to wait out the ban or to restart `proxyd` — a restart builds a fresh consensus poller (`NewConsensusPoller` calls `Reset`) that re-polls every backend from scratch.

Capture the diagnostics **before** restarting, because a restart resets the ban state and wipes the evidence:

```bash
curl -s http://<PROXYD_METRICS_HOST>:<METRICS_PORT>/metrics \
  | grep -E 'proxyd_group_consensus_count|proxyd_consensus_backend_banned|proxyd_backend_unexpected_block_tags' \
  > proxyd-consensus-diagnostics.txt
```

Then restart (set `graceful_shutdown_seconds` to drain first if `proxyd` is behind a load balancer):

```bash
kubectl -n <NAMESPACE> rollout restart deploy/<PROXYD>
kubectl -n <NAMESPACE> rollout status deploy/<PROXYD>
```

**Prevention (a config change, not an emergency lever).** If interop reorgs are expected to rewind `safe`/`finalized` on this network, raising `safe_block_drift_threshold` and `finalized_block_drift_threshold` above `0` keeps the expected regression from banning backends in the first place. Apply this between incidents, not mid-recovery.

**Exit gate.** `group_consensus_count` back above `0`, `consensus_backend_banned` cleared, and clients served again (no `ErrNoBackends`). If heads are stable but bans keep re-applying after a restart, stop and escalate — do not loop restarts.

**Abort / safe baseline.** If restarting `proxyd` worsens the incident — for example dropping all ingress under load — stop. Leave the failsafe engaged (interop is not being admitted anyway) and get more eyes on it rather than repeatedly cycling a customer-facing component.

### Which Component Is Actually Stuck

| Symptom | Stuck component | Where to go |
| --- | --- | --- |
| `ErrNoBackends` and `consensus_backend_banned = 1` | `proxyd` consensus routing | This section (wait out the ban or restart) |
| Interop validations failing (`result="failsafe"` or `"errored"`), filter unhealthy | `op-interop-filter` | **Inspect and Control the Interop Filter Failsafe** |
| Both clean but interop transactions still rejected | `op-reth` shared pool not resuming admission | See the fallback restart in **Clear the Network-Wide Failsafe and Re-Enable Interop** |

## Restore This Network (Failsafe Stays Engaged)

This section restores **one** network. It does **not** clear the failsafe — that happens once, at the very end, in **Clear the Network-Wide Failsafe and Re-Enable Interop**, after every affected network has reached the end state below. Keeping the failsafe engaged here is what lets you restore each network independently without re-opening cross-network interop.

Work the gates in order. Each must be positively confirmed; if any is unmet, stop in the safe state (failsafe engaged) and get more eyes on it.

**Gate 1 — Heads are canonical.** This network's unsafe head matches the supernode, and the conductor cluster is healthy (the exit gate from **Recover a Conductor-Managed Sequencer**):

```bash
cast rpc --rpc-url http://<SEQ_NODE_RPC> optimism_syncStatus | jq '.unsafe_l2'
cast rpc --rpc-url http://<SUPERNODE_RPC> supernode_syncStatus | jq '.chains["<CHAIN_ID>"].unsafe_l2'
# Expect: identical hash and number
```

**Gate 2 — The batcher is resumed and tracking the recovered chain.** Confirm the batcher is running and that the re-pause guard from **Coordinate the Batcher and Proposer** did not fire (the unsafe head has not changed forks again since you resumed it):

```bash
cast rpc --rpc-url http://<BATCHER_ADMIN_RPC> admin_startBatcher
# Expect: error "batcher is already running"  (it should already be running from the coordination step)
```

**Gate 3 — A healthy batch has been posted to L1 and processed.** This is the key gate; wait for it rather than trusting the unsafe tip. After the batcher resumes, the recovered chain must be batched to L1 and derived back so the **safe** head advances **past the reorg height you recorded at triage**, with a hash that matches the supernode. A wrong-fork batch can advance the number too, so check the **hash**, not just the number:

```bash
cast rpc --rpc-url http://<SEQ_NODE_RPC> optimism_syncStatus | jq '{safe: .safe_l2, finalized: .finalized_l2}'
cast rpc --rpc-url http://<SUPERNODE_RPC> supernode_syncStatus | jq '.chains["<CHAIN_ID>"] | {safe: .safe_l2, finalized: .finalized_l2}'
# Expect: safe_l2.number > <recorded reorg height>, and safe_l2.hash matches the supernode's safe_l2.hash
```

On a quiet chain the safe head only bumps when the batcher closes a channel, which can be slow. To force the batcher to publish what it has buffered now — so the safe head advances past the reorg height without waiting out `MAX_CHANNEL_DURATION` — flush it on its admin RPC:

```bash
cast rpc --rpc-url http://<BATCHER_ADMIN_RPC> admin_flushBatcher
# Then re-check safe_l2 above; it should advance within a few L1 blocks.
```

<Note>`finalized_l2` lags `safe_l2` by L1 finality — roughly two epochs (about 13 minutes), and longer under adverse L1 conditions. A `finalized_l2` that has not yet caught up is **expected**; do not read it as failure. Confirm `finalized_l2` is advancing on the recovered chain, then wait for it to pass the reorg height before the terminal failsafe clear.</Note>

**Gate 4 — The triggering condition is gone.** The filter failsafe reason is no longer auto-tripping (it is not re-asserting `reorg` or `cross_validation`), and the invalid message and its source are not about to re-trigger the reorg. Re-read the reason as in **Query the Failsafe State**; it must be stable, not re-firing.

**End state for this network:** canonical, batched to L1, and finalizing — but the failsafe is **still engaged**. Do not clear it here. Loop back to **Triage** for any other affected network in the dependency set. Only when every affected network has reached this same end state do you proceed to the terminal section below.

## Clear the Network-Wide Failsafe and Re-Enable Interop

This is the **only** place the failsafe is cleared, and it is run **once**, after **every** affected network has individually passed the gates in **Restore This Network**.

<Warning>Before clearing, list every network that reorged during this incident and confirm each one is individually canonical, batched to L1, and finalizing. The failsafe is network-wide: clearing it re-opens interop admission across the entire dependency set at once. If even one affected network has not reached the **Restore This Network** end state, stop — do not clear.</Warning>

### Disable the Failsafe on Every Filter

Clear the failsafe on **every** `op-interop-filter` instance. In an HA set, `op-reth` keeps admission closed until **all** filters report clear (the any-trips-all / clear-requires-unanimity behavior from **HA Setups With Multiple Interop Filters**), so a single missed or unreachable filter holds interop closed for the whole network. Loop over every filter:

```bash
# Disable on each filter's JWT admin port (cast mints the JWT per Authenticate to Admin Endpoints):
cast rpc admin_setFailsafeEnabled false --jwt-secret <PATH_TO_JWT_SECRET> -r http://<FILTER_HOST>:8546

# Confirm each filter is reachable and clear:
cast rpc --rpc-url http://<FILTER_HOST>:8545 admin_getFailsafeEnabled
# Expect: false on every filter

cast rpc --rpc-url http://<FILTER_HOST>:8545 interop_checkAccessList '[]' '"unsafe"' '{}'
# Expect: null on every filter
```

Confirm `op-reth`'s aggregate view has actually opened — not just that you issued the disables:

```bash
curl -s http://<OP_RETH_METRICS_HOST>:<METRICS_PORT>/metrics | grep -E 'interop.*failsafe_enabled|interop.*endpoint'
# Expect: optimism_transaction_pool.interop.failsafe_enabled = 0, and no endpoint stuck "unavailable"
```

A silent or unreachable filter keeps admission closed — a network blip is not a healthy filter. Do not proceed until the aggregate gauge reads `0`.

### Admission Resumes Automatically

Once every filter reports clear, `op-reth` resumes admitting interop transactions on its own: its ingress gate reads the filter failsafe state on a roughly one-second poll, so it flips back to admitting within about a second of the gauge reaching `0`. No node restart is required.

Interop transactions that were already pooled when the failsafe engaged were evicted and not re-added, so the clients that submitted them must resubmit. That is expected mempool behavior, not a node fault.

<Note>`op-reth` resumes admission automatically on its roughly one-second poll, so a restart should not normally be necessary. As a fallback for a node that fails to pick the cleared state back up — if, several seconds after the aggregate gauge reads `0`, a test interop transaction is still not admitted (see the next step) — restart `op-reth`, and every `op-rbuilder`, which shares the pool. Do this only **after** the failsafe is cleared (a node restarted while the failsafe is still engaged just re-evicts on boot) and **after** finalization (so restarting an execution client cannot lose the just-set head). Restart **rolling**, one node at a time, confirming `admin_sequencerActive` and a re-anchored head per node, and handle the **active sequencer's execution client last**. For `op-rbuilder`, heed the leadership-transfer caution in **Recover the Flashblocks Builder Stack** (restart non-leaders first).</Note>

### Confirm Interop End to End

Do not stop at `admin_getFailsafeEnabled == false`. Submit a test interop (executing-message) transaction and confirm it is actually **included**, checked through **every** `op-reth` and `op-rbuilder` node — in an HA set, seeing a test message land via one node can hide another still rejecting interop traffic:

```bash
# Submit the test executing-message transaction directly to a node's ingress (not via proxyd),
# then confirm a receipt from each node in turn:
cast receipt <TX_HASH> --rpc-url http://<OP_RETH_RPC>
# Expect: a receipt with status 1 from every op-reth and op-rbuilder node
```

<Note>There is no canonical one-liner to **construct** the test executing message — it requires an initiating message on another chain in the dependency set and an access list referencing it, which is specific to your deployment and tooling. Use whatever interop-transaction helper your environment already has to submit it (directly to a node's ingress, not via `proxyd`); the verifiable, deployment-independent part is the `cast receipt` check above, confirmed against every node.</Note>

When a test interop transaction is included and confirmed across every node, every affected network is canonical and finalizing, and the failsafe is clear network-wide, the incident is recovered.
