# Recovering From an Invalid Interop Message Reorg

<Warning>Interop is still in development. This is a manual, safety-over-liveness recovery. The interop failsafe — not the stall — is what makes the network safe: while it is engaged, no interop transactions are admitted, so no new invalid executing message can be included and no further interop reorg can be triggered. **Engaging the failsafe is always the correct first step.** When you cannot confidently identify the canonical head, the target node, or the failure mode, halt with the failsafe engaged and get more engineering eyes on it — do not force recovery alone.</Warning>

When an OP Stack interop network includes an **invalid executing message**, cross-chain validation rejects it and the message — together with every block built on it — is reorged out. The invalid block is replaced with a deposit-only block at the same height, and the execution layer rewinds from the tip back to the last common ancestor. This rewind can be deep; recovery is complete when heads reconverge on the canonical chain, not at any fixed depth. Never accepting an invalid message is the correct behavior, so the protocol deliberately stops rather than serve invalid state.

The cost of that safety is that several components do not recover from the resulting deep reorg on their own and need manual operator intervention: the `op-interop-filter` failsafe stays engaged, `op-conductor` can deadlock on a stale unsafe head, a follow-mode sequencer can stay stuck on the wrong chain, and `op-reth`'s interop transaction pool can stay evicted after the failsafe clears. This runbook walks a chain operator or on-call engineer through detecting the stall, recovering each affected component, and restoring normal interop operation.

The recovery follows a single outer loop, the **failsafe-first spine**: keep interop admission blocked while you repair the wedged components, and only re-enable interop once every affected network is canonical and finalizing. The sections below are steps inside that loop.

The failsafe is the thing that makes the network safe, and it is what you engage first. A network that has truly stalled — producing no blocks at all — is incidentally safe because nothing is being admitted, but you should not rely on the stall: the guarantee comes from the failsafe blocking interop-transaction admission, which prevents any new invalid executing message from landing and any further interop reorg from being triggered. Not every failure mode stalls. Some leave the sequencer producing blocks on an **orphaned chain** — the network is live but building on a fork the rest of the dependency set has reorged away. In that case the failsafe is what keeps it safe, so engage the failsafe regardless of whether the sequencer is stalled or still producing.

This runbook targets `op-reth`-based interop deployments. It assumes the validating topology is `op-supernode` driving `op-node`, with `op-interop-filter` enforcing executing-message validity at sequencer ingress.

## Before You Begin

You should be comfortable operating `op-node`, `op-reth`, `op-conductor`, `op-interop-filter`, and the batcher and proposer for the affected network, and reaching each over RPC or `kubectl`. Recovery touches consensus-layer-aware state across multiple components, so confirm your access and inputs before you start.

### Confirm Access

Confirm you can reach all of the following **before** an incident escalates:

* The JWT secret and a reachable admin port for **every** `op-interop-filter` instance in the deployment.
* `op-conductor` RPC and `op-node` admin RPC for each sequencer, reachable **directly** — by port-forward or node address, **not** through `proxyd`. During an incident `proxyd` ingress may be returning errors or restarting, and routing your control plane through it can sever your own access mid-recovery.
* The upstream `op-supernode` RPC for the network. This is the source of truth for the canonical head.
* `kubectl` or equivalent exec access to restart `op-reth`, `op-rbuilder`, and `op-node`, and to pause, inspect, and restart the batcher, proposer, and `proxyd`.

### Sign a JWT for Admin Endpoints

Some admin endpoints in this runbook are JWT-authenticated — the `op-interop-filter` admin port most prominently, but the same pattern applies to any JWT-protected OP Stack RPC. Each protected service has its own 32-byte hex secret in a file passed to that service (for the filter, the `--admin.jwt-secret` path); read each from the right file rather than assuming one shared secret.

The token is a standard HS256 JWT whose only required claim is `iat` (issued-at), which must be within 60 seconds of the server's clock, so sign a fresh one just before each call. Sign it from the hex secret:

```bash
JWT_SECRET_HEX=$(cat <PATH_TO_JWT_SECRET>)   # e.g. the filter's --admin.jwt-secret file
JWT=$(python3 - "$JWT_SECRET_HEX" <<'EOF'
import sys, hmac, hashlib, base64, json, time
h = sys.argv[1].strip()
secret = bytes.fromhex(h[2:] if h.startswith("0x") else h)
b64 = lambda b: base64.urlsafe_b64encode(b).rstrip(b"=")
header = b64(b'{"alg":"HS256","typ":"JWT"}')
payload = b64(json.dumps({"iat": int(time.time())}, separators=(",", ":")).encode())
sig = b64(hmac.new(secret, header + b"." + payload, hashlib.sha256).digest())
print((header + b"." + payload + b"." + sig).decode())
EOF
)
```

Pass `$JWT` as a bearer token (`-H "Authorization: Bearer $JWT"`), as the filter commands below do. If a call fails with an authentication error after a delay, re-sign `$JWT` — the freshness window is short.

### Enumerate the Interop Dependency Set

List every network in this interop set. A reorg on one network can cascade a reorg onto a dependent network, so more than one may end up reorged and stalled, and you engage the failsafe across all of them up front.

For each network, have a per-network status check ready so you can tell which networks actually reorged and need recovery:

* The network's `op-interop-filter` failsafe state (and the reason it tripped).
* The sequencer's `optimism_syncStatus` (`unsafe_l2`, `safe_l2`, `finalized_l2`).

### Gather the Required Inputs

Collect these for the network you are recovering:

* The filter **index-to-URL** map (HA deployments only). When `op-reth` is configured with multiple `op-interop-filter` endpoints, it labels per-endpoint metrics and logs by configuration index (`endpoint="0"`, `"1"`, and so on) rather than URL, because the URLs can carry basic-auth credentials. Keep a mapping from index to physical filter host so you know which filter each metric and command refers to. A single-filter deployment can skip this.
* The set of sequencer and `op-conductor` nodes for the network.
* The upstream `op-supernode` RPC (the canonical-head source of truth).
* How to reach the batcher, proposer, and `proxyd` to pause, inspect, and restart them.
* Whether the `proxyd` sequencer-ingress backend group uses `routing_strategy = "consensus_aware"`. This determines whether the `proxyd` recovery section applies — confirm it now, because it is hard to determine mid-incident.

### Know When to Stop

A stalled-but-safe network is an acceptable holding state. There is no automatic recovery deadline. Before you take any risky step, know who or what you turn to for additional engineering judgment — your team's on-call or a co-responder. This runbook does not assume a formal escalation tier; "escalate" here means pause and bring in more eyes, not hand off to a separate group.

## Recovery Principles

These principles apply to **every** recovery section below. They are the spine that keeps the per-component steps from becoming a footgun. Read them before you start, and apply them at every mutating step.

* **Failsafe first.** The global order is fixed: (1) engage or keep the failsafe engaged so no interop transaction is admitted while the chain is repaired, (2) recover the wedged components until heads reconverge across every affected network, and (3) clear the failsafe **last** and restart `op-reth`. Every per-component section is a step inside this loop.
* **Confirm the target before every mutating command.** Interop spans multiple networks, and there are multiple filters, sequencers, conductors, and `op-reth` nodes. Before any write, confirm and echo back which chain ID (`eth_chainId` or `optimism_syncStatus`), which node, which filter index, and which conductor you are about to act on.
* **One observed confirmation per hazardous step.** Every hazardous step ends with a check you must observe before continuing. Never chain two mutations without confirming the first took effect, and do not proceed when a check does not return what is expected.
* **Issue recovery RPCs directly to the node, never through `proxyd`.** Every `admin_*`, `conductor_*`, and `optimism_*` recovery call targets the node directly. `proxyd` ingress can be unavailable or restarting during the incident.
* **Capture the incident baseline first.** Record the **reorg height** (the last common ancestor or replacement height) and the pre-action head numbers and hashes per affected node. The restore gate and the destructive-step rollbacks are evaluated against this baseline; without it you cannot tell when recovery is complete.
* **The supernode is the source of truth for the correct head.** Derive the canonical post-reorg head from the upstream `op-supernode` and confirm hashes against it. Never hand-enter a head. `admin_postUnsafePayload` performs **no** canonicity check — it validates only the envelope's own block hash — so posting a wrong head and starting on it re-forks the chain.
* **Destructive steps are flagged and gated.** Execution-layer rewinds, raft re-bootstrap (`OP_CONDUCTOR_RAFT_BOOTSTRAP=true`), and filter wipe-and-restart each discard data irreversibly. Each carries a warning stating exactly what is lost, requires you to capture the pre-action state first, and marks an explicit point of no return.
* **Unvalidated steps are labeled.** Some procedures here have not yet been exercised against a real wedged chain. Those steps are labeled so you do not treat unverified prose as battle-tested during a live incident.

### On Stopping Safely

This is a safety-over-liveness system: a stalled network with the failsafe engaged is safe. Stopping is always a valid choice.

* **Do not start under uncertainty.** If you cannot confidently identify the canonical head, the target node, or the failure mode, halt and leave the failsafe engaged. The network stays safe, just stalled. Get more eyes on it before taking a risky step rather than forcing recovery alone.
* **If a step makes things worse, roll back.** Each hazardous section names how to return to the known-safe baseline — failsafe engaged, every sequencer stopped — and stop there. Returning to the safe baseline and pausing is always preferable to improvising mid-incident.

## Symptoms and Alerting

Alerting should detect this situation, not only guide recovery once you are already looking. The signals below are both what you observe during triage and the basis for alert definitions; tune thresholds and panels with your observability owner.

* **Interop failsafe engaged.** The `op-reth` aggregate gauge `optimism_transaction_pool.interop.failsafe_enabled == 1` sustained beyond a few minutes, or any filter's `admin_getFailsafeEnabled == true`. This is the first thing to check.
* **Sequencer unsafe-head lag.** `optimism_syncStatus.unsafe_l2` time falling behind wallclock or not advancing, and `op-conductor` logging `unsafe head is falling behind the unsafe interval`.
* **Sequencer on an orphaned chain.** The sequencer's `unsafe_l2` is still advancing — so head-lag and stall alerts stay quiet — but its hash diverges from the upstream `op-supernode`'s canonical chain at the same height. A still-producing sequencer is not safe while it builds on an orphaned fork; engage the failsafe.
* **Conductor cluster wedged.** `conductor_sequencerHealthy == false` across the cluster, no node reporting `conductor_leader == true`, and a high leadership-transfer rate.
* **Follower diverged or stalled.** A follow-mode node's head lagging or disagreeing with the upstream `op-supernode`, a rising `FollowSourceRequests{error_*}` rate, or repeated `could not get payload: not found` logs.
* **Filter quorum rejecting.** Rising `quorum_reject_*` counters on `op-reth`.

Look first at the failsafe state and its **reason**, `optimism_syncStatus` per network, and conductor health. Those three route the rest of triage.

## Triage

Work this decision tree top to bottom. It is explicit about ordering: the failsafe-first spine wraps the whole tree, and sequencer recovery comes before `proxyd` recovery and before the restore gate.

1. **Confirm, contain, and record the baseline.** Confirm the reorg or invalid message from the filter failsafe state, its **reason label**, and the supernode and sync status. **Record the reorg height** (the last common ancestor or replacement height) — the restore gate compares against it. Ensure the failsafe is **engaged** (it usually auto-trips on the reorg; if not, engage it) before anything else.
   * *Non-reorg branch:* if the failsafe is on but the reason is **not** `reorg` or `cross_validation` — that is, `conflict`, `data_corruption`, or `invalid_log` — this is not an invalid-message reorg. Route to the filter non-reorg remedy (wipe-and-restart, see **Inspect and Control the Interop Filter Failsafe**) and stop. The rest of this runbook does not apply.
   * *Failsafe-off-but-wedged branch:* if symptoms of trouble are present but the failsafe is off — for example it was cleared too early, or auto-recovery cleared an `ErrorReorg` while the chain stayed wedged — **re-engage the failsafe network-wide** and continue. The symptoms are not only a stall: head lag, conductor churn, or a stuck follower, **but also a sequencer that is still producing blocks on an orphaned chain** (a fork the rest of the dependency set reorged away). A live-but-orphaned sequencer is not safe until the failsafe is engaged, so engage it here regardless of whether blocks are still being produced.
2. **Engage the failsafe network-wide, then work one network at a time.** This runbook is written from the perspective of a single network whose sequencers got stuck during the reorg. Enable the failsafe across the whole dependency set up front, because a reorg on one network can cascade onto a dependent one. Then recover this one network with the sections below. If a second network in the set also reorged and stalled, **repeat the whole runbook for that network**. There is no cross-network ordering beyond keeping the failsafe engaged everywhere until each affected network is individually recovered and canonical. See **Scope: One Network at a Time**.
3. **Coordinate the batcher and proposer** for the network under repair — pause the batcher before any head surgery. See **Coordinate the Batcher and Proposer**.
4. **Recover the wedged sequencer first.** The sequencer and execution-layer heads must stop regressing before `proxyd` or the restore gate can succeed.
   * Is the sequencer conductor-managed and wedged? Go to **Recover a Conductor-Managed Sequencer**.
   * Is a follow-mode or light-mode sequencer stuck on the wrong chain or stalled? Go to **Recover a Stuck or Stalled Follow-Mode Sequencer**.
   * *Combined case:* if the wedged sequencer is **both** conductor-managed and a stalled follower, **re-anchor the follower's head first** (follow-mode section), then run the conductor recovery — otherwise `admin_startSequencer` rejects the pinned stale head.
5. **Recover the flashblocks builder stack**, if the network runs flashblocks (`rollup-boost` and `op-rbuilder`). Confirm `rollup-boost` fell back to its standard `op-reth` execution client, and check whether the builder is silently dropping interop transactions. The network's safety does not depend on the builder. See **Recover the Flashblocks Builder Stack**.
6. **Recover `proxyd`**, now that heads are stable. If ingress is still failing for all clients (`ErrNoBackends`), or the ingress group is `consensus_aware` and showing banned backends, go to **Recover proxyd**. Do this **after** the sequencer is recovered — restarting `proxyd` while heads still regress just re-bans backends within about a second. If interop transactions fail but the filter is healthy and the group is **not** `consensus_aware`, that is the `op-reth` interop pool eviction; restart `op-reth` (handled in **Clear the Network-Wide Failsafe and Re-Enable Interop**), not a `proxyd` problem.
7. **Restore this network.** Once this network's heads are canonical, the batcher and proposer are resumed, and a healthy batch has been posted to L1 and processed, go to **Restore This Network** — the failsafe stays engaged there. The failsafe is cleared only in the single terminal section **Clear the Network-Wide Failsafe and Re-Enable Interop**, run once **every** affected network has reached this point.

At any branch where you are uncertain, stop. Leave the failsafe engaged — the network is safe, just stalled — and get more eyes on it before forcing a risky step. See [On Stopping Safely](#on-stopping-safely).

## Inspect and Control the Interop Filter Failsafe

`op-interop-filter` validates interop executing messages at sequencer ingress and answers `interop_checkAccessList`. Its **failsafe** is the master switch for interop admission: while engaged, the filter rejects every interop access-list check with JSON-RPC error code `-320602`, so no executing-message transaction is admitted. Non-interop transactions are unaffected. The failsafe is the first lever in the failsafe-first spine — engage it before any recovery, and clear it only at the very end.

The failsafe turns on in two ways:

* **Automatically.** Any chain reorg the filter ingests trips it (reason `reorg`), as do `conflict`, `data_corruption`, `invalid_log`, and a cross-validation failure (reason `cross_validation`). During an invalid-message reorg it has almost certainly already tripped before you look.
* **Manually.** You set it with `admin_setFailsafeEnabled` (reason `manual`).

The filter exposes two RPC servers:

* **Public RPC** (default port `8545`, no auth): `interop_checkAccessList` and the read-only `admin_getFailsafeEnabled`. This is the port `op-reth` and `proxyd` poll.
* **Admin RPC** (default port `8546`, JWT-authenticated): the write toggle `admin_setFailsafeEnabled`, plus `admin_getFailsafeEnabled`. It is enabled only when `admin.rpc.addr` is configured; the JWT secret is the path given by `--admin.jwt-secret`.

### Query the Failsafe State

Read the boolean from the public port, with no auth:

```bash
cast rpc --rpc-url http://<FILTER_HOST>:8545 admin_getFailsafeEnabled
# Expect: false  (validating normally)  |  true  (failsafe engaged, rejecting all interop txs)
```

The boolean does not tell you **why** the failsafe tripped. Read the reason from the filter's metrics or logs:

* Metric: the filter's `failsafe_reason_active` gauge (namespace `op_interop_filter`), labeled `reason="manual"`, `"reorg"`, `"conflict"`, `"data_corruption"`, `"invalid_log"`, or `"cross_validation"`, with value `1` for each currently active reason. More than one reason can be active at once.
* Log: while the failsafe is engaged the filter re-logs the active reason at `WARN` on a heartbeat (`--failsafe-log-interval`, default `1m`).

The reason routes triage. `reorg` or `cross_validation` is the invalid-message-reorg path this runbook covers. `conflict`, `data_corruption`, or `invalid_log` is a different failure with a different remedy — see [Non-Reorg Failsafe Trips](#non-reorg-failsafe-trips).

### Engage the Failsafe

If the failsafe has not already auto-tripped — or you are containing a still-producing sequencer on an orphaned chain — engage it on the JWT admin port:

```bash
curl -s http://<FILTER_HOST>:8546 \
  -H "Authorization: Bearer $JWT" \
  -H 'Content-Type: application/json' \
  -d '{"jsonrpc":"2.0","id":1,"method":"admin_setFailsafeEnabled","params":[true]}'
```

Confirm it took effect from the public port:

```bash
cast rpc --rpc-url http://<FILTER_HOST>:8545 admin_getFailsafeEnabled
# Expect: true
```

`$JWT` is the bearer token from [Sign a JWT for Admin Endpoints](#sign-a-jwt-for-admin-endpoints), signed with the filter's `--admin.jwt-secret`. Engaging the failsafe is always safe — it only blocks interop admission — so when in doubt, engage it first.

Clearing the failsafe is the **last** step of recovery, owned by the terminal **Clear the Network-Wide Failsafe and Re-Enable Interop** section, because clearing it also requires restarting `op-reth` to undo a transaction-pool eviction. Do not clear it mid-recovery.

### Verify the Filter Is Validating

To confirm the filter process itself is healthy and answering — independent of failsafe state — call `interop_checkAccessList` with an empty access list on the public port:

```bash
cast rpc --rpc-url http://<FILTER_HOST>:8545 interop_checkAccessList '[]' '"unsafe"' '{}'
# Expect: null  (healthy and not in failsafe)
# Expect: an error with code -320602  (failsafe engaged)
```

<Note>The exact encoding of the `minSafety` and executing-descriptor arguments is version-specific; pin it against your deployment during validation. An empty inbox-entries list is enough to tell a healthy filter (`null`) from one in failsafe (`-320602`).</Note>

<Note>The filter's `/healthz` probe reports process liveness only — it is **not** failsafe-aware. Never infer failsafe state from `/healthz`.</Note>

When the filter returns a transient HTTP 5xx, `proxyd` marks that backend unhealthy and re-probes after about 10 seconds (`load_balancing_unhealthiness_timeout`). A `-320602` failsafe rejection is **not** treated as backend-unhealthy — the filter is healthy, just rejecting — so it is returned to the caller as a genuine rejection. Do not mistake the roughly 10-second re-probe window for a stuck filter.

### HA Setups With Multiple Interop Filters

When `op-reth` is configured with multiple filters (`--rollup.interop-http` repeated, with `--rollup.interop-min-responses` as the quorum threshold), `op-reth` aggregates across them and the failsafe behaves as **any-trips-all** and **clear-requires-unanimity-and-reachability**.

* **Engage (any-trips-all).** The moment **any** filter reports failsafe — on a transaction check, or on `op-reth`'s roughly 1-second background poll, which short-circuits on the first `true` — `op-reth` halts all interop admission. A failsafe on one filter cannot be outvoted by healthy ones. So to stop admission across the set, engaging the failsafe on **any one** filter is enough.
* **Disengage (clear-requires-unanimity-and-reachability).** `op-reth` clears its gate only when **every** filter replies `false`. If any filter is silent or unreachable, the gate stays closed — a silent filter might be the one in failsafe. So clearing requires setting `admin_setFailsafeEnabled false` on **every** filter instance, then confirming each is reachable and returns `false`. Loop over all filter hosts; do not stop after the first.

Read the aggregate state:

* There is no single aggregate RPC. Per-filter truth is each instance's own `admin_getFailsafeEnabled`.
* `op-reth`'s OR-aggregate view is the gauge `optimism_transaction_pool.interop.failsafe_enabled` (`1` or `0`); it reads `0` only when the gate is truly clear across every filter.
* Per-endpoint metrics live under `optimism_transaction_pool.interop.endpoint`, labeled `endpoint="<index>"` by **configuration index, not URL**, exposing `valid`, `invalid`, `unavailable`, and `query_latency`. Use the index-to-URL map from [Before You Begin](#before-you-begin) to know which filter each label refers to.

Degraded quorum can block admission even with the failsafe off:

* Watch the `op-reth` counters `quorum_reject_disagreement` (filters returned mixed verdicts) and `quorum_reject_not_reached` (too few definitive verdicts — fail-closed), plus the rate-limited "failing closed" log. These clear automatically once enough filters return definitive, agreeing verdicts.
* Under the `--rollup.interop-min-responses` default (unanimity, fail-closed), a single unreachable or out-of-sync filter blocks all interop admission. A majority quorum (`N/2 + 1`) tolerates one degraded filter while still only admitting on unanimous agreement among responders.

<Note>`proxyd` does not yet enforce quorum or honor the filter failsafe; that is a separate, not-yet-landed change. Do not treat `proxyd` as failsafe-aware — the aggregation described here is `op-reth`'s.</Note>

<Note>Toggling one filter while `op-reth`'s roughly 1-second poll is mid-flight can briefly flap the gate. A filter you restart to clear errors reads as `unavailable` and holds the gate closed for the whole set until it finishes resyncing. Sequence filter restarts expecting the set to stay closed until the last one is back.</Note>

### Non-Reorg Failsafe Trips

If the failsafe reason is `conflict`, `data_corruption`, or `invalid_log` rather than `reorg` or `cross_validation`, this is **not** an invalid-message reorg and the rest of this runbook does not apply.

`admin_rewind` is not implemented — it returns an error directing you to wipe and restart — and the filter's automatic recovery clears only a `reorg` error. So the remedy for these reasons is to **wipe the filter's data directory and restart it**, letting it re-ingest from its sources.

<Warning>Wiping the filter's data directory discards its ingested state and is irreversible; the filter rebuilds by re-ingesting from its configured sources on restart. Confirm you have targeted the correct filter instance before deleting anything. In an HA set, wipe and restart one filter at a time — a restarting filter reads as `unavailable` and holds the gate closed for the whole set until it resyncs.</Warning>

The filter also has an opt-in `--reorg-recovery-enabled` flag (default off). When enabled, a background loop rewinds each errored chain's local state to its finalized point and clears **only** the `reorg` error, so a pure-reorg failsafe trip can self-clear without operator action. Manual failsafe and non-reorg errors are never auto-cleared.

## Scope: One Network at a Time

This runbook is written from the perspective of a **single network** whose sequencers got stuck during the reorg — the network where the invalid executing message landed. It does not prescribe a cross-network ordering algorithm.

Enable the failsafe **network-wide** across the whole interop dependency set up front, before recovering anything. A reorg on one network can cascade onto a dependent network, so more than one may end up reorged and stalled. Keeping the failsafe engaged everywhere blocks interop admission across the set while any single network is still being repaired.

Resuming this network's batcher and sequencer is safe even while a neighbor is still stalled. The failsafe gates only interop **executing-message admission** — it has no effect on block production, batching, or derivation (it is not referenced anywhere in `op-batcher` or `op-proposer`). So this network can produce blocks, batch to L1, and advance its safe and finalized heads while a neighbor is down, and it still cannot emit a cross-network executing message, because admission stays blocked network-wide. Resuming one network does not re-open cross-network interop.

There is no cross-network coordination beyond that:

* Recover this one network with the sections below.
* If a second network in the dependency set also reorged and stalled, **repeat the whole runbook for that network**.
* Completion is per-network canonicity — validate by canonicity, never by a reorg-depth bound. Interop reorgs can be deep.
* The network-wide failsafe stays engaged until **every** affected network has individually recovered and is canonical. It is cleared only once, in the terminal **Clear the Network-Wide Failsafe and Re-Enable Interop** section.

## Coordinate the Batcher and Proposer

Before any head surgery on the wedged sequencer, settle the two services that read from it and write to L1. Both run independently of the failsafe, so neither stops on its own when interop admission is blocked.

### Pause the Batcher Before Head Surgery

The batcher loads **unsafe** blocks from the sequencer and submits them to L1. It has safe-chain reorg detection and rebuilds its channel state from the recovered chain on resume (`clearState`), but it has two windows where it can write bad data to L1:

* Between the reorg and the manual head set, it can submit data for blocks that have just been reorged out.
* After a force-set head, it can submit data that conflicts with the recovered chain.

So pause or stop the batcher **before** the head surgery in **Recover a Conductor-Managed Sequencer** (or the follow-mode recovery), and resume it **only after** the unsafe head has converged on the supernode-confirmed canonical head. On resume, confirm the batcher is tracking the recovered chain rather than a stale channel.

**Re-pause guard.** If, after resuming the batcher, the unsafe head changes again — a re-reorg, or a cascade from another network — **immediately re-pause the batcher** and return to the safe baseline before bad data is batched. The healthy-batch check in **Restore This Network** guards against this by comparing the batched `safe_l2` **hash** against the supernode-canonical hash, not merely the block number: a wrong-fork batch can advance the number too.

### The Proposer Stalls Safely

The proposer proposes from `FinalizedL2`, or from `SafeL2` when `AllowNonFinalized` is set. It does not read the unsafe head, so head surgery cannot directly corrupt a proposal. It naturally stalls during the wedge — that is expected — and resumes on its own once safe and finalized advance past the reorg.

The one case that needs a check is `AllowNonFinalized`: the proposer reads `SafeL2`, which can briefly track a wrong fork.

* **Detection:** compare the proposed outputs or super-roots already on L1 against the recovered safe chain at the reorg height, to see whether the proposer submitted across the reorg discontinuity.
* **Routing:** if a stale root reached L1, route it to the dispute-games owner as tracked follow-up. Do not gate recovery on it — but do not leave it undetected either.

## How the Corrected Head Propagates

A payload set on the sequencer with `admin_postUnsafePayload` is fed into the local derivation pipeline **and gossiped over P2P** to verifiers and replicas — this is intended; it is the same path conductor failover uses. Two consequences for recovery:

* **Before** setting the head, confirm the **supernode** is on the canonical chain. If you re-anchor onto a head the supernode will reorg again, the corrected payload gossips a head that is itself about to be replaced.
* **After** setting it, verify the payload propagated to downstream replicas, and re-anchor by hand any node still pinned on the pre-reorg branch.
