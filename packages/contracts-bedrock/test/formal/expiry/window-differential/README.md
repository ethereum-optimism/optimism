# Message expiry window: Go/Rust differential

The protocol rejects an executing message whose block is more than the message expiry window `W`
after the block of its initiating message
([spec](https://specs.optimism.io/interop/messaging.html#message-expiry-invariant)):

```
valid  iff  init <= exec  and  exec - init <= W,   W = override > 0 ? override : 604800 (7 days)
```

and an override above 7 days must be rejected when the dependency set is read (never clamped),
because `L2ToL2CrossDomainMessenger` marks a message expired, and apps refund it, a day after
7 days. This directory holds the shared vectors; the tests that check the real implementations
against them live next to those implementations.

| Implementation | Test | Path exercised |
|---|---|---|
| op-core `LinkCheckerImpl.CanExecute` | `op-core/interop/depset/window_differential_test.go` | a real `StaticConfigDependencySet`, built by the constructor, from JSON and from TOML (all three must agree) |
| op-supernode `verifyExecutingMessage` | `op-supernode/supernode/activity/interop/window_differential_test.go` | an `Interop` built with `New` from that dependency set, its source logs DB swapped for one that contains every message |
| kona `MessageGraph` | `rust/kona/crates/protocol/interop/tests/window_differential.rs` | `MessageGraph::derive` + `resolve` over a two-chain superchain, with the window the proof program passes and the dependency set parsed from JSON; plus `MessageRules` directly |

## Vectors

`vectors.json` (214 vectors) is generated by `gen-vectors.py`, with expected values computed on
unbounded integers, independently of the implementations:

- for each override in 0, 1, 2, 3600, 7d-1, 7d (accepted) and 7d+1, 8d, 2^63-1, 2^64-2, 2^64-1
  (rejected): `exec - init` in {W-1, W, W+1, 0, 1} and `init - exec` in {1, W, W+1} from bases
  1, 1e9, 2^63 and 2^64-1-W-1; and the u64 extremes, including `init = 2^64-1, exec = 1`, where a
  lone wrapping `exec - init` would come out as 2 and pass;
- `reason` is the first failing rule (`future`, `expired`) or `ok`; overrides above the cap carry
  `configRejected: true`.

2^63-1 is the largest TOML integer, so it reaches op-core's cap through every config path; 2^64-2
and 2^64-1 are rejected by the TOML parser first (the Go test checks the cap's own error wherever
the cap is reached). Every vector has `init, exec >= 1`, so the activation rule (activation 0,
block time 1) never fires first.

Each test also runs a seeded property test against the formula: Go `testing/quick` (20,000
cases) and a seeded loop (25,000) for op-supernode; Rust `StdRng` cases through `MessageGraph`
(5,000) and through `MessageRules` (200,000).

## Running

```sh
python3 gen-vectors.py   # regenerate vectors.json
just build-superchain-go # once, for op-supernode
go test ./op-core/interop/depset/ ./op-supernode/supernode/activity/interop/ \
  -run 'WindowDifferential|WindowVectors|WindowProperty' -count=1
cd rust && cargo nextest run -p kona-interop --test window_differential
```

## Results

All pass on the formal branch at `8fbf931eb7` plus the kona test's update for the
`MessageExpiryOverride` newtype (`override_message_expiry_window` is now
`Option<MessageExpiryOverride>`; the test reads it through `u64::from`): the op-core vector and
property tests, op-supernode's `WindowVectors` and `WindowProperty`, and kona's five
`window_differential` tests (`cargo test -p kona-interop --test window_differential`). That branch
merges the window cap of op-core, kona and op-interop-filter into the contracts stack. They first
passed at `52ff613e14`. Each of these single-line changes to the implementations makes the
tests fail: drop op-core's cap; clamp instead of reject; `>` to `>=` in the op-core window check;
drop op-supernode's ordering check; drop kona's cap; `<=` to `<` in kona's expiry or ordering
check; and remove the `check_message_ordering` call from `MessageGraph` (caught by the graph-level
tests, not by the `MessageRules` ones).

## Notes

- `init > exec`: both Go functions check ordering first and reject it. kona's
  `check_message_expiry` alone is not total (it documents `init <= exec` as a precondition, and a
  wrapping build would accept `init = 2^64-1, exec = 1`); `MessageGraph` always checks ordering
  first, which the graph-level test exercises.
- kona's override is a `MessageExpiryOverride`, whose `TryFrom<u64>` (also used by serde)
  rejects a value above the cap, so a larger window can be neither parsed nor built in code, and
  the effective window never exceeds the cap. op-interop-filter has its own cap in
  `Config.Validate` (`op-interop-filter/filter/config.go`).
- An identifier timestamp above 2^64 is decoded differently: Go rejects the log, kona saturates it
  to 2^64-1. The verdicts differ only if `exec = 2^64-1`, which cannot happen.
