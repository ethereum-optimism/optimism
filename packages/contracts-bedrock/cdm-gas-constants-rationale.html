Evidence tags: verified read directly from code, commit messages or tests at this commit; inferred reasoned from EVM/EIP semantics or arithmetic, not stated in the repo; unverified could not be confirmed.

Reading guide: local vs remote

baseGas is computed on the sending chain but budgets relayMessage on the receiving chain. f4dde99251 therefore split each constant by whose EVM runs it: LOCAL_* drive this chain's own relayMessage (relayMessage hasMinGas check, gas for the call); REMOTE_* feed baseGas for the other chain (L1 baseGas, L2 baseGas). So L1 REMOTE_* describes L2 execution and vice versa. verified The same commit states "All values are unchanged", and all current values are identical on both sides. The legacy RELAY_* getters are aliases of the REMOTE_* values (L1CrossDomainMessenger.sol:64-78, L2CrossDomainMessenger.sol:48-62).

Spec note: the OP specs repo (at 7a556d55) describes baseGas qualitatively (specs/experimental/contracts/L1/l1-cross-domain-messenger.md, L2 equivalent) and the Portal min gas limit as bytes*40 + 21000 and receive limit 100000 (specs/fault-proof/stage-one/optimism-portal.md). It gives no numeric values for the relay constants. verified

How the constants combine

Receiving side (relayMessage): proceeds to the call only if hasMinGas(_minGasLimit, LOCAL_RESERVED + LOCAL_BUFFER), i.e. gas*63 ≥ minGas*64 + 63*(40000 + reserved + buffer) (SafeCall.sol:98-104). Then it forwards gasleft() - LOCAL_RESERVED to the target.

Sending side (_baseGas): executionGas = CONSTANT + CALL_OVERHEAD + RESERVED + BUFFER + minGas*64/63; size = len(message) + 260; baseGas = 21000 + max(executionGas + size*16, size*40). verified

Design property: if the relay tx is given baseGas, then after intrinsic gas and the 200k constant overhead the hasMinGas check passes, so the target gets at least _minGasLimit, and failure can always be recorded for replay. Gas between the two (enough to record, not to call) records the message in failedMessages (CrossDomainMessenger.sol:266-283). verified (comment text in code and 2bf225ae17 message)

Per-constant sections

LOCAL_RELAY_RESERVED_GAS / REMOTE_RELAY_RESERVED_GAS (both 125,000)

Used at
Local: CrossDomainMessenger.sol:266 (in hasMinGas reserve), CrossDomainMessenger.sol:285 (subtracted from forwarded gas); getters L1CrossDomainMessenger.sol:150, L2CrossDomainMessenger.sol:114. Remote: L1CrossDomainMessenger.sol:127, L2CrossDomainMessenger.sol:91 into _baseGas.
Budgets for
Everything relayMessage does after the target call: reset xDomainMsgSender, write successfulMessages[hash] or failedMessages[hash] (a fresh slot), emit the event. verified (natspec)
Derivation
40,000 (2023): introduced as RELAY_RESERVED_GAS = 40_000 with the comment "finalizing the execution of relayMessage after the safe call" in 2bf225ae17. No derivation is given in the commit; it comfortably exceeds a cold zero-to-nonzero SSTORE (22,100) plus event and the xDomainMsgSender reset. inferred
125,000 (2026): 37ce0f6928 (squashed into 6b1b243623, #681). Message: under Amsterdam the fresh-slot write costs EIP-8037 state gas on top of the SSTORE, more than 40k; a target that burned all forwarded gas left the relay out of gas while recording the failure, so the relay reverted at any gas amount and could not be replayed. "Measured need is about 113k in an unoptimized build; raise the reserve to 125k." verified The 113k is a forge measurement; 125k is the measured need plus roughly 12k margin (about 10%). The margin choice is not otherwise justified. inferred Consistency check: EIP-8037 prices a new storage slot at 64 bytes x 1,530 = 97,920 state gas, which matches the "roughly 97,920" figure in the #681 message and leaves about 15k for regular gas. verified (arithmetic from EIP text and commit)
History
2bf225ae17 (Apr 2023, merged via 3006ef0c92, PR #5508 "Remove minGas revert in relayMessage") added it as 40,000. 37ce0f6928 raised it to 125,000 and "raises baseGas by 85k in both directions". f4dde99251 split it into LOCAL/REMOTE (value unchanged). 37ce0f6928 also retuned the invariant test's under-funded band from 125k-135k to 225k-235k (invariant test test/invariants/CrossDomainMessenger.t.sol) and changed the Portal bricking tests (37ce0f6928 diff).
Why symmetric
Both directions got 125k although only L1 runs EIP-8037. L1's LOCAL value is the one 8037 requires. L2's LOCAL value and L1's REMOTE value (L1-to-L2 messages carry the extra 85k) were raised for symmetry; the repo never shows that L2 needs 125k. inferred
Nit
The L2 natspec for LOCAL_RELAY_RESERVED_GAS (L2CrossDomainMessenger.sol:26-28) and the L1-side REMOTE_RELAY_RESERVED_GAS (L2CrossDomainMessenger.sol:40-42) say "including EIP-8037 state gas". On L2, EIP-8037 does not apply (L1 only), so the L2 LOCAL comment is misleading; the L2 REMOTE_* (L1 cost) comment is accurate. verified

LOCAL_RELAY_GAS_CHECK_BUFFER / REMOTE_RELAY_GAS_CHECK_BUFFER (both 5,000)

Used at
CrossDomainMessenger.sol:266; getters L1CrossDomainMessenger.sol:155, L2CrossDomainMessenger.sol:119; remote L1CrossDomainMessenger.sol:128, L2CrossDomainMessenger.sol:92.
Budgets for
Execution between the hasMinGas check and the CALL opcode: xDomainMsgSender = _sender (SSTORE), the gasleft() read, arguments setup. Natspec: "Gas reserved ... for the execution between the hasMinGas check and the external call". verified
Derivation
Chosen as a conservative round number in 2bf225ae17 (inline comment: "(Conservative)"). The previous inline derivation in callWithMinGas counted only 51 gas between GAS and CALL; but the messenger also performs an SSTORE of xDomainMsgSender in that window (up to ~22k cold if the slot were not already warm; it is non-zero so the transition costs 2,900-5,000 with the slot warmed by the earlier read). The 5,000 figure therefore covers a warm nonzero-to-nonzero SSTORE. inferred
History
Unchanged since 2bf225ae17; renamed LOCAL/REMOTE in f4dde99251. Note the SafeCall natspec talks about a "5,700" buffer (see the 40,000 section); that is a different, older figure.
EIP-8037
Not adjusted. xDomainMsgSender is non-zero to non-zero (default 0xdead to sender) so no new state is created; no state gas expected. inferred

REMOTE_RELAY_CONSTANT_OVERHEAD (200,000)

Used at
L1CrossDomainMessenger.sol:125, L2CrossDomainMessenger.sol:89 into _baseGas. There is no LOCAL counterpart: it is only a sending-side budget.
Budgets for
Fixed cost of relayMessage on the remote chain up to the check: pause check, nonce decode, V1 hashing, cold SLOADs of successfulMessages and failedMessages, _isOtherMessenger() (portal l2Sender() call on L1), _isUnsafeTarget. Also absorbs the cost of recording a failure from cold storage when the check fails. inferred
Derivation
Empirical. b7b77d6c86 (PR #3023, Jul 2022, smartcontracts) "tweak XDM.baseGas to more accurately reflect the actual cost of performing a deposit on L2. I've been able to use the SDK to successfully complete deposits with these values." It doubled the original MIN_GAS_CONSTANT_OVERHEAD from 100,000 to 200,000. verified
History
100,000 (original) → 200,000 (b7b77d6c86) → renamed RELAY_CONSTANT_OVERHEAD in 2bf225ae17 → REMOTE_RELAY_CONSTANT_OVERHEAD in f4dde99251. The pre-2022 shape was a per-byte "dynamic overhead" of 1 gas/byte plus the constant.
Margin
Not independently derived in the repo. The invariant test band (225k-235k after 37ce0f6928) is described as "enough gas for the relay to record the failure from cold storage, but too little to call the target", which implies the pre-check path plus failure recording fits inside roughly that range. inferred

REMOTE_RELAY_CALL_OVERHEAD (40,000)

Used at
L1CrossDomainMessenger.sol:126, L2CrossDomainMessenger.sol:90 into _baseGas.
Budgets for
"Dynamic parts of the CALL opcode": address access (cold 2,600), positive-value transfer (9,000) and value to empty account (25,000), as in hasMinGas. verified (natspec, SafeCall natspec)
Derivation
It mirrors the hardcoded 40,000 inside hasMinGas: the receiving chain's check requires 40,000 above minGas*64/63, so the sender must supply the same. Added together with the check in 2bf225ae17; the old comment says "3/5 of the CALL opcode's dynamic gas factors". verified
History
2bf225ae17 as RELAY_CALL_OVERHEAD = 40_000; unchanged since. The inline comment in 2bf225ae17 describes it as "gas reserved for performing the external call". verified

MIN_GAS_DYNAMIC_OVERHEAD_NUMERATOR / DENOMINATOR (64 / 63)

Used at
CrossDomainMessenger.sol:384: (_minGasLimit * 64) / 63. Same ratio in hasMinGas (SafeCall.sol:102).
Budgets for
EIP-150: a CALL forwards at most 63/64 of remaining gas, so to deliver minGas to the target the frame needs minGas*64/63. verified
History
b7b77d6c86 used 1016/1000 (a 1.6% empirical margin; EIP-150 needs 1.5625%) in 2022; 2bf225ae17 replaced it with the exact 64/63. The initial uint32 type overflowed for large minGas; baseGas later moved to uint64 (35a7bb5e9c, Aug 2022). verified
EIP-8037
EIP-8037 says the 63/64 rule applies to gas_left only and the state-gas reservoir passes to a child in full. That does not invalidate this ratio for the execution gas the target is promised, but the interaction with gasleft() when a reservoir exists is unverified here. unverified

MIN_GAS_CALLDATA_OVERHEAD (16), TX_BASE_GAS (21,000), FLOOR_CALLDATA_OVERHEAD (40), ENCODING_OVERHEAD (260)

Used at
CrossDomainMessenger.sol:390 (size), CrossDomainMessenger.sol:397-401 (final formula).
Budgets for
The relay transaction's intrinsic cost on the destination chain: 21,000 base; 16 gas per non-zero calldata byte (zero bytes cost 4, so 16 is a worst-case bound); and the EIP-7623 floor of 40 gas per non-zero byte, taking max(execution + calldata, floor). The test comment confirms: "after EIP-7623, we still deduct 21k + 16 gas per calldata token from the gas limit before execution... the EVM will floor the cost to 21k + 40 gas per calldata token". verified
ENCODING_OVERHEAD derivation
Natspec: 260 is an upper bound; actual can be as low as 228 for an empty message. Check: selector 4 + six head words (nonce, sender, target, value, minGas, offset) + length word = 4 + 7*32 = 228; plus up to 31 bytes ABI padding gives 259, rounded to 260. verified (natspec) inferred (the arithmetic is mine)
History
MIN_GAS_CALLDATA_OVERHEAD = 16 since b7b77d6c86 (2022; then applied per message byte only). The other three are new in 8de0d08097 (PR #14608, smartcontracts, Mar 2025): "Updates the way that gas limits are handled ... to account for EIP-7623. Most significant change is to make the baseGas calculation inside of CrossDomainMessenger more principled." The commit comment adds that the floor is "mostly relevant in the L1 -> L2 case ... it doesn't hurt in the L2 -> L1 case", and that contract creation need not be handled. verified
Whose rules
These apply to the destination chain's intrinsic rules, not the sender's. L1 Glamsterdam does not change L2's calldata pricing, and vice versa. L2-to-L1 messages are internal calls inside the finalize transaction, so the floor term there is conservative padding. inferred

Hardcoded 40,000 in SafeCall.hasMinGas

Used at
hasMinGas; natspec SafeCall.sol:85-89; also reached by callWithMinGas via SafeCall.sol:117, used in OptimismPortal2.finalizeWithdrawalTransaction (OptimismPortal2.sol:628).
Budgets for
"The worst case of the dynamic cost of the CALL opcode's address_access_cost, positive_value_cost, and value_to_empty_account_cost factors with an added buffer of 5,700 gas." It explicitly does not cover memory_expansion_cost and code_execution_cost. verified (natspec)
Arithmetic check
2,600 (cold access) + 9,000 (value) + 25,000 (new account) = 36,600, leaving 3,400 of headroom, not 5,700. The documented 5,700 does not reconcile with Berlin-era prices; the value 40,000 stands as a round number. inferred The origin of "5,700" is not explained in 1c612248e5.
History
Introduced in 1c612248e5 (Apr 2023, clabby, "Account for worst-case cost of CALL opcode in callWithMinGas", PR #5508), replacing the earlier "((_minGas + 200) * 64) / 63" check. 6eb05430d1 ("Remove division from hasMinGas for precision", Apr 2023) rewrote the inequality as gas*63 ≥ minGas*64 + 63*(40000+reserved) without changing 40,000. No later change. verified
Effect
It is added on every use, so the Portal's callWithMinGas also requires minGas*64/63 + 40,000; and the messenger's check effectively requires 40,000 + 125,000 + 5,000 = 170,000 above minGas*64/63 post-#681 (previously 85,000). verified

EIP-8037 (Glamsterdam, L1 only) impact

EIP-8037 (fetched from eips.ethereum.org) splits gas into regular and state gas: cost per state byte 1,530; a new storage slot costs 64 bytes (97,920 state gas); a new account 120 bytes (183,600). State gas is paid from a state_gas_reservoir first, then from gas_left; the EIP-7825 cap applies to regular gas only; the 63/64 rule applies to gas_left only, and the reservoir passes to a child in full. verified (from the EIP page)

Open concerns

(a) Post-call reserve must cover a fresh successfulMessages/failedMessages SSTORE including state gas.
Verified: the reserve was raised to 125k for exactly this (37ce0f6928), tests assert the failure is recorded and replayable (test/integration/MessengerETHBricking.t.sol). Concerns, all inferred: (1) 113k was measured in an unoptimized build with forge's Amsterdam model; production builds are cheaper regular-gas wise, but the state-gas component (97,920) is fixed by the EIP, so 125k has ~12k margin over a fixed floor of ~98k plus SSTORE regular gas, event, and the xDomainMsgSender write. If the EIP's constants shift before Glamsterdam ships (CPSB or slot size), 125k must be re-derived. (2) With a state-gas reservoir present (tx gas above the 2^24 cap) gasleft() may not include the reservoir, so state gas may be paid from the reservoir and the 125k reserve is over-provisioned; with no reservoir it is paid from gas_left and the reserve matters. The code subtracts the reserve from gasleft() in both cases; whether that is correct for every reservoir split is not tested. unverified (3) The success path writes successfulMessages and the failure path failedMessages; both are one new slot, but the failure path additionally ran after the target consumed all forwarded gas, which is the case tested.
(b) SafeCall.hasMinGas's 40,000 doesn't cover a new-account state charge on value transfer.
EIP-8037 charges 120 x 1,530 = 183,600 state gas for a CALL with value to a non-existent account (verified from the EIP, arithmetic mine). The 40,000 constant budgets the legacy 25,000 value_to_empty_account_cost only. inferred Consequence: a message with value to an empty account may pass hasMinGas yet leave the CALL itself short of state gas; whether that state gas comes out of the target's forwarded gas (so the target gets less than _minGasLimit) or from the reservoir depends on the EIP's reservoir semantics, which I did not verify. Applies to OptimismPortal2.finalizeWithdrawalTransaction (callWithMinGas) and to relayMessage with value. Also the SafeCall.t.sol changes in 6b1b243623 only "bound explicit call gas above Amsterdam CALL precharges", i.e. the tests were fitted to the new costs, not the constant. verified
(c) Calldata floor constants follow the destination chain's rules.
L1 Glamsterdam does not change L2's calldata pricing, so L1 messenger's _baseGas (budgeting L2 relay) stays on 16/40. For L2 messenger's _baseGas (budgeting L1 relay), the floor is padding only (internal call). Separate forward risk: EIP-7976 (fetched) raises the floor to 64 gas per byte (16 per token, tokens counting zero and non-zero bytes the same). If it ships in the same L1 fork it would not affect L1-to-L2 messages (L2 rules) and would barely matter for L2-to-L1; if L2 ever adopts it, FLOOR_CALLDATA_OVERHEAD = 40 would under-budget. inferred Whether 7976 is in Glamsterdam is not established here. unverified The base-gas tests still hand-write the L2 intrinsic estimate and carry the TODO(#14609) (test/L2/L1CrossDomainMessengerBaseGas.t.sol).
Other observations
• The 85k increase in both directions means every L1-to-L2 and L2-to-L1 message pays more: L1-to-L2 deposits burn ~85k extra L2 gas on L1 per message (L2 side does not need it for 8037). verified (commit message states "both directions")
• L2 LOCAL_RELAY_RESERVED_GAS natspec nit: mentions EIP-8037 although L2 does not get 8037 (L2CrossDomainMessenger.sol:26-28).
• 37ce0f6928 lives on branch jm/glamsterdam-test and was squashed into 6b1b243623 in this branch's history; f4dde99251 is the split.

Open questions

  1. Is 125k on the L2 side required at all? If not, L2.LOCAL_RELAY_RESERVED_GAS and L1.REMOTE_RELAY_RESERVED_GAS could remain 40,000, saving ~85k per L1-to-L2 message. The split in f4dde99251 makes that possible without an API change.
  2. How do state gas and the reservoir interact with gasleft() - LOCAL_RELAY_RESERVED_GAS when tx gas exceeds the 2^24 cap?
  3. Should hasMinGas add state gas for value to empty accounts, and where should the 5,700 figure be corrected?
  4. Is the 200k constant overhead still sufficient on L1 under Glamsterdam for a relay that fails the check and must record from cold storage?
  5. Do EIP-7976 or later fork changes warrant making FLOOR_CALLDATA_OVERHEAD chain-specific?
